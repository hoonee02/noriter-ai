# [작업 지시서] 개인 영속성 메모리 + LLM 위키(백과사전) 기능 구현

## 0. 배경 / 기존 상태와의 관계
이 프로젝트(Noriter AI, Tauri + Rust + Dart Wasm)에는 이미 **세션 한정 작업 기억**(`src-tauri/src/memory.rs`)이 있다 — 최근 3턴은 원문 그대로, 4~8턴 전은 요약, 그 이후는 삭제. 이건 **재시작하면 사라지는 단기 기억**이다.

이번 작업은 그것과 **별개의, 재시작해도 사라지지 않는 두 가지 저장소**를 새로 만드는 것이다:

1. **개인 영속성 메모리 (Personal Persistent Memory)** — 사용자에 대한 오래 남는 사실/선호/맥락 (예: "사용자는 GTX 1660 6GB VRAM 환경을 씀", "엑셀 첨부 시 표 형식 요약을 선호함"). ChatGPT의 "메모리" 기능과 유사한 개념.
2. **LLM 위키 / 백과사전 (Knowledge Base)** — 대화 중 등장한 개념/사실을 독립된 문서(엔트리) 단위로 정리해 쌓아두고, 이후 대화에서 검색/참조할 수 있는 구조. 위키백과처럼 제목-본문-태그-상호링크 구조를 가짐.

두 저장소 모두 세션 작업 기억과 달리 **디스크에 영속 저장**되고, **명시적으로 조회/편집 가능한 UI**를 가져야 한다 (이 프로젝트의 기존 패턴: 🧠모델 / ✈텔레그램 / 📝프롬프트 / ⚙설정 패널처럼, 새 버튼 2개를 추가하는 방향을 권장).

---

## 1. 개인 영속성 메모리 (Personal Persistent Memory)

### 1.1 목적
대화 도중 자연스럽게 드러나는 사용자에 대한 사실을 모아두고, 이후 모든 대화(웹 채팅 + 텔레그램)에 시스템 컨텍스트로 주입한다. 예: 선호 모델, 하드웨어 사양, 자주 다루는 주제, 어투 선호 등.

### 1.2 저장 위치 & 형식
- `AppConfig`과 별도 파일: OS config dir 아래 `noriter-ai/memory.json` (기존 `config.rs`의 `config_path()` 패턴 재사용).
- 단순 JSON 배열. SQLite 등 DB 엔진 도입은 과함 — 이 프로젝트 규모에서는 파일 기반으로 충분.

### 1.3 메타데이터 스키마 (엔트리 1개)
```json
{
  "id": "mem_20260716_001",
  "content": "사용자는 GTX 1660(6GB VRAM) + 32GB RAM 환경에서 로컬 모델을 돌린다.",
  "category": "hardware",       // hardware | preference | fact | instruction | other
  "source": "web",               // "web" | "telegram:{chat_id}" | "manual" (사용자가 직접 UI에서 입력)
  "created_at": "2026-07-16T02:14:00+09:00",
  "updated_at": "2026-07-16T02:14:00+09:00",
  "confidence": "high",          // high | medium | low -- 자동 추출된 사실의 신뢰도
  "pinned": false                // true면 컨텍스트 주입 시 항상 최우선 포함
}
```

### 1.4 채워지는 방식
- **자동 추출**: 매 턴 응답 후, 별도의 짧은 Ollama 호출로 "이번 대화에서 사용자에 대해 기억해둘 만한 새로운 사실이 있는지" 판단시켜 있으면 엔트리로 저장 (기존 `memory.rs`의 요약 호출과 동일하게 `queue::run_queued`를 통해 큐에 태워서 직렬화할 것 — 동시에 두 Ollama 요청이 돌지 않게).
  - 비용이 크므로 매 턴마다 하지 말고, 예: 5턴마다 1번, 또는 사용자가 명시적으로 "이거 기억해둬"라고 말했을 때만 트리거하는 두 가지 모드를 모두 지원.
- **수동 입력**: UI에 "🧑 메모리" 버튼 → 패널에서 사용자가 직접 엔트리를 추가/수정/삭제/pin 가능.

### 1.5 사용 방식
- 매 Ollama 요청 조립 시 (`memory::build_messages`가 하듯), pinned 엔트리 전부 + 최근 갱신된 엔트리 상위 N개(예: 10개)를 하나의 `ChatMessage::text("user", "(사용자에 대해 기억하고 있는 정보: ...)")`로 앞에 붙인다.
- 컨텍스트 크기 예산을 넘지 않도록 엔트리 총 글자수에 상한을 둘 것 (예: 2000자, 넘으면 오래된/낮은 confidence부터 제외).

## 2. LLM 위키 / 백과사전 (Knowledge Base)

### 2.1 목적
대화 중 나온 개념/데이터를 "문서" 단위로 구조화해서 쌓아두고, 나중에 관련 대화가 나오면 검색해서 참고자료로 불러온다. 예: 엑셀 파일을 분석한 결과를 "예제모음.xlsx 분석" 문서로 저장해두면, 나중에 "저번에 분석한 엑셀 자료 다시 보여줘" 같은 요청에 대응 가능.

### 2.2 저장 위치 & 형식
- `noriter-ai/wiki/` 디렉토리 아래 문서 1개당 JSON 파일 1개 (`wiki/{slug}.json`), 또는 `wiki/index.json` 하나에 배열로 (구현 편의상 후자를 권장 — 문서 수가 개인용 앱 규모에서 수백 개를 넘지 않을 것이므로).

### 2.3 메타데이터 스키마 (문서 1개)
```json
{
  "id": "wiki_20260716_001",
  "title": "예제모음.xlsx 데이터 구조",
  "summary": "엑셀 예제 파일의 시트 구성과 데이터 타입 정리",
  "body": "## 기본화면\n...\n## 엑셀데이터\n...",   // 마크다운 본문
  "tags": ["excel", "attachment", "telegram"],
  "source": "telegram:123456789",     // 어느 대화에서 파생됐는지
  "related_ids": ["wiki_20260710_003"], // 상호링크 (위키 특성)
  "created_at": "2026-07-16T02:14:00+09:00",
  "updated_at": "2026-07-16T02:14:00+09:00"
}
```

### 2.4 채워지는 방식
- 사용자가 명시적으로 "이거 위키에 저장해줘" / "정리해서 기록해줘" 라고 하면, 방금 대화(또는 방금 처리한 첨부파일 분석 결과)를 요약해 문서화 → LLM에게 title/summary/tags를 뽑게 하는 별도 Ollama 호출 1회(큐를 통해 직렬화).
- 자동 저장은 하지 않는다 (매 대화를 다 위키화하면 노이즈가 너무 커짐) — 명시적 트리거만.

### 2.5 사용 방식 (검색)
- 새 IPC 커맨드 `wiki_search(query: String) -> Vec<WikiEntry>`: 아주 단순하게 title/tags/body에 대한 부분 문자열 매칭으로 시작 (임베딩 기반 의미 검색은 과설계, 나중에 필요하면 추가).
- 대화 중 사용자가 "저번에 정리한 거 보여줘" 류의 요청을 하면, UI에서 위키 패널을 열어 직접 찾아보게 하는 것으로 충분 (자동으로 대화에 주입하지 않음 — 이건 개인 메모리와 다른 지점: 위키는 "찾아보는 것", 메모리는 "항상 깔려있는 것").

## 3. 아키텍처 반영 지침 (이 프로젝트 컨벤션 준수)

- Rust 모듈 분리: `src-tauri/src/personal_memory.rs`, `src-tauri/src/wiki.rs` (기존 `memory.rs`, `queue.rs`와 같은 레벨).
- 모든 상태는 `tauri::State`로 관리 (`PersonalMemoryState`, `WikiState`), `AppHandle`을 통해 `telegram.rs`/`main.rs` 양쪽에서 접근.
- Ollama 호출은 전부 `queue::run_queued()`를 통과시킬 것 — 이 프로젝트의 불변식(웹+텔레그램이 Ollama를 동시에 부르지 않음)을 절대 깨지 말 것.
- Dart Wasm 쪽: `dart_ui/lib/main.dart`에 새 헤더 버튼 2개(🧑 메모리, 📚 위키) + 패널 추가, 기존 🧠모델/✈텔레그램/📝프롬프트/⚙설정 패널과 동일한 토글/저장 패턴을 그대로 따를 것 (새로운 패턴을 발명하지 말 것).
- `AppConfig`(`config.rs`)에는 아무것도 추가하지 말 것 — 이건 별도의 새 파일들(`memory.json`, `wiki/index.json`)로 관리해야 함 (설정과 데이터를 섞지 않기 위해).
- 작업 완료 후 SPEC.md/CHANGELOG.md/BUGFIXES.md 갱신을 잊지 말 것 (이 프로젝트의 기존 관례).

## 4. 하지 말아야 할 것 (과설계 방지)
- SQLite/임베딩 벡터DB 도입 금지 (이 앱 규모에 안 맞음, 파일 기반 JSON으로 충분).
- 매 턴마다 자동으로 위키 문서를 만드는 것 금지 (노이즈 폭증).
- 개인 메모리와 위키를 하나의 저장소로 합치는 것 금지 (용도가 다름: 하나는 "항상 주입", 하나는 "검색해서 찾아보는 것").
