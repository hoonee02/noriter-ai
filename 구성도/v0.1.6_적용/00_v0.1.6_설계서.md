## 1. 왜 바꾸는가 — 임시방편이 UI가 되어 있었다

v0.1.5 결함 조치를 끝내고 앱을 띄웠을 때, 📚 위키 패널은 이런 모습이었다.

```
[📥 자료 통합]  원문을 붙여넣는 칸
[🏢 기업 스코프] 기업명을 적는 칸
[❓ 위키에 질문]  질문을 적는 칸
[저장 폼]        제목 · 요약 · 본문 · 태그 · 기업 · 회계기간 · ☑재무수치
```

**이 항목들의 출처를 따져보면 절반이 v0.1.5 조치 과정에서 내가 만든 것이다.**

| 항목 | 언제 생겼나 | 설계상 **원래 누가** 채우나 |
|---|---|---|
| 제목·요약·본문·태그 | v0.1.4 수동 저장 폼 | **ingest** — 모델이 구조화([D1](../v0.1.5_적용/00_v0.1.5_설계서.md)) |
| 기업 | **D-05b 조치** (2026-08-02) | **Taxonomy 2단계**([설계서 §4.1.2](../v0.1.5_적용/00_v0.1.5.1_설계서.md)) |
| 회계 기간 | **D-05b 조치** | 전처리부의 재무제표 파싱 |
| ☑ 재무 수치 | **D-04 조치** | 전처리부/Taxonomy — **O-22로 미결**([09 §6](../v0.1.5_적용/09_재무수치_정의.md)) |

즉 **에이전트가 판정해야 할 값을, 그 에이전트가 아직 없다는 이유로 사람에게 물어보고 있었다.**
D-05a(읽기 필터)를 만들려면 `company`를 채우는 경로가 하나는 필요했고, 그래서 가장 빠른
경로인 "사용자에게 입력받기"를 택한 것이다. 결함은 닫혔지만 **미완성 상태가 제품의 UI로
굳어졌다.**

### 이것이 silent-wrong의 UI판이다

v0.1.5 결함 8건을 관통한 성질은 *"동작은 하는데 조용히 틀린다"* 였다. 이번 건도 형태가 같다 —
화면은 멀쩡히 동작하고 저장도 되지만, **사용자는 자기가 왜 이걸 채우고 있는지 알 수 없다.**
"LLM 위키"라면서 사람이 메타데이터를 손으로 입력하는 모순이 눈에 보이지 않은 채 유지됐다.

> **교훈**: 결함을 막기 위해 세운 임시 경로는 **임시임을 코드가 아니라 제품 표면에 드러낸다.**
> `// O-22 미결이라 사람이 표시` 주석은 개발자만 보지만, 체크박스는 사용자가 매번 본다.

## 3. 라우팅 — `chairman::decide_intent`

```rust
pub enum Intent { Chat, WikiQuery, WikiIngest }

pub async fn decide_intent(
    app: &AppHandle, model: &str, num_ctx: u32,
    prompt: &str, attachment_names: &[String],
) -> Intent
```

**세 갈래로만 나눈다.** 설계 §2.4의 `Routing`(분류 필요 / 스탠드얼론)보다 거칠지만, Taxonomy·
Research가 아직 없으므로 지금 구분할 수 있는 최소 단위다. 에이전트가 들어오면 `WikiQuery`
안쪽이 `NeedsClassification`/`StandaloneResearch`로 다시 갈린다.

### 판별 실패 시 `Chat`으로 떨어뜨린다

```rust
Ok(r) => Intent::from_label(&r.content).unwrap_or(Intent::Chat),
Err(e) => { eprintln!("chairman: routing failed, treating as chat: {e}"); Intent::Chat }
```

`Chat`은 **디스크에 아무것도 쓰지 않는 유일한 결과**다. 오분류 비용이 "사용자가 다시 물어본다"에
그치는 쪽으로 몰아둔 것이며, 반대로 `Ingest`로 잘못 떨어지면 원치 않는 페이지가 위키에 남는다.

### 라벨 파싱은 관대하게

소형 로컬 모델은 `QUERY -- 위키를 찾아야 함`처럼 덧붙인다. 정확 일치만 인정하면 멀쩡한 판정이
전부 `Chat`으로 떨어지므로 **접두사 매칭 + 대소문자 무시**로 받는다(D-08 파싱 완화와 같은 판단).

### LLM 호출 1회 추가 — E-3에 반영해야 한다

라우팅이 `call_llm`을 한 번 더 부른다(D-01 원칙 준수). [05 체크리스트](../v0.1.5_적용/05_확인사항_체크리스트_v0.1.5.2.md)
E-3("파이프라인 LLM 호출 수")의 실측 대상에 이 호출이 추가된다.

## 4. 기업 스코프 — 문장에서 뽑는다

입력칸을 없앤 자리는 **RD-01 조치로 이미 만들어둔 것**이 대신한다.

```rust
let scope = preflight::match_known_company(&entries, &prompt).map(|c| c.corp_code);
```

[설계서 §8.2.3](../v0.1.5_적용/00_v0.1.5.1_설계서.md)이 정한 그대로다 — 위키에 이미 있는 기업명과
문자열 매칭(LLM 없음), 최장 일치, 못 찾으면 `None`. **입력칸을 지우면서 잃은 기능이 없다**:
사용자가 "삼성전자 재무 어때?"라고 쓰면 그 문장에서 스코프가 잡힌다.

> 오히려 나아진 점: 입력칸 시절에는 스코프를 **한 번 적어두면 계속 남아** 다음 질문에도
> 조용히 적용됐다. 이제는 문장마다 다시 판정하므로 스코프가 눌러붙지 않는다.

## 5. 첨부파일 — 텔레그램과 같은 규칙으로

`attachment.rs`를 신설해 `telegram.rs`에 있던 추출 로직을 옮겼다.

| 파일 | 처리 |
|---|---|
| 이미지(png/jpg/gif/webp/bmp) | base64로 모델에 `images`로 전달 |
| `.xlsx` | `calamine`으로 시트별 표 → 텍스트 |
| 그 외 | UTF-8(lossy) 디코드 |

- **8000자 상한**을 넘으면 자르고 **자른 사실을 본문에 명시**한다 — 조용히 줄이면 모델이 일부만
  보고 전체를 본 것처럼 답한다(D-04와 같은 원칙).
- 웹 UI는 `FileReader`로 base64를 만든다. 바이트를 Dart에서 문자 루프로 도는 방식은 수 MB
  스프레드시트에서 UI 스레드를 멈추게 하므로 브라우저 네이티브 인코딩을 쓴다.

## 5.1 진입점을 합치면서 생긴 회귀 — 대화 기억 단절 (RG-01)

**증상**: 위키 질의로 라우팅되면 대화 기억이 통째로 빠졌다. "삼성전자 정보 뽑아줘" 다음에
"이 정보에 대한 날짜를 알려줘"라고 물으면 모델은 **"이 정보"가 무엇인지 알 수 없다.**

**원인**: `ollama_chat`에서 `memory::build_messages`를 부르는 곳이 `Chat` 분기뿐이었다.

```rust
chairman::Intent::WikiQuery => {
    let answer = wiki::query(...).await?;   // 기억 없음
    return Ok(...);                          // record_turn 도 없음
}
```

두 방향으로 끊긴다.

| 빠진 것 | 결과 |
|---|---|
| 기억을 **읽지** 않음 | 후속 질문이 맥락 없이 모델에 감 |
| 턴을 **기록**하지 않음 | 이후 일반 대화에서도 그 턴이 통째로 비어 있음 |

**왜 생겼나**: v0.1.4~0.1.5에서 위키 질의는 **별도 버튼**이었다. 대화창 밖의 독립 행위였으므로
대화 기억이 없는 것이 오히려 자연스러웠다. 0.1.6에서 같은 대화창으로 합치면서 **사용자의 기대는
"대화가 이어진다"로 바뀌었는데 코드는 예전 전제 그대로**였다.

> 이것이 §1에서 말한 함정의 반복이다 — **경로를 옮기면 그 경로가 기대던 전제도 함께 옮겨야
> 한다.** 입력 UI만 옮기고 그 뒤의 가정을 그대로 두면 이런 구멍이 남는다.

**조치**

| 대상 | 내용 |
|---|---|
| `memory::history_messages` | `build_messages`에서 "현재 프롬프트를 뺀 기억"만 분리 — 자체 프롬프트를 만드는 경로(위키 질의)가 쓸 수 있게 |
| `wiki::query(.., history)` | 기억을 앞에 붙여 호출 |
| `ContextBudget::reserving(chars)` | **기억이 차지한 만큼 위키 몫을 줄인다** |
| QUERY·INGEST 분기 | `record_turn` 추가 |

**예산 차감이 핵심이다.** 기억과 위키 컨텍스트가 각자 전체 창을 기준으로 크기를 잡으면 합쳐서
넘치고, 넘치면 **꼬리가 조용히 잘린다** — D-04가 없앤 바로 그 실패가 한 겹 밖에서 재현된다.
회귀 테스트 `history_takes_its_share_out_of_the_content_budget`으로 고정했다.

### `update`(편집)를 없앤 것의 대가

사용자가 **"완전 제거"** 를 선택하면서 **모델이 잘못 정리한 문서를 손으로 고칠 방법이
사라졌다.** 남은 수단은 두 가지다.

1. **검토 대기에서 거르기** — 질의 답변은 `draft.json`에 쌓이고, 확인 후 "위키에 반영"을
   눌러야 승격된다(D-03). 잘못된 내용은 여기서 "버리기".
2. **삭제 후 재요청** — 이미 승격된 페이지는 지우고 다시 정리시킨다.

> ⚠ **이 절충을 기록해 둔다**: 편집이 없으므로 **부분 수정이 불가능**하다. 긴 문서에서 한 줄만
> 틀렸을 때도 통째로 다시 만들어야 한다. 사용자가 이 비용을 알고 선택했으나, 실사용에서
> 불편이 확인되면 "직접 편집"을 되살리는 것이 첫 번째 후보다.

## 7. 이 변경이 기존 미결 항목에 미치는 영향

| 항목 | 변화 |
|---|---|
| **O-22** (`body_required`를 누가 세우나) | **더 급해졌다.** 사람에게 묻는 임시 경로가 사라졌으므로 현재 ingest 저장분은 전부 `false`다 → 재무 페이지가 요약으로 강등될 수 있다. **전처리부 구현 시 최우선** |
| **D-05b** (쓰기 경로에 company 채우기) | 수동 입력이 사라져 **Taxonomy 없이는 `company`가 채워지지 않는다**. 현재 ingest 저장분은 `company: None` → 스코프 필터가 개념 페이지로만 취급 |
| **E-3** (LLM 호출 수) | 라우팅 1회 추가 |
| **D-2** (Research 스탠드얼론 기준) | `decide_intent`가 그 자리를 임시로 채운다. 기준 확정 시 이 함수가 확장 대상 |

> **정직하게 적어둔다**: 이번 변경으로 **`company`·`period`·`body_required`가 당분간 아무도
> 채우지 않는 필드가 된다.** D-05a 필터와 D-04 예산 배분은 코드로는 완성돼 있으나, 값이 비어
> 있으므로 **실질적으로는 Taxonomy·전처리부가 들어와야 작동한다.** 수동 입력은 그 값을
> 채우는 유일한 경로였고, 그것을 없앤 것은 "임시방편을 제품에 남기지 않는다"를 택한 결과다.

## 9. 실동작 확인 상태 — 아직 검증되지 않았다

0.1.6 앱으로 라우팅을 확인한 적이 **없다.** 0.1.5.2 앱이 떠 있는 상태에서 질의 2건이 이뤄졌고,
그것은 위키 패널의 질문 입력칸을 거친 것이므로 `decide_intent`를 지나지 않았다.

| 확인된 것 | 확인 안 된 것 |
|---|---|
| D-03 2저장소 분리(답변이 `draft`로) — 0.1.5.2에서 확인 | **라우팅 3갈래 분기** |
| | INGEST 경로·첨부파일 |
| | 기업 스코프 문장 추출 |
| | 검토 대기 → 반영 승격 |
| | RG-01 조치 후 후속 질문 맥락 유지 |

> 라우팅 오분류 빈도는 소형 모델에서 특히 중요하다 — `decide_intent`가 `Chat`으로 떨어지면
> 사용자는 "위키에 안 들어갔다"만 보게 되므로, 실측 전에는 이 설계가 성립한다고 말할 수 없다.
