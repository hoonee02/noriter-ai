## 1. 모든 문서를 관통하는 하나의 문제의식

형태는 다르지만, 열 개 문서 전부가 결국 같은 질문에서 출발한다 — **"LLM과의 상호작용에서 만들어진
지식이 왜 대화가 끝나면 사라지는가, 그리고 어떻게 영속화·재사용할 것인가"**. 메이커 에반 영상은
이를 "어제 설명한 걸 오늘 또 설명해야 한다"는 사용자 경험으로, LLM위키 완벽 가이드는 "반복 설명이야말로
위키로 남길 재료"라는 실무 원칙으로, 에르메스 에이전트는 "AI 에이전트가 무엇을 기억해야 하는가"라는
시스템 설계 문제로 각각 표현한다. 결국 하나의 문제의식이 세 가지 층위(개인 사용자 경험 → 실무 운영
절차 → 에이전트 시스템 아키텍처)로 반복 등장하는 셈이다.

## 2. 공통으로 반복되는 8가지 원칙

### (1) raw ↔ 정리본을 분리하고, 정리본을 재사용 단위로 삼는다
- [구성도.md](구성도.md)의 "입력 소스 → 구조화 → 저장소" 3단 흐름
- 카파시 방식의 "원본 파일 / AI가 만든 위키 / CLAUDE.md" 3요소 ([메이커 에반 구성도.md](메이커%20에반%20Maker%20Evan-구성도.md))
- LLM위키 완벽 가이드의 raw/wiki/schema 3층 구조, "원본과 정리본을 섞지 마라" 원칙
- Deep Agents의 Store Backend([딥에이전트_핵심개념.md](딥에이전트_핵심개념.md))도 결국 같은 역할을 코드 레벨에서 수행

### (2) 요약·인덱스를 먼저 보고, 필요한 만큼만 하위로 내려간다 (토큰 절감의 공통 원리)
- Hierarchical RAG의 "다단계 요약 후 선택적 확장" ([RAG_개념_확장.md](RAG_개념_확장.md))
- 하이브리드 에이전트의 부모-자식 청크·요약 인덱싱, 라우터가 거시/중간/미시 질문을 분기 ([하이브리드_에이전트_RAG.md](하이브리드_에이전트_RAG.md))
- Graphify의 `GRAPH_REPORT` 1페이지 요약 → 관련 노드 2~3개만 열람(최대 71.5배 절감 주장, [메이커 에반 구성도.md](메이커%20에반%20Maker%20Evan-구성도.md))
- LLM위키의 `INDEX.md` 우선 확인
- 이 원리는 별개로 발명된 것이 아니라 **동일한 아이디어가 이름만 바뀌어 반복 등장**한다는 점이 이번 종합에서 가장 뚜렷하게 드러난 패턴이다.

### (3) 관계(그래프)를 남겨야 다중 홉 질문과 근거 제시가 가능하다
- Graph RAG 개념 ([RAG_개념_확장.md](RAG_개념_확장.md))의 실제 구현체가 GraphRAG_완전정복(Neo4j/Cypher)이며,
  "전통 RAG는 점 단위 검색이라 다중 홉 질의에 약하다"는 것이 그 책의 핵심 메시지
- Graphify의 관계 유형("이걸 근거로 만들었다" 등)과 신뢰도 등급(확실/추론/불확실)
- **워크플로우 그래프(LangGraph) vs 지식 그래프(GraphRAG)는 서로 다른 축**이라는 점을 GraphRAG_완전정복
  요약이 명시적으로 구분함 — 전자는 "실행 흐름"을, 후자는 "데이터 구조"를 그래프로 표현한다.

### (4) 명시적 트리거 원칙 — 자동 축적은 노이즈를, 사람의 확인은 신뢰를 만든다
- [구성도.md](구성도.md) §4 "자동 저장 vs 명시적 저장"
- LLM위키 완벽 가이드의 "근거 없는 문장은 확인 필요로 표시하라"
- [메이커 에반 구성도_확장.md](메이커%20에반%20Maker%20Evan-구성도_확장.md) 가상 명세의 "부서 담당자의 명시적 요청이 있을 때만 위키에 통합"
- 이 원칙은 자동화를 포기하자는 것이 아니라, **무엇을 자동화하고 무엇을 사람이 승인할지 경계선을 명확히 그으라**는 요구로 일관된다.

### (5) 검색 후 생성에서 끝나지 않고, 결과가 다시 지식으로 축적되는 되먹임 루프
- Self-updating RAG ([RAG_개념_확장.md](RAG_개념_확장.md))
- 카파시 위키의 "질의 응답이 다시 새 위키 페이지로 저장" ([메이커 에반 구성도.md](메이커%20에반%20Maker%20Evan-구성도.md))
- LLM위키 6장 "검증한 내용을 다시 위키에 반영"
- 에르메스 에이전트의 shared-memory([에르메스_에이전트_핵심개념.md](에르메스_에이전트_핵심개념.md))
- 다만 (4)와 긴장 관계에 있다 — 되먹임을 무제한 허용하면 노이즈가 쌓이므로, 실제로는 "질의 결과는
  일단 로그로 쌓되 승격은 사람이 검토"하는 절충이 여러 문서에서 공통적으로 나타난다.

### (6) 단일 에이전트가 아니라 역할이 분업된 에이전트 조직으로 확장된다
- LangGraph 가이드북 Part4의 Supervisor·Handoffs 패턴 (코드 아키텍처)
- 에르메스 에이전트의 조사형/정리형/실행형 역할 분담 (운영 관찰, [에르메스_에이전트_핵심개념.md](에르메스_에이전트_핵심개념.md))
- Deep Agents의 서브에이전트 위임 (`create_deep_agent()` API)
- 세 문서는 같은 문제(하나의 에이전트가 모든 걸 처리하지 않는다)를 **코드/개념/운영-관찰**이라는
  서로 다른 층위에서 다룬다는 점이 흥미로운 대응 관계다.

### (7) 도구/외부 연동은 "함수로 추상화된 도구함"으로 수렴한다
- 하이브리드 에이전트의 Tool Definition (`search_executive_summary()` 등)
- 딥에이전트·에르메스 에이전트의 MCP 도구 서버 연동
- 「LLM부터 Agent까지」 00장(Claude Code의 서브에이전트/Skills/MCP/Hooks)도 실무 도구 수준에서 같은 개념
- 즉 "검색"이든 "업무 자동화"든, 에이전트가 다루는 외부 기능은 결국 **이름 붙은 호출 가능한 함수**로 수렴한다.

### (8) 유지보수·평가는 별도 층위로 분리되고, 결과물 자체를 오염시키지 않는다
- [구성도.md](구성도.md)의 유지보수(모순/고아 문서 탐지)는 "문서로 저장하지 않고 리포트로만" 남긴다는 원칙
- 하이브리드 에이전트의 Retrieval/Generation Evaluator (재검색 트리거, 할루시네이션 검증)
- LLM위키 8장의 정기 감사 흐름, [메이커 에반 구성도_확장.md](메이커%20에반%20Maker%20Evan-구성도_확장.md)의 `#wiki-lint` 슬랙 리포트
- LangGraph의 Guardrails(결정론적 규칙 → LLM 심사 → HITL 3중 방어)도 같은 축의 "검증 레이어 분리" 사례

## 3. 하나의 통합 아키텍처로 겹쳐 그리기

앞의 8가지 원칙을 한 장의 다이어그램으로 합치면, 지금까지의 개별 문서들은 아래 구조의 서로 다른
부분을 확대한 것이었음을 알 수 있다.

                    ┌────────────────────────┐
                    │  수집·구조화 (Ingest)     │  단일 문서 통합 vs 다중 문서 동시 갱신
                    └────────────┬───────────┘
                                 ▼
      ┌──────────────────────────────────────────────────────────┐
      │                     저장소 (원칙 1)                         │
      │  ┌────────────┐  ┌───────────────┐  ┌──────────────────┐ │
      │  │ 위키 문서    │  │  관계 그래프    │  │  요약/인덱스 계층   │ │

      │  │             │  │  등급 포함)     │  │                   │ │
      │  └────────────┘  └───────────────┘  └──────────────────┘ │
      └───────────────────────────┬──────────────────────────────┘
                                   │
                 ┌─────────────────┼─────────────────┐
                 ▼                 ▼                 ▼
        ┌────────────────┐ ┌──────────────┐ ┌──────────────────┐
        │ 라우터 (원칙 2)   │ │ 도구함/MCP     │ │ 멀티 에이전트 분업   │

## 4. 문서마다 다른 이름, 같은 개념 — 용어 대응표

| 공통 개념 | 구성도.md | 카파시/Graphify | LLM위키 완벽 가이드 | LangGraph 가이드북 | GraphRAG 완전정복 | 에르메스/딥에이전트 |
|---|---|---|---|---|---|---|
| 원본 데이터 | 입력 소스 | raw 폴더 | raw | (문서 로딩) | 원본 문서 | 채널/메일/회의록 |
| 정리된 지식 | 문서 저장소 | wiki 폴더 | wiki | (RAG 벡터 저장소) | 지식 그래프 | 위키/장기 메모리 |
| 요약 우선 탐색 | 인덱스(태그/제목) | GRAPH_REPORT / INDEX.md | INDEX.md | (요약 미들웨어) | GRAPH_REPORT 유사 개념 없음(파트7 요약 페이지) | context_schema |
| 관계 정보 | 링크 그래프(related_ids) | graph.json 관계 유형 | 문서 간 연결 | StateGraph 엣지(실행 흐름) | Cypher 관계(엔티티 그래프) | (명시적 그래프 없음) |
| 운영 규칙 문서 | (미정의) | CLAUDE.md | AGENTS.md/CLAUDE.md | (시스템 프롬프트) | (없음, 코드로 구현) | AGENTS.md/USER.md/SOUL.md |
| 검증 레이어 | 유지보수 | (grep 금지 지시) | 근거 라벨링(확인 필요) | Guardrails/Evaluator | (RAGAS 유사 평가 없음, 성능 튜닝 중심) | 없음(운영 체크리스트로 대체) |

이 표에서 가장 눈에 띄는 것은, **모든 소스가 "원본/정리본/요약인덱스/관계/운영규칙/검증"이라는
동일한 6칸을 채우고 있지만, 어느 소스도 6칸을 전부 명시적으로 정의하지는 않는다**는 점이다. 즉
하나의 구현체를 설계한다면 이 표의 빈 칸들이 실제 보완해야 할 지점이다.

## 5. 실무 적용 체크리스트 (전체 문서 종합)

- [ ] 원본과 정리본을 물리적으로 분리했는가 (원칙 1)
- [ ] 요약/인덱스 우선 탐색 경로가 있는가, 이를 강제하는 운영 규칙 문서(CLAUDE.md류)가 있는가 (원칙 2)
- [ ] 개념 간 관계에 "종류"와 "신뢰도"를 함께 기록하는가 (원칙 3)
- [ ] 무엇을 자동 반영하고 무엇을 사람이 승인할지 경계가 명시되어 있는가 (원칙 4)
- [ ] 질의 결과가 다시 지식으로 승격되는 경로가 있되, 무분별한 자동 승격은 막았는가 (원칙 5)
- [ ] 복잡한 작업을 역할별 에이전트로 분업할 필요가 있는지 검토했는가 (원칙 6)
- [ ] 외부 기능을 이름 붙은 도구(Tool/MCP)로 추상화했는가 (원칙 7)
- [ ] 정합성 점검·평가 결과가 본문을 오염시키지 않고 별도 로그로 분리되는가 (원칙 8)

## 6. 결론

`구성도/` 폴더에 쌓인 문서들은 겉보기엔 서로 다른 책·영상·개념 노트지만, 실제로는 하나의
문제("휘발되는 LLM 지식을 어떻게 영속화·재사용할 것인가")를 개인 사용자 경험 → 실무 운영 절차 →
코드 아키텍처 → 조직 운영이라는 서로 다른 고도(altitude)에서 반복해서 풀어낸 결과물이다. 이번
종합에서 확인된 8가지 원칙과 6칸짜리 용어 대응표는, 앞으로 새 문서를 추가하거나 실제 시스템을
설계할 때 "이 문서/설계가 어느 원칙을, 어느 고도에서 다루고 있는가"를 빠르게 위치짓는 기준으로
쓸 수 있다.
