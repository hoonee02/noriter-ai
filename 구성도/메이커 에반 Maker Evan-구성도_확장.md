# LLM 위키 + Graphify 기반 사내 의사결정 지원 시스템 (가상 명세)

> [메이커 에반 Maker Evan-구성도.md](메이커%20에반%20Maker%20Evan-구성도.md)에 정리한 "카파시 LLM 위키 + Graphify" 개념을,
> 가상의 회사 프로세스에 접목해 의사결정 전략과 업무 효율화를 위한 시스템으로 확장·설계한 명세서.
> 실존 제품/조직과 무관한 가상 시나리오이며, 원 영상에 없는 내용(조직 구조, KPI, 운영 규칙 등)은
> 이 문서에서 새로 설계한 것이다.

## 1. 가상 시나리오

- 회사: 30인 규모 B2B SaaS 스타트업 "가상컴퍼니"
- 문제 상황:
  - 매주 발생하는 고객 미팅록, 세일즈 노트, 경쟁사 리서치, 제품 스펙 문서, 이슈 트래커 로그가
    부서별로 흩어져 있고, 신규 의사결정마다 담당자가 과거 자료를 처음부터 다시 찾아 읽음.
  - "지난 분기에 왜 이 가격 정책을 접었더라?" 같은 질문에 답하려면 슬랙 검색 + 문서함 뒤지기로
    평균 2~3시간 소요.
  - 신규 입사자 온보딩 시 동일한 배경 설명을 매번 사람이 반복.
- 목표: LLM 위키 + Graphify 구조를 도입해, "한 번 정리한 지식을 조직 전체가 재사용"하는
  의사결정 지원 체계를 구축한다.

## 3. 폴더/파일 명세

```
company-wiki/
├── raw/
│   ├── sales/            # 세일즈 CRM 노트, 상담 녹취 요약
│   ├── product/           # 제품 스펙, 로드맵 문서
│   ├── cs/                # 고객 문의·피드백 로그
│   ├── finance/           # 예산, 매출 리포트
│   ├── competitor/        # 경쟁사 리서치
│   └── meetings/          # 회의록 원본
├── wiki/
│   ├── decisions/          # "2026-Q1 가격 정책 변경" 같은 결정 단위 페이지
│   ├── entities/           # 고객사, 경쟁사, 제품 기능 등 개체 페이지
│   ├── concepts/           # "이탈률", "PMF 지표" 같은 반복 개념 페이지
│   └── INDEX.md            # 전체 위키 목차
├── graph.json               # Graphify가 생성하는 전체 관계 그래프
├── GRAPH_REPORT.json        # 1페이지 요약 (핵심 개념/그룹/신뢰도/답변 가능 질문 목록)
└── CLAUDE.md                # 아래 4번 항목의 운영 규칙
```

## 4. CLAUDE.md 운영 규칙 (가상 명세)

```markdown
# company-wiki 운영 규칙

## 수집 (Ingest)
- raw/ 하위에 새 파일이 들어오면, 해당 부서 담당자의 명시적 요청이 있을 때만 위키에 통합한다.
  (전 직원 대화가 자동으로 위키에 쌓이지 않도록 — 노이즈 방지를 위해 "저장" 트리거 필수)
- 통합 시 wiki/decisions, wiki/entities, wiki/concepts 중 적절한 위치에 페이지를 생성하거나
  기존 페이지를 업데이트한다. 신규 생성보다 기존 페이지 갱신을 우선 검토한다.

## 질의 (Query)
- 질문을 받으면 원본 파일을 직접 탐색하지 말고, 반드시 GRAPH_REPORT.json을 먼저 읽는다.
- GRAPH_REPORT에서 식별된 관련 노드 2~3개만 wiki/ 에서 열람한다.
- grep으로 raw/ 전체를 훑는 행위는 금지한다. (토큰 낭비 방지)
- 답변 시 신뢰도 등급(확실/추론/불확실)을 함께 표시한다.
- 답변은 다시 wiki/decisions 아래 "질의 로그" 페이지로 저장해, 동일 질문 재발생 시 재사용한다.

## 유지보수 (Maintenance)
- 매주 1회 wiki 전체에 대해 다음을 점검한다: 모순되는 결정 페이지, 연결 없는 고아 페이지,
  자주 언급되지만 전용 페이지가 없는 개념.
- 점검 결과는 문서화하지 않고 #wiki-lint 슬랙 채널에만 리포트한다.
```

## 5. 의사결정 전략에의 접목

### 5.1 결정 단위 페이지 (wiki/decisions/*.md)
모든 주요 의사결정을 아래 템플릿으로 위키 페이지화한다.

| 필드 | 설명 |
|---|---|
| 결정 제목 | 예: "2026-Q1 Freemium 요금제 폐지" |
| 배경 | 관련 raw 소스(회의록, 데이터) 링크 |
| 대안 | 검토했던 다른 선택지들 |
| 근거 | Graphify 관계 유형("이 데이터를 근거로 함") 표시 |
| 신뢰도 | 확실 / 추론 / 불확실 |
| 결정자 / 결정일 | |
| 관련 페이지 | related_ids로 연결된 다른 결정·개념 |

- 효과: 신규 의사결정 시 AI가 GRAPH_REPORT를 통해 "과거 유사 결정"을 즉시 찾아 제시 →
  같은 실수 반복 방지, 결정 근거의 추적 가능성(traceability) 확보.

### 5.2 신뢰도 기반 의사결정 브리핑
- AI가 의사결정 브리핑을 생성할 때, 원본에 명시된 사실(확실)과 AI가 추론한 해석(추론)을
  분리해서 제시하도록 강제 — 임원진이 "이건 데이터고, 이건 AI 해석이다"를 구분해 판단 가능.
- 불확실 등급 항목은 별도로 "추가 확인 필요" 섹션에 모아 제시.

### 5.3 온보딩 자동화
- 신규 입사자가 특정 고객사·프로젝트에 배치되면, 해당 entity 노드와 연결된 그룹(관련 결정,
  관련 회의록 요약)을 GRAPH_REPORT 기준으로 자동 브리핑 생성 → 사람이 반복 설명할 필요 제거.

### 5.4 분기 회고/감사
- graph.json의 시간 축(created_at/updated_at)을 활용해, 분기별로 "이 시기에 내려진 결정들과
  그 근거"를 자동 추출 → 회고 미팅 준비 시간 단축.

## 6. 효율성 기대 효과 (가상 추정치)

| 항목 | 도입 전 | 도입 후 (가상 추정) |
|---|---|---|
| 과거 의사결정 근거 조회 시간 | 2~3시간 (수동 검색) | 요약 페이지 1장 + 관련 노드 2~3개 열람 |
| 신규 입사자 온보딩 설명 시간 | 담당자별 반복 설명 다수 | 자동 브리핑 1회 생성 후 재사용 |
| 컨텍스트 조회 시 토큰/비용 | 원본 문서 전체 반복 조회 | GRAPH_REPORT 기반으로 대폭 절감 (원 영상 기준 최대 71.5배 참고치) |
| 결정 근거 추적성 | 구두 전달·기억 의존 | wiki/decisions 페이지로 영구 기록 |

> ※ 절감 배수는 원 영상(카파시/Graphify)에서 언급된 수치를 참고치로 인용한 것이며,
> 실제 도입 시 데이터 규모와 질의 패턴에 따라 달라진다.

## 7. 리스크 및 운영 상 주의점 (가상 설계 시 고려사항)

- **자동 저장 vs 명시적 저장**: 민감한 결정 정보가 자동으로 위키에 쌓이면 접근 권한 관리가
  복잡해지므로, 4번 CLAUDE.md 규칙처럼 명시적 트리거를 원칙으로 함.
- **권한 분리**: wiki/decisions 중 재무·인사 관련 페이지는 별도 접근 권한(부서별 ACL) 필요.
- **신뢰도 오남용 방지**: "추론" 등급 정보가 마치 확정 사실처럼 인용되지 않도록, 브리핑
  템플릿에서 신뢰도 표시를 필수 항목으로 강제.
- **고아 결정 페이지 관리**: 담당자가 퇴사하거나 프로젝트가 종료된 결정 페이지는 주 1회
  유지보수 점검에서 아카이브 대상으로 표시.
