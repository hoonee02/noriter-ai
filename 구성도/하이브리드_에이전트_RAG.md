# 하이브리드 에이전트 (Agentic + Hierarchical RAG)

[RAG_개념_확장.md](RAG_개념_확장.md)에서 정리한 RAG 확장 형태 중 **Agentic RAG**(자율적 판단 능력)와
**Hierarchical RAG**(방대한 문서의 계층적 구조화 능력)를 결합한 아키텍처.
수백 페이지 매뉴얼, 사내 규정집, 복잡한 코드베이스처럼 크고 복잡한 문서를 다룰 때 가장
강력한 구성으로 꼽힌다. 이 문서는 이를 성공적으로 구현하기 위해 레이어별(데이터 / 에이전트 /
오케스트레이션)로 반드시 갖춰야 할 핵심 요소를 정리한다.

## 1. 데이터 레이어 — Hierarchical(계층형) 인덱싱 구조

방대한 데이터에서 에이전트가 길을 잃지 않도록, 문서를 다단계로 쪼개고 연결하는 구조가 필요하다.

### 1.1 다단계 청킹 (Multi-level Chunking)
- **부모-자식 청크(Parent-Child Chunk)**: 문서를 요약본 형태의 큰 청크(Parent)와 아주 구체적인
  세부 문장 형태의 작은 청크(Child)로 나누어 저장.
- 검색은 세부 청크(Child)로 정밀하게 하고, LLM에 컨텍스트를 넘길 때는 맥락이 살아있는
  부모 청크(Parent)를 넘겨준다 — 정밀한 매칭과 문맥 보존을 동시에 확보하는 방식.

### 1.2 요약 메타데이터 인덱싱 (Summary Indexing)
- 문서 전체 요약본, 장(Chapter)별 요약본, 절(Section)별 요약본을 각각 별도로 인덱싱.
- "이 문서 전체의 핵심이 뭐야?" 같은 거시적 질문에는 수만 개의 자잘한 청크를 뒤지는 대신
  '문서 요약 인덱스'로 바로 찾아갈 수 있게 한다.
- [구성도.md](구성도.md)에서 다룬 인덱스(제목/요약/태그) 우선 탐색, [메이커 에반 구성도.md](메이커%20에반%20Maker%20Evan-구성도.md)의
  `GRAPH_REPORT`/`INDEX.md` 우선 탐색 개념과 동일한 원리다.

### 1.3 하이브리드 검색 (Hybrid Search)
- **벡터 검색(Dense Retrieval)**: 의미 유사도 기반 검색.
- **키워드 검색(BM25)**: 정확한 고유명사·키워드 매칭에 강함.
- 두 결과를 결합한 뒤 **리랭커(Reranker)**(예: BGE-Reranker, Cohere Rerank)로 최적 순위 재정렬.
- 벡터 검색만으로는 놓치는 정확한 용어 매칭(예: 제품 코드, 법조문 번호)을 키워드 검색이 보완.

## 2. 에이전트 레이어 — Agentic 컨트롤 루프 (추론 및 제어)

에이전트가 스스로 검색 결과를 평가하고, 부족하면 재검색하는 '두뇌' 역할을 하는 요소들이다.

### 2.1 라우터 (Router)
- 사용자의 질문을 분석해 다음 중 어디로 접근할지 결정하는 관문:
  - 전체 요약층 (거시적 질문)
  - 특정 장/절 요약층 (중간 범위 질문)
  - 세부 데이터층 (미시적·구체적 질문)
  - 또는 외부 API 호출

### 2.2 자가 피드백 루프 (Self-Correction / Evaluation Loop)
- **Retrieval Evaluator (검색 평가기)**: 검색된 문서가 질문과 실제로 관련 있는지(Relevance) 평가.
  관련도가 낮으면 에이전트가 검색 쿼리를 스스로 수정(Query Rewriting)해 재검색.
- **Generation Evaluator (생성 평가기)**: LLM이 만든 답변이 검색된 문서에 근거하는지
  (할루시네이션 검증), 질문에 완전히 답했는지 평가.
- 이 이중 평가 루프가 표준 RAG와 Agentic RAG를 가르는 핵심 차이 — "검색 → 생성"에서 끝나지
  않고 "검색 → 평가 → (필요 시 재검색) → 생성 → 검증"까지 순환한다.

## 3. 오케스트레이션 및 도구(Tools) 프레임워크

하이브리드 에이전트 아키텍처를 유기적으로 연결하고 개발하기 위한 환경.

### 3.1 에이전트 프레임워크
- **LangGraph** 또는 **LlamaIndex (Workflows)**: Agentic RAG의 핵심인 '반복 루프(Loop)'와
  '조건부 분기(Conditional Branching)'를 상태(State) 중심으로 가장 안정적으로 구현할 수 있는 도구.
- 단순 체이닝 구조인 LangChain 기본형으로는 이런 반복·분기 제어를 구현하기 복잡함.

### 3.2 도구함 (Tool Definition)
- 에이전트가 사용할 수 있도록 검색 기능을 함수(Tool) 형태로 추상화.
- 예:
  - `search_executive_summary()` — 전체 요약 검색
  - `search_detailed_chapters()` — 세부 청크 검색
  - `query_rewrite_tool()` — 쿼리 재작성

## 4. 하이브리드 에이전트 작동 아키텍처

```
[사용자 질문]
       │
       ▼
 [에이전트 라우터] ─── (거시적 질문인 경우) ───► [상위 계층: 문서/장 요약 인덱스 검색] ──┐
       │                                                                            │
 (미시적 질문인 경우)                                                                  │
       │                                                                            │
       ▼                                                                            ▼
 [하위 계층: 세부 청크 벡터 검색] ──► [리랭커(Reranker)] ──► [검색 결과 평가 (Evaluator)] ──┤
                                                                │                   │
                                                      (정보가 부족하면 쿼리 수정 후 재검색)   │
                                                                │                   │
                                                                ▼                   ▼
                                                      [최종 답변 생성 및 검증 (LLM)]
```

## 5. 레이어별 핵심 요소 요약표

| 레이어 | 핵심 요소 | 역할 |
|---|---|---|
| 데이터 | 부모-자식 청크 | 정밀 검색 + 문맥 보존 동시 확보 |
| 데이터 | 요약 메타데이터 인덱싱 | 거시적 질문에 대한 빠른 진입점 제공 |
| 데이터 | 하이브리드 검색 + 리랭커 | 의미 검색과 키워드 검색의 약점 상호 보완 |
| 에이전트 | 라우터 | 질문 성격에 맞는 계층/도구로 분기 |
| 에이전트 | Retrieval Evaluator | 검색 관련성 검증 + 쿼리 재작성 트리거 |
| 에이전트 | Generation Evaluator | 답변의 근거 기반 여부(할루시네이션) 검증 |
| 오케스트레이션 | LangGraph / LlamaIndex Workflows | 루프·조건부 분기를 상태 기반으로 안정적 구현 |
| 오케스트레이션 | Tool Definition | 검색 기능을 에이전트가 호출 가능한 함수로 추상화 |

## 6. 구현 시 가장 먼저 마주할 관문

이 시스템에서 가장 비용이 많이 들고 무거운 작업은 **"방대한 문서를 어떻게 계층적
(Hierarchical) 구조로 깔끔하게 파싱하고 요약하여 DB에 넣어둘 것인가"** 이다.
이 데이터 가공(ETL) 파이프라인이 먼저 설계되어야 Agentic 루프가 제대로 작동한다.

- 순서상 우선순위: ① 문서 파싱·계층 분할 규칙 설계 → ② 각 레벨 요약 생성 파이프라인 →
  ③ 하이브리드 인덱스 구축 → ④ 라우터/평가기 로직 → ⑤ 오케스트레이션 연결.
- [메이커 에반 구성도_확장.md](메이커%20에반%20Maker%20Evan-구성도_확장.md)의 "수집(Ingest) 단계에서
  명시적 트리거만 위키에 반영" 원칙처럼, ETL 파이프라인 설계 단계에서 무엇을 자동으로
  인덱싱하고 무엇을 사람이 검토 후 반영할지 미리 정해두는 것이 노이즈 관리에 유리하다.

## 7. RAG 확장 계보 안에서의 위치

[RAG_개념_확장.md](RAG_개념_확장.md) §5의 비교표 기준으로 보면, 하이브리드 에이전트는
**Agentic RAG**(반복적·적응적 검색, 자가 평가)와 **Hierarchical RAG**(다단계 요약·계층 탐색)를
결합한 형태이며, 여기에 **하이브리드 검색+리랭커**라는 검색 정확도 보강 레이어를 추가로
얹은 구성으로 정리할 수 있다.
