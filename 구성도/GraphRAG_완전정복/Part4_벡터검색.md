# Part 4. 벡터 검색의 세계

> 원본: [neo4j] GraphRAG 완전 정복 - 초보자를 위한 지식 그래프 기반 RAG 시스템
> https://wikidocs.net/book/18976

## 4-1. 텍스트를 숫자로 - 임베딩
원본: https://wikidocs.net/319208

- 컴퓨터는 텍스트 자체를 이해하지 못하므로 숫자로 변환해야 한다. 과거 방식인 원-핫 인코딩(단어마다 한 자리만 1인 벡터)은 모든 단어 쌍의 거리가 동일해 의미적 유사성을 전혀 반영하지 못하는 근본적 한계가 있었다.
- **임베딩(Embedding)**은 텍스트의 의미를 고차원 벡터 좌표로 표현하는 기법으로, 핵심 원리는 "비슷한 의미 → 비슷한 벡터". OpenAI `text-embedding-3-small`은 1536차원, `text-embedding-3-large`는 3072차원 벡터를 생성한다.
- 실습 패턴: `OpenAIEmbeddings(model="text-embedding-3-small")`를 초기화한 뒤 `embed_query(단일 텍스트)` 또는 `embed_documents(텍스트 리스트)`로 벡터를 얻는다. 전자는 검색 질의용, 후자는 문서 저장용으로 구분해 사용하는 것이 관례.
- 임베딩의 세 가지 특성: (1) 의미적 유사성 보존(비슷한 문장은 벡터도 가까움), (2) 언어 간 의미 보존(다국어 문장이라도 뜻이 같으면 벡터가 근접), (3) 벡터 연산 가능(덧셈/뺄셈 등으로 유추 관계 표현 가능).
- 다음 절로 이어지는 문제의식: 임베딩만으로는 검색이 안 되고, 벡터 간 "유사도"를 계산하는 절차가 추가로 필요하다.

## 4-2. 유사도 검색 이해하기
원본: https://wikidocs.net/319209

- 벡터 간 유사도를 재는 대표 지표는 **코사인 유사도(Cosine Similarity)** — 두 벡터의 방향이 얼마나 비슷한지를 측정하며 값의 범위는 -1(반대 방향)~0(직각/무관)~1(완전 동일 방향).
- 코사인 유사도는 `dot(A,B) / (|A| * |B|)`로 직접 계산 가능하며, numpy로 몇 줄이면 구현된다.
- 실습에서 "오늘 날씨가 좋다"를 기준 문장으로 여러 문장과 비교하면, 의미가 가까운 문장일수록(예: "화창한 하늘") 유사도가 높고, 주제가 다른 문장(예: "파이썬 프로그래밍")은 유사도가 낮게 나오는 것을 직접 확인한다.
- **검색 함수 패턴**: 문서 집합을 미리 임베딩해 두고(`doc_vectors`), 질의가 들어오면 질의 벡터와 모든 문서 벡터의 코사인 유사도를 계산 → 내림차순 정렬 → 상위 k개 반환. 이것이 벡터 검색(Vector Search)의 기본 알고리즘이다.
- 실무에서는 매번 직접 계산하지 않고 LangChain의 `InMemoryVectorStore` 같은 벡터 저장소를 사용해 임베딩 저장과 유사도 검색을 캡슐화한다.
- 벡터 검색의 장단점을 요약: 의미 기반 검색이 가능해 키워드 검색보다 유연하지만(장점), 여전히 "점 대 점" 비교이므로 여러 문서에 흩어진 사실을 연결하는 관계형 질의나 다중 홉 추론에는 약하다(단점) — 이는 Part1-3에서 언급한 GraphRAG 필요성으로 다시 연결된다.

## 4-3. 첫 번째 RAG 파이프라인
원본: https://wikidocs.net/319211

- RAG 파이프라인의 4단계: 질문 임베딩 → 벡터 저장소에서 유사 문서 검색 → 검색 결과를 컨텍스트로 프롬프트에 결합(Augmentation) → LLM이 컨텍스트 기반 답변 생성.
- 실습은 조선시대 왕(세종대왕/정조)과 이순신에 관한 짧은 문서 여러 개를 준비하는 것으로 시작한다.
- **청킹(Chunking)**: `RecursiveCharacterTextSplitter`로 긴 문서를 `chunk_size`/`chunk_overlap` 파라미터에 따라 작은 조각으로 분할. 필요성으로 LLM 컨텍스트 윈도우 제한, 긴 문서일수록 임베딩 품질 저하, 작은 청크가 더 정밀한 검색 결과를 준다는 점을 든다.
- 벡터 저장소 구축 패턴:
```python
vector_store = InMemoryVectorStore(embeddings)
vector_store.add_texts(chunks)
results = vector_store.similarity_search(query, k=3)
```
- 완전한 RAG 체인은 LangChain의 LCEL 스타일(`ChatPromptTemplate` + `RunnablePassthrough` + `StrOutputParser`)로 검색기(retriever)와 LLM을 파이프처럼 연결해 "검색 → 프롬프트 조립 → 생성"을 하나의 실행 가능한 체인으로 구성한다.
- 이 절 후반에서는 지금까지 만든 전통 RAG의 한계를 직접 체험시키는 것이 목적이다. 여러 문서(세종대왕-집현전-한글, 세종대왕-과학기구)에 사실이 나뉘어 있을 때, 청크 단위 유사도 검색만으로는 "집현전에서 이루어진 것 중 세종대왕의 과학적 업적과 관련된 것은?"처럼 정보를 연결해야 하는 질문에 취약함을 보여주며, 이것이 Part5부터 시작되는 Neo4j/Cypher 기반 그래프 구현으로 이어지는 동기가 된다.
