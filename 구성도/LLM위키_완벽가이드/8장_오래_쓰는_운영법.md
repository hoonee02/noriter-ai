# 8장. 오래 믿고 쓰는 LLM위키 운영법

> 원본: https://wikidocs.net/book/19830 (박승규, 「LLM위키 완벽 가이드」)

## 8.1 위키에도 점검이 필요한 이유
원본: https://wikidocs.net/353406

- 위키는 한 번 만들고 끝나는 문서함이 아니다. 시간이 지나면 낡은 내용, 출처 없는 주장, 서로 안 맞는 설명이 자연스럽게 생긴다. 문제는 LLM이 만든 요약이 문장은 매끄러워서 내용도 맞아 보인다는 점 — "위키에 적혀 있다"가 아니라 "어떤 원천 자료와 확인 절차로 뒷받침되는가"를 믿어야 한다.
- **요약이 왜곡되는 지점**: 원천 자료 → LLM 정리(조건 누락 위험) → 위키 문서(추정의 단정화, 출처 링크 누락 위험) → 업무 산출물(오래된 주장 재사용 위험). 예를 들어 원문 "이번 분기에는 임시로 적용한다"가 위키에서 "이 방식으로 적용한다"로, "A안과 B안 중 미결정"이 "A안을 추진한다"로 슬쩍 바뀔 수 있다.
- **점검 질문 4가지**(재구성):

| 점검 질문 | 확인할 것 | 위험한 상태 |
|---|---|---|
| 이 문장은 어디서 왔는가 | 원천 자료 파일명·URL·확인일 | 출처 없이 자연스러운 설명만 있음 |
| 조건이 빠지지 않았는가 | 기간·대상·예외·전제 | 임시 결정을 일반 원칙처럼 씀 |
| 추정이 단정으로 바뀌지 않았는가 | "가능성/검토중/확인필요" 표현 | 모르는 내용을 확정처럼 씀 |
| 최신성이 필요한가 | 버전·정책일·가격·일정 | 오래된 정보를 현재 기준처럼 씀 |
- 실습 예시: 원천 메모("반복 문의 중 배송 상태 확인이 많다고 말했다", "정확한 비율은 아직 집계하지 않았다")를 근거로 위키 요약("반복 문의 대부분은 배송 상태 확인이다")을 점검하면, 비율 미집계 사실이 빠져있어 "확인 필요"로 판정되고 "많이 언급되었으나 정확한 비율은 확인 필요"로 고쳐야 한다. 목적은 "틀린 문장 색출"이 아니라 "더 정확한 문장으로 교정"하는 것이며, 점검은 비난이 아니라 루틴이다.

## 8.2 정리와 감사 흐름 만들기
원본: https://wikidocs.net/353407

- LLM위키의 기본 흐름을 ingest(수집) → query(질문) → lint(점검)로 요약할 수 있다. 이 절은 그중 lint에 해당하는 운영 습관을 다룬다. 여기서 "감사(audit)"는 거창한 보안 감사가 아니라, 문서 형식 일관성·근거 유무·중복 여부를 주기적으로 확인하는 가벼운 습관이다.
- 순환 구조(재구성): 원천 자료 추가 → 위키 문서 정리 → 업무 질문에 활용 → **정리와 감사**(형식/근거/구조 문제 점검) → 문제 발견 시 문서 템플릿 보정·출처 보강 또는 확인 필요 표시·중복 병합/링크 정리 → 다음 자료 수집으로 순환. 위키는 "작성한 문서"가 아니라 "계속 정리되는 업무 지식"이라는 관점이 핵심.
- **위키 문서 최소 형식 5요소**(모든 문서가 답해야 할 질문): 이 문서가 무엇을 설명하는가 / 어떤 원천 자료를 근거로 삼았는가 / 언제 확인했는가 / 아직 확인 못한 내용은 무엇인가 / 다음에 어떻게 다시 쓸 수 있는가. 각 항목이 없을 때 생기는 문제(재구성):

| 항목 | 역할 | 없을 때 문제 |
|---|---|---|
| 한 문장 요약 | 핵심을 빠르게 확인 | 문서 쓸모를 바로 알기 어려움 |
| 근거 | 원천자료·확인일 명시 | 위키 문장을 원본처럼 믿게 됨 |
| 확인된 내용 | 근거 있는 사실 정리 | 추정과 사실이 섞임 |
| 확인 필요 | 단정 불가 내용 분리 | 불확실한 주장이 보고서로 유입 |
| 다시 물어볼 질문 | 다음 활용 방향 제시 | 문서가 읽고 끝나는 메모로 전락 |
- 이 형식은 "모든 문서를 길게 쓰라"가 아니라 "짧아도 다섯 항목만 있으면 LLM에게 다시 맡기기 쉽다"는 취지다.
- 실습은 Python 스크립트로 wiki/ 폴더의 각 Markdown 문서에 "## 한 문장 요약", "## 근거" 등 필수 섹션이 있는지 자동 점검하는 간단한 형식 검사기를 만들어보는 것으로, 형식을 잘 지킨 문서(good-note.md)와 부실한 문서(weak-note.md)를 비교해 부족한 항목을 찾아낸다.

## 8.3 주제가 늘어날 때 관리하기
원본: https://wikidocs.net/353408

- 처음엔 작게 시작해야 하지만, 잘 쓰다 보면 주제가 늘어나면서 "어디에 넣지?", "이 위키 아직 쓰나?", "비슷한 위키가 두 개 아닌가?" 하는 문제가 생긴다.
- 관리 방식 3가지 비교(재구성):

| 방식 | 적합한 상황 | 장점 | 위험 |
|---|---|---|---|
| 하나의 큰 위키 | 주제가 작고 서로 강하게 연결됨 | 찾을 곳이 하나라 단순 | 주제가 늘면 답변 맥락이 흐려짐 |
| 여러 주제 위키 | 업무흐름·독자·자료출처가 다름 | 질문 범위를 좁히기 쉬움 | 중복 문서·관리 누락 위험 |
| 큰 위키 + 주제 폴더 | 공통 규칙은 같고 세부 주제만 다름 | 공통기준+주제별 맥락 유지 | 폴더 규칙 없으면 다시 뒤섞임 |
- 새 자료가 생겼을 때 판단 흐름(재구성): "기존 위키의 핵심 질문과 같은가?" → 같으면 기존 주제 위키에 추가 / 다르면 "같은 독자·같은 업무 흐름인가?" → 그렇다면 기존 위키 안에 주제 폴더 추가 / 아니면 새 주제 위키 생성 → 마지막에 인벤토리(전체 위키 현황 목록)에 상태 기록.
- **주제를 나누는 기준은 폴더 이름이 아니라 "실제 질문"**이다. 예: 같은 "meeting-notes"라는 이름이라도 주간 회의록(→ 팀 운영 위키, 질문: 이번 주 실행 항목은?), 고객 인터뷰 회의록(→ 고객 리서치 위키, 질문: 고객이 반복 겪는 문제는?), 자동화 검토 회의록(→ 업무 자동화 위키, 질문: 자동화 후보는?)처럼 실제 질문에 따라 서로 다른 위키로 분리하는 것이 좋다.
- 오래된 주제는 삭제하지 않고 **아카이브**한다는 원칙도 제시된다(더 이상 안 쓰는 위키를 없애기보다 보관 상태로 표시해 필요시 다시 찾을 수 있게 함). 도구 명령 예시(nvk/llm-wiki 등)는 특정 버전 기준이므로 실제 사용 시 설치된 도구 문서를 재확인해야 한다.

## 8.4 내 업무 루틴에 붙이기
원본: https://wikidocs.net/353409

- LLM위키는 만들어두면 끝나는 문서함이 아니다. 업무가 바뀌면 자료도 바뀌고 예전 판단 기준도 낡으므로, "언제 무엇을 넣고 언제 무엇을 점검할지"를 업무 루틴에 실제로 붙여야 한다. 목표는 거창한 자동화가 아니라 "다음 주의 나 자신이 같은 설명을 반복하지 않는 것"이다.
- **매일 넣을 자료를 고르는 3가지 질문**: ① 다음에도 LLM에게 설명할 가능성이 있는가? ② 원천 자료를 남길 수 있는가? ③ 업무 판단이나 산출물에 다시 쓰일 가능성이 있는가? 세 질문에 모두 "예"면 raw/에 원본 보관 후 필요할 때만 wiki/에 정리 문서를 만든다.
- 자료 유형별 처리 기준표(재구성):

| 자료 후보 | 넣는 조건 | 먼저 둘 위치 | 바로 넣지 않는 경우 |
|---|---|---|---|
| 회의록 | 결정사항·담당자·기한이 있음 | raw/meetings/ | 참석자 동의·공유범위 불분명 |
| 반복 설명한 업무규칙 | 다음 요청에도 재사용될 것 | wiki/rules 또는 wiki/concepts | 개인 취향에 가까워 재사용성 낮음 |
| 공식/제품 문서 | 업무판단 근거로 쓰임 | raw/references/ | 확인 날짜 없이 최신성 불명확 |
| 고객 피드백 | 반복패턴·우선순위 판단에 쓰임 | raw/feedback/ | 개인정보·계약정보가 그대로 있음 |
| 보고서 초안 | 다음 보고서 형식 기준이 됨 | output/ | 근거 미연결 일회성 문장 |
| 할 일 목록 | 실행기준·의사결정 이력 있음 | raw/tasks 또는 log.md | 단순 개인일정이라 지식화 불필요 |
- 자료 유입 판단 흐름(재구성): 오늘 생긴 업무 자료 → "다음에도 쓸 가능성?"(아니면 넣지 않음) → "원천 자료를 남길 수 있는가?"(아니면 확인 필요 메모만) → "민감정보·권한 문제 있는가?"(있으면 마스킹/보류) → raw에 원본 저장 → "정리할 가치가 있는가?"(아니면 log에 수집기록만) → wiki 문서로 정리 → index·관련문서에 연결.
- **가장 중요한 지점은 raw에 넣기 전 권한 확인**이다. 로컬 Markdown이라도 LLM 도구·플러그인이 처리하는 순간 외부 모델 호출이나 웹 수집 정책이 개입할 수 있으므로, 고객정보·개인정보·계약정보·비공개 코드는 반드시 조직 기준을 먼저 확인해야 한다.
- 이 절(그리고 책 전체)의 결론은, LLM위키가 "한 번의 정리"가 아니라 "매일·매주 반복되는 작은 습관"으로 정착될 때 비로소 오래 믿고 쓸 수 있는 업무 지식 시스템이 된다는 것이다.
