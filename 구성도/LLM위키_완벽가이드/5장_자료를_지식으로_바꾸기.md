# 5장. 자료를 넣고 다시 쓰기 좋은 지식으로 바꾸기

> 원본: https://wikidocs.net/book/19830 (박승규, 「LLM위키 완벽 가이드」)

## 5.1 자료를 넣기 전에 정할 기준
원본: https://wikidocs.net/353394

- 자료는 많이 넣는다고 좋아지지 않는다. 원본·요약·추측·오래된 정보가 한곳에 섞이면 나중에 검증이 불가능해진다. 이 절의 핵심 원칙은 **원천 자료와 요약문을 절대 섞지 않는 것**이다.
- 원천 자료(회의록 원문, 웹 문서 캡처, PDF 추출 텍스트, 인터뷰 메모)와 요약문("이번 회의 결정 사항" 같은 파생 문서)을 같은 파일에 섞으면 생기는 문제 4가지: 원문 발언과 LLM 정리를 구분 불가, 요약 오류 검증 기준 소실, 오래된 요약이 최신 원문처럼 오인될 위험, 다른 사람이 무엇을 믿어야 할지 판단 곤란.
- Karpathy의 LLM Wiki 아이디어 문서가 제시한 원천자료/위키/스키마 3층 분리를 이 책은 raw/, wiki/, 규칙(지침) 파일로 실무화한다. 흐름: 원천 자료(회의록·웹문서·PDF·메모) → raw/ 원본 보관 → (LLM 또는 사람이 읽고 정리) → wiki/(요약·개념·결정사항) → 질문과 산출물(보고서·실행계획·체크리스트), 각 단계에 검증 기준이 따라붙는다.
- raw/ 원칙: 원문을 그대로 두고, 오탈자·표현이 마음에 안 들어도 원본 파일을 직접 고치지 않는다. 수정이 필요하면 별도 메모를 남긴다.
- wiki/ 원칙: 원문 복사가 아니라 핵심 개념·결정사항·반복 질문에 대한 답·업무 규칙·확인 필요 항목을 정리하는 지식층. wiki 문서는 항상 "근거: raw/파일경로" 형태로 원천 자료를 명시해 언제든 raw로 돌아가 검증할 수 있어야 한다.
- 실습은 회의록 원문을 `raw/meetings/`에, 그 근거를 명시한 요약 문서를 `wiki/decisions/`에 따로 저장하는 최소 예제(고객 문의 자동화 기준: 반복 문의는 자동응답 후보, 환불·개인정보 요청은 제외)로 원본-요약 분리를 체득시킨다.

## 5.2 자료 수집하기
원본: https://wikidocs.net/353395

- 자료 수집은 위키의 첫 단추다. 아무렇게나 넣으면 위키 문서도 아무렇게나 만들어지고, 반대로 원천 자료·확인 날짜·처리 이력을 남기면 나중에 LLM 요약을 검증할 수 있다. 이 절의 예제는 특정 도구의 필수 명령이 아니라 수동 Markdown으로 익히는 "패턴"이다.
- **웹 문서 수집 시 최소 4항목**을 반드시 남긴다: 제목(재검색용), URL(원문 복귀용), 확인 날짜(최신성 판단용), 수집 이유(위키에 넣을 가치 판단용). 웹 문서는 답변 재료이면서 동시에 "감사 대상"이라는 인식이 중요하다.
- 웹 문서 수집 흐름(재구성): 웹 문서 발견 → "위키에 넣을 가치가 있는가"(아니면 후보 제외) → `raw/web`에 원천 카드 저장 → `wiki/sources`에 정리 문서 작성 → `index.md`에 링크 추가 → `log.md`에 처리 이력 기록 → 이후 질문·산출물에 재사용. raw/web(원문 추적용)과 wiki/sources(재질문용 정리)를 분리하는 것이 핵심.
- 웹 문서 저장 범위에 대한 주의: Obsidian Web Clipper 같은 도구로 전체 페이지를 저장할 수도 있지만, 공개 문서·사내 문서·유료 문서·고객 자료는 권한·보안 기준이 다르므로 저장 가능 범위가 불확실하면 제목·URL·확인일·짧은 메모만 남기고 원문 전체 저장은 보류한다.
- 실습은 `raw/web`, `raw/meetings`, `wiki/sources`, `wiki/meetings`, `output` 폴더를 만들고, "Codex AGENTS.md 공식 문서"를 예시로 한 웹 원천 자료 카드(raw/web)를 작성하는 Bash 스크립트로 구성된다.

## 5.3 위키 문서로 정리하기
원본: https://wikidocs.net/353396

- 자료를 raw/에 모으는 것만으로는 부족하다. 주제별 문서로 정리하지 않으면 다음 질문에 다시 쓰기 어렵다. 목표는 "읽기 좋은 요약"이 아니라 "근거를 찾을 수 있고 빠르게 판단할 수 있는 지식 문서"다.
- **흩어진 자료를 주제별로 묶는 기준은 "다시 어떤 질문에 쓰일 것인가"**다. 하나의 회의록 안에도 결정 사항·이슈·고객 요청·일정 변경이 섞여 있으므로, 자료 종류가 아니라 재질문 기준으로 여러 위키 문서로 쪼갠다. 예(재구성):

| 원천 자료 조각 | 묶을 위키 문서 | 다시 쓸 질문 |
|---|---|---|
| 회의록의 반복 문의 목록 | wiki/customer-inquiry-types.md | 어떤 문의부터 자동화해야 하는가 |
| 상담팀 메모의 예외 처리 | wiki/escalation-rules.md | 자동응답에서 상담사로 넘길 조건은? |
| 제품 문서의 환불 정책 | wiki/refund-policy-summary.md | 환불 답변 시 지켜야 할 기준은? |
| 개인 메모의 실험 아이디어 | wiki/automation-experiment-ideas.md | 이번 주 작게 검증할 실험은? |
- 같은 회의록에서 나온 내용이라도(예: "문의 유형"과 "예외 처리 기준") 서로 다른 문서로 나누면, 나중에 필요한 문서만 골라 불러와 답변을 구성할 수 있다는 것이 이 절의 핵심 이점이다.
- 실습 예시: 고객지원 자동화 회의록(raw) 하나를 두고, "배송 상태 문의가 최다·환불 문의는 예외가 많아 자동화 어려움·비밀번호 재설정은 기존 도움말로 해결 가능"이라는 내용을 `wiki/inquiry-types.md`로 정리하며 근거(원천 자료 경로·확인일·자료성격)와 "확인된 내용/확인 필요"를 구분해 기록한다. 이런 방식으로 하나의 회의록에서 문의 유형, 예외 처리 규칙, 자동화 실험 계획 등 여러 개의 독립된 위키 문서를 파생시킨다.
