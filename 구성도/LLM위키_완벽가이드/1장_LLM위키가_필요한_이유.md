# 1장. LLM위키가 필요한 이유

> 원본: https://wikidocs.net/book/19830 (박승규, 「LLM위키 완벽 가이드」)

## 1.1 LLM을 써도 지식이 남지 않는 이유
원본: https://wikidocs.net/353378

- LLM 대화는 매번 "일회성"으로 끝난다. 어제 길게 설명한 업무 배경(용어, 톤, 제외 정보, 판단 기준)이 오늘 대화창에는 남아 있지 않아 똑같은 설명을 반복하게 된다.
- 문제의 핵심은 "반복 설명이 필요한 업무 기준"이 프롬프트 안에서만 쓰이고 대화 밖으로 나오지 못한다는 점이다. 기준이 문서로 분리되면 다음 요청은 "지난번처럼 해줘"가 아니라 "이 기준 문서를 참고해줘"로 짧아진다.
- 반복 설명 후보를 찾는 기준표(재구성):

| 반복되는 항목 | 예시 | 위키로 남겼을 때 효과 |
|---|---|---|
| 출력 형식 | 회의록을 결정사항/실행항목/확인질문으로 나눔 | 매번 같은 형식으로 정리 가능 |
| 판단 기준 | 결제 오류·장애 신고를 우선 처리 | 분류 결과의 일관성 확보 |
| 금지 사항 | 고객명·계약 금액 요약 제외 | 민감정보 노출 위험 감소 |
| 문체 기준 | 임원 보고서는 결론 우선 | 초안 톤을 맞추기 쉬움 |
| 참고 자료 | 최근 3개월 문의 유형 보고서 기준 | 답변 근거 재확인 가능 |

- **대화 기록 ≠ 업무 지식.** 대화 기록은 질문·중간답변·시행착오가 시간순으로 섞여 있어 나중에 어떤 결론이 최종인지 알기 어렵다. 업무 지식은 확인한 사실·결정한 기준·남은 의문·출처를 분리해 주제별로 정리한 것이다.
- 대화를 업무 지식으로 바꾸는 방법: 확인일·상태를 표시하고, 기본 분류/예외 규칙/제외 정보/출력 형식/남은 확인 필요 항목을 섹션으로 나눠 Markdown 문서화한다. 이렇게 만든 문서를 참고시키면 다음 요청이 짧고 안정적으로 바뀐다.
- 반복 질문은 보통 세 지점에서 발생한다: ① 같은 업무를 반복할 때(회의록, 주간보고, 문의분류), ② 같은 기준을 여러 문서에 적용할 때(보안, 문체, 용어 기준), ③ 여러 사람이 같은 배경을 공유해야 할 때(결정 이력, 프로젝트 범위).
- 위키 후보 판별 흐름: "자주 묻는 업무가 있다 → 배경 설명이 반복되는가 → 판단기준/출력형식이 있는가 → 출처·확인일이 중요한가" 순으로 예/아니오를 따라가면, 마지막까지 "예"가 이어지는 업무일수록 LLM위키 문서로 만들 가치가 크다. 단순 문체 교정처럼 가벼운 반복은 프롬프트 템플릿만으로 충분한 경우도 많다.
- 실습 취지: 최근 1주일간 LLM에 반복 설명한 업무 규칙 3개를 찾아 "다시 설명한 맥락 / 왜 반복했나 / 다음에도 필요한가"로 표를 채워보는 것이 첫 위키 후보를 고르는 출발점이다.

## 1.2 LLM위키는 무엇인가
원본: https://wikidocs.net/353379

- LLM위키는 특정 제품명이 아니라 **지식 관리 패턴**이다. Andrej Karpathy가 2026년 4월 공개한 아이디어 문서에서 제시된 개념으로, 원천 자료를 보존하고 LLM이 이를 구조화된 Markdown 위키로 정리하며, 이후 질문·갱신·검증을 그 위키에 누적하는 방식을 말한다.
- 책의 정의: "LLM위키는 원천 자료를 보존하고, LLM이 이를 다시 쓰기 좋은 위키 문서로 정리하며, 질문·갱신·검증 결과를 계속 누적하는 지식 관리 패턴"이다. Markdown 파일만으로 작게 시작할 수도 있고, Claude Code·Codex 같은 에이전트 도구, nvk/llm-wiki 같은 구현체와 결합할 수도 있다 — 도구는 달라도 구조는 유지된다.
- **세 개 층 구조**(이 책의 핵심 골격, 2장에서 더 깊이 다룸):
  - raw (원천 자료): 회의록, 웹 문서, 메모, 파일 — 원본 그대로 보존
  - wiki (위키): 개념·결정·절차·질문이 분리·연결된 정리 문서
  - schema (작업 규칙): AGENTS.md/CLAUDE.md 등 "원천 자료를 덮어쓰지 않는다", "확인 안 된 주장은 확인 필요로 표시" 같은 규칙
  - 이 구조 위에서 사용자가 질문하면 위키를 근거로 보고서·실행계획 같은 output이 나온다.
- 일반 대화형 사용과의 차이 (재구성 비교표):

| 구분 | 일반 대화형 사용 | LLM위키 사용 |
|---|---|---|
| 업무 맥락 | 매번 프롬프트에 재입력 | 위키·작업규칙에 보존 |
| 자료 | 대화창에 붙여넣고 소비 | 원천 자료로 별도 보존 |
| 답변 | 그 순간의 결과물 | 다음 작업의 재료 |
| 검증 | 대화 기록을 다시 뒤져야 함 | 원천 자료·위키 문서로 추적 |
| 위험 | 좋은 답이 일회성으로 끝남 | 잘못된 정리가 누적될 수 있음(관리 필요) |

- **"컴파일"이라는 비유**: 원천 자료를 위키로 바꾸는 과정을 소스코드→실행형태 비유로 설명한다. 단순 요약이 아니라 여러 자료의 중복 제거, 관련 문서 연결, 출처·갱신일 기록, 확인 안 된 내용은 "확인 필요"로 표기하는 작업까지 포함한다.
- 원천 자료와 위키 문서는 절대 섞지 않는다는 것이 핵심 원칙이다. raw는 근거, wiki는 해석·정리이므로 섞이면 나중에 원문과 LLM 재구성을 구분할 수 없다.
- 좋은 컴파일 결과를 점검하는 네 가지 기준(재구성): 출처(이 문장이 어느 자료에서 왔는가), 구조(요약/근거/확인필요가 구분되는가), 연결(관련 문서·다음 질문이 남아있는가), 갱신기준(언제 다시 확인해야 하는가). 네 가지가 없으면 각각 근거 없는 단정, 판단 곤란, 지식 고립, 정보 노후화 문제가 생긴다.

## 1.3 이 책에서 만들 결과물
원본: https://wikidocs.net/353380

- 이 책은 설치법 암기가 아니라 "내 업무에 붙이면 어떤 결과물이 나오는가"를 먼저 보여주는 데 목적이 있다. 예제 주제로 **work-automation**(반복 업무 자동화: 회의록 정리, 문의 분류, 주간보고 초안)을 시종일관 사용한다.
- **최소 LLM위키 폴더 구조**(예시 재구성):
  - `raw/` — 원천 자료 보관
  - `wiki/` — 정리된 위키 문서 (하위에 `concepts/` 등)
  - `output/` — 보고서·요약문·실행계획
  - `inbox/` — 아직 정리 전인 임시 메모
  - `index.md` — 위키 전체 입구
  - `log.md` — 자료 추가/수정 이력
  - `AGENTS.md` 또는 `CLAUDE.md` — LLM 도구가 따라야 할 작업 규칙(Codex는 AGENTS.md, Claude Code는 CLAUDE.md를 기준으로 삼는 경우가 많음)
- 구성요소별 점검 기준표:

| 구성요소 | 역할 | 확인할 것 |
|---|---|---|
| raw/ | 원천 자료 보관 | 원본이 임의로 바뀌지 않았는가 |
| wiki/ | 재사용 가능한 정리 문서 | 출처·핵심 개념이 남아있는가 |
| output/ | 업무 산출물 | 보고서/실행계획으로 쓸 수 있는가 |
| inbox/ | 임시 입력 공간 | 정리 전 자료가 구분되는가 |
| index.md | 위키 입구 | 전체 문서 위치를 찾을 수 있는가 |
| log.md | 처리 기록 | 언제 무엇을 넣고 고쳤는지 남았는가 |
| 작업 규칙 문서 | LLM의 작업 기준 | 출처·최신성·확인필요 규칙이 있는가 |

- 폴더 이름 자체보다 "원천 자료 / 정리된 위키 / 업무 산출물 / 작업 규칙"을 구분하는 원칙이 더 중요하며, 실제 도구에 따라 저장 위치는 달라질 수 있다.
- 이 책이 제시하는 전체 워크플로: **수집 → 보관 → 정리 → 질문 → 산출 → 검증 → 갱신**의 순환 구조. 일부 구현체는 이를 `ingest`, `compile`, `query`, `lint`, `audit` 같은 명령으로 나누지만, 이 책은 명령어보다 각 단계의 "역할"을 먼저 이해시키는 데 집중한다.
- 실습 미리보기는 Bash 계열 셸에서 `mkdir -p`와 `printf`로 `raw/ wiki/ output/ inbox/ index.md log.md AGENTS.md`의 빈 뼈대만 만들어보는 수준이며, 아직 실제 자료를 넣는 단계는 아니다.
