# 3장. 내게 맞는 LLM위키 방식 고르기

> 원본: https://wikidocs.net/book/19830 (박승규, 「LLM위키 완벽 가이드」)

## 3.1 시작 방식 비교하기
원본: https://wikidocs.net/353386

- 시작할 때 중요한 것은 "기능이 가장 많은 도구"가 아니라 "이번 주 안에 자료 하나를 넣고 정리 문서를 만들어 질문까지 해볼 수 있는가"이다. 첫 선택은 되돌릴 수 있다 — 수동 Markdown으로 시작한 위키를 나중에 Claude Code/Codex로 옮기거나, CLI로 만든 파일을 Obsidian 같은 데스크톱 앱에서 열 수도 있다.
- 네 가지 시작 방식 비교(재구성):

| 방식 | 잘 맞는 상황 | 장점 | 부담 |
|---|---|---|---|
| 수동 Markdown | 자료가 적고 원리를 먼저 배우고 싶을 때 | 설치 거의 없음, 구조가 눈에 보임 | 색인·로그·출처를 직접 챙겨야 함 |
| Claude Code/Codex 기반 | 이미 에이전트형 도구를 쓸 때 | 대화 흐름 안에서 수집~질문을 이어감 | 플러그인 설치·권한·버전 확인 필요 |
| CLI 방식 | 같은 작업을 반복/자동화하고 싶을 때 | 명령 기록·재현이 쉬움 | Node.js/Python, API 키 관리 필요 |
| 데스크톱 도구 | 화면에서 문서·그래프를 보고 싶을 때 | 파일·연결 상태를 눈으로 확인 | 앱 설치, 모델 설정, 저장 위치 확인 필요 |
- 선택 흐름(재구성): "자료가 적고 구조부터 배우고 싶다 → 수동 Markdown" / "이미 Claude Code·Codex를 쓴다 → 에이전트 기반 방식" / "명령줄·API 키가 익숙하다 → CLI" / "화면에서 보고 싶다 → 데스크톱 도구". 저자는 처음엔 수동 Markdown이 가장 안전하다고 권한다 — 구조가 눈에 보이고 실패 원인을 찾기 쉽기 때문.
- **수동 Markdown 최소 구조**: `AGENTS.md`, `raw/meeting-note.md`, `wiki/index.md`, `wiki/concepts/`, `output/`. 원칙은 여전히 원본(raw)과 정리본(wiki)을 섞지 않는 것. 실습에서는 회의 메모 하나를 raw에 넣고, 그 근거를 명시한 wiki 문서와 index.md를 만들어보는 셸 스크립트 예제를 제시한다.
- 책 전반의 도구 설명은 2026-05-16 KST 기준 조사 내용이며, LLM위키 구현체는 빠르게 바뀌므로 실행 전 README/Release Notes를 재확인하라고 당부한다.

## 3.2 도구를 고를 때 확인할 것
원본: https://wikidocs.net/353387

- 도구 선택 기준은 "무엇을 많이 할 수 있는가"가 아니라 "내가 계속 관리할 수 있는가"이다. LLM위키는 단일 표준 제품이 아니라 패턴이므로 구현체마다 설치·저장위치·지원형식·명령이 다르다.
- 방식별 부담 비교(재구성):

| 방식 | 시작 부담 | 유지보수 부담 | 먼저 확인할 것 |
|---|---|---|---|
| 수동 Markdown | 낮음 | 낮음 | 원본/위키 문서 분리가 가능한가 |
| Claude Code/Codex | 중간 | 중간 | 지침 파일, 플러그인 권한, 저장 위치 |
| CLI 도구 | 중간~높음 | 중간~높음 | 런타임 버전, API 키, 릴리스 노트 |
| 데스크톱 앱 | 낮음~중간 | 낮음~중간 | 내보내기, 백업, 원본 보존 여부 |
| 연구·실험 구현체 | 높음 | 높음 | 문서 최신성, 한계, 변경 이력 |
- **첫 도구가 갖춰야 할 최소 3조건**: ① 원천 자료와 정리된 위키 문서를 구분 저장할 수 있다, ② 생성된 위키 문서를 사람이 직접 열어 고칠 수 있다, ③ 공식 문서와 변경 이력을 확인할 수 있다. 이 중 하나라도 약하면 근거 상실, 오류 수정 불가, 구식 명령 답습 같은 문제가 생긴다.
- **도구 선택 체크리스트**(예/아니오로 점검): 30분 안에 샘플 자료를 넣어볼 수 있는가 / 원본 자료가 따로 남는가 / 위키 문서가 Markdown처럼 읽기 쉬운가 / 저장 위치를 확인할 수 있는가 / 공식 README가 있는가 / Releases·Changelog가 있는가 / 권한과 네트워크 호출 범위를 설명할 수 있는가. "예"가 5개 미만이면 그 도구를 바로 도입하지 말고 수동 Markdown으로 먼저 핵심 흐름(원본 보존→지식 갱신→근거 확인)을 익히라고 권한다.
- 실습은 raw/wiki/concepts/output 구조를 만들고 회의록 샘플과 그를 근거로 삼은 위키 문서를 셸 스크립트로 생성해보는 30분짜리 검증 절차다.

## 3.3 이 책의 실습 환경 정하기
원본: https://wikidocs.net/353388

- 완벽한 도구를 처음부터 찾으려 하면 시작이 늦어진다. 이 책은 특정 제품에 묶이지 않는 흐름(원본 보존 → 위키 문서가 원본을 가리킴 → 작업 이력 기록)을 먼저 익히고, 이후 Codex·Claude Code·CLI 같은 도구를 필요에 따라 얹는 순서를 권한다.
- 책의 **기본 실습 환경**(재구성):

| 항목 | 기본 선택 | 이유 |
|---|---|---|
| 저장 형식 | Markdown 파일 | 대부분의 LLM 도구·편집기에서 호환 |
| 기본 구조 | raw/, wiki/, output/, index.md, log.md | 원본·정리지식·산출물 분리 |
| 작업 규칙 | AGENTS.md (+선택적 CLAUDE.md) | Codex와 Claude Code 모두 대응 |
| 첫 자료 | 가상의 짧은 회의록 | 개인정보·기밀 노출 회피 |
| 첫 검증 | 파일 구조·출처·확인필요 항목 점검 | 도구보다 흐름이 잡혔는지가 우선 |
- 실습 초반에는 큰 자료 묶음이 아니라 회의록 하나, 메모 하나 정도의 "작은 예제"로 검증한다. 자료를 많이 넣으면 문제가 도구 탓인지 자료 탓인지 질문 탓인지 구분하기 어렵기 때문이다.
- 10분짜리 미니 위키 실습: `raw/meeting-notes/`, `wiki/concepts/`, `output/`을 만들고 `AGENTS.md`(원본 임의수정 금지, 근거 표시, 확인필요 표시, log.md 기록 규칙)와 `CLAUDE.md`(AGENTS.md를 `@AGENTS.md`로 불러와 Claude Code 전용 규칙을 덧붙임)를 함께 둔다. 이후 실제 회의 메모(raw)와 그 근거를 명시한 위키 문서(wiki/concepts)를 만들어 흐름을 확인한다.
- 이 절부터 책은 본격적으로 "work-automation" 예제 위키를 4장 이후 실습에서 계속 확장해 나가는 구조로 이어진다.
