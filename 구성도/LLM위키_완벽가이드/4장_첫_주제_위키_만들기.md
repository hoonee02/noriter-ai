# 4장. 첫 번째 주제 위키 만들기

> 원본: https://wikidocs.net/book/19830 (박승규, 「LLM위키 완벽 가이드」)

## 4.1 업무 주제 정하기
원본: https://wikidocs.net/353390

- 첫 위키를 "회사 업무 전체"처럼 크게 잡으면 자료 수집에 지치고 질문도 흐려진다. 첫 주제는 "많이 아는 주제"가 아니라 "작게 검증 가능한 주제"여야 한다.
- 큰 주제를 첫 위키용으로 줄이는 예(재구성):

| 큰 주제 | 줄인 주제 | 줄인 이유 |
|---|---|---|
| 업무 자동화 전체 | 반복 회의록에서 실행 항목 뽑기 | 자료가 회의록으로 좁혀짐 |
| 고객 지원 개선 | 최근 20건 문의 유형 분류 | 결과를 표로 검증 가능 |
| 마케팅 전략 정리 | 다음 뉴스레터 주제 후보 정리 | 산출물이 명확 |
| 개발 지식 관리 | 온보딩 자주 묻는 질문 정리 | 독자·사용 장면이 분명 |
- **주제를 줄이는 세 질문**: ① 다음 주 안에 실제로 쓸 업무인가? ② 원천 자료를 3~5개로 모을 수 있는가? ③ 결과가 나오면 잘됐는지 확인할 수 있는가? 세 질문을 모두 통과해야 첫 주제로 채택한다. (예: "AI로 업무 효율화" → "주간 회의록 실행 항목 정리 위키"로 축소)
- 첫 위키에 넣을 **자료 선정 기준**(재구성): 최근 회의록 3개·고객 문의 20건(개인정보 제거)·공식 문서 1~2개(URL·확인일 기록)는 적합도가 높다. 반면 6개월치 채팅 로그 전체나 기억에 의존한 요약 메모는 범위가 넓거나 원본 확인이 어려워 부적합하고, 비공개 계약서 원문 등은 보안 기준을 먼저 확인해야 한다. 핵심은 "양보다 성격" — 출처가 분명하고 다시 확인 가능한 자료를 우선한다.
- 첫 자료 묶음 문서에는 주제, 원천 자료 후보 표(번호/자료명/날짜/성격/사용이유/주의점), 그리고 그 자료로 던질 "첫 질문"을 함께 적어두는 방식을 권장한다.

## 4.2 위키 초기화하기
원본: https://wikidocs.net/353391

- Karpathy의 LLM Wiki 아이디어 문서가 제시한 "원천 자료 / 위키 / 스키마(작업규칙)" 3분할을 초보자용으로 단순화해 raw/, wiki/, output/, 규칙 파일 구조로 실습한다.
- 최소 구조 역할표(재구성):

| 위치 | 역할 | 처음 넣을 내용 |
|---|---|---|
| raw/ | 원본 자료 보관 | 회의록, 메모, 웹 문서 저장본 |
| wiki/ | LLM이 정리한 문서 | 개념 정리, 질문별 답변, 요약 |
| output/ | 업무 산출물 | 보고서, 실행계획, 공유용 초안 |
| index.md | 위키 안내판 | 문서 목록, 주요 질문 |
| log.md | 처리 이력 | 언제 무엇을 넣고 바꿨는지 |
| AGENTS.md | 작업 규칙 | LLM 도구가 참고할 규칙 |
- raw/는 "기준점"이라 임의로 고치면 안 되고, wiki/는 계속 다듬어도 되는 영역이라는 점이 다시 강조된다.
- 실습에서는 `work-automation-wiki/` 아래에 `raw/meeting-notes`, `wiki/concepts`, `output`을 만들고, index.md에 "이 위키의 질문"과 "문서 목록"을, log.md에 처리 이력 표를 채우는 Bash 스크립트를 제시한다. 이 단계에서는 아직 LLM을 사용하지 않고, 사람이 이해할 수 있는 뼈대만 만든다.
- **작업 규칙 파일**: 도구별로 이름이 다르다 — OpenAI Codex는 `AGENTS.md`를 프로젝트 지침 파일로 사용하고, Claude Code는 `CLAUDE.md`를 프로젝트 메모리 파일로 사용한다(필요하면 CLAUDE.md가 AGENTS.md 내용을 가져오는 방식 권장). 다만 이런 규칙 파일은 LLM 행동을 "강제"하지 않고 "유도"할 뿐이므로, 결과가 규칙대로 나왔는지는 반드시 사람이 확인해야 한다.

## 4.3 첫 질문으로 방향 잡기
원본: https://wikidocs.net/353392

- 막연한 업무 질문("반복 업무를 줄이려면?")은 LLM이 그럴듯한 일반론으로 답하기 쉽고 내 업무에 맞는지 검증하기 어렵다. **위키 질문**은 위키 안의 실제 자료를 기준으로 답하도록 범위를 좁힌 질문이다.
- 위키 질문을 만들 때 채워야 할 4요소(재구성):
  1. 자료 기준 — 어떤 raw/wiki 자료를 근거로 삼을지
  2. 결정 목적 — 이 답이 어떤 결정을 돕는지
  3. 답변 형식 — 표/목록 등 원하는 출력 구조
  4. 검증 요청 — 근거 없는 추정은 "확인 필요"로 표시하도록 명시
  - 예: "raw/meeting-notes와 wiki 문서 기준으로, 다음 주 자동화 후보 1개를 고르기 위해, 업무명·반복이유·기대효과·근거·확인필요를 표로 정리하고, 근거 부족한 내용은 확인 필요로 표시해달라"는 식의 질문으로 완성된다.
- **초기 답변은 세 구역으로 나눠 받는 것이 좋다**: ① 현재 자료로 확인된 내용(파일명·문서명·확인일이 함께 남아야 함), ② 제한된 근거로 추정한 내용("추정"/"가능성"/"확인 필요" 같은 표현으로 명시), ③ 답하기 위해 더 필요한 자료. 이렇게 나누면 답변을 무비판적으로 신뢰하지 않고, 위키가 이미 아는 것과 모르는 것을 구분할 수 있다.
- 첫 답변의 품질 자체가 위키 상태를 보여주는 진단 신호다 — 답변이 얕으면 자료 부족, 답이 산만하면 질문이 아직 넓은 것, 근거가 없으면 위키 문서의 출처 연결이 약한 것으로 해석하고 다음 자료 수집·질문 조정의 방향을 잡는다.
