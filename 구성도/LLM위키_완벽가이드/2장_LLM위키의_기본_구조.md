# 2장. LLM위키의 기본 구조

> 원본: https://wikidocs.net/book/19830 (박승규, 「LLM위키 완벽 가이드」)

## 2.1 지식이 쌓이는 세 층
원본: https://wikidocs.net/353382

- 자료를 한 폴더에 다 넣으면 처음엔 편하지만 시간이 지나면 원본·요약·판단·산출물이 뒤섞인다. 가장 위험한 패턴은 "LLM이 만든 매끄러운 요약이 원본처럼 보이는 것" — 예를 들어 원문에는 "검토 후 결정"이었는데 위키에는 "도입 결정"으로 슬쩍 단정되는 식의 왜곡이 생길 수 있다.
- 세 가지 구조를 비교(재구성):

| 구조 | 처음의 장점 | 나중의 문제 |
|---|---|---|
| 한 폴더에 전부 | 만들기 쉽고 검색됨 | 원본/요약/판단/산출물 혼재 |
| 원본+위키만 분리 | 근거·정리 구분 가능 | 정리 기준을 매번 설명해야 함 |
| raw+wiki+규칙파일 3층 | 원본 보존, 재사용, 작업기준을 함께 관리 | 초기 구조 설계가 필요 |

- **raw (원본 보관층)**: 회의록 원문, 웹 문서 저장본, PDF 추출 텍스트, 업무 메모 등을 원본 그대로 보존. 원칙은 "원본과 해석을 섞지 않는다" — 개인 판단이나 의견은 raw 파일에 적지 않고 wiki 쪽에 둔다. raw에 넣을지 판단하는 기준(재구성):
  - 회의록 원문·공식 문서 저장본·업무 메모 원문: 넣어도 됨 (근거 확인용)
  - LLM 요약문·개인 해석: 보통 raw에 두지 않음 (파생 문서이므로 wiki로)
  - 고객 개인정보·계약 조건·비공개 코드: 조직 보안 기준을 먼저 확인 필요
  - raw 파일 최소 형식: 제목, 출처, 확인 날짜(웹이면 URL+확인일, 회의록이면 날짜+참석범위)를 반드시 남긴다.
- **wiki (활용층)**: LLM이 원본을 읽고 정리한 지식이 쌓이는 곳. 원본을 그대로 반복하지 않고, 여러 원본에 흩어진 개념을 묶고 문서 간 연결을 만든다. 원본보다 짧고 구조적이어야 하며, 핵심 주장 옆에는 반드시 출처/근거 위치를 남겨야 한다 — 그래야 LLM이 만든 그럴듯한 문장이 실제로는 원본 조건을 빠뜨렸는지 검증할 수 있다.
- raw→wiki 흐름 예시: `raw/meeting-notes`, `raw/web-sources`, `raw/memos`의 여러 원천이 `wiki/concepts`(반복 업무 후보), `wiki/decisions`(결정 사항) 등 주제별 문서로 합쳐지고, `wiki/index.md`가 전체를 안내한다.
- **작업 규칙 파일(AGENTS.md/CLAUDE.md)**: LLM이 raw와 wiki를 어떤 기준으로 다룰지 규정하는 세 번째 층. "원본을 임의로 고치지 않는다", "확인 안 된 내용은 확인 필요로 표시한다" 같은 규칙을 담아, 사람이 매번 설명하지 않아도 LLM이 일관되게 작업하도록 만든다.
- 좋은 wiki 문서의 최소 형태(재구성 예): 제목 → 요약 → 확인된 내용(출처 표시 포함) → 확인 필요 항목. 확실한 것과 불확실한 것을 섞지 않는 것이 핵심.

## 2.2 좋은 폴더 구조 이해하기
원본: https://wikidocs.net/353383

- 이 책이 쓰는 최소 폴더 구조:
  ```
  work-automation/
  ├── index.md
  ├── log.md
  ├── raw/
  ├── wiki/
  └── output/
  ```
  raw는 원본 보존, wiki는 정리된 지식, index.md는 안내판, log.md는 작업 이력, output/은 실제로 쓰는 산출물(보고서·실행계획·요약문).
- **주제별로 폴더를 나눠야 하는 이유** 두 가지: ① 질문 범위를 좁히기 위해 — 관련 없는 자료가 섞이면 LLM 답변이 흐릿해지고, 한 주제 안에 필요한 자료만 있으면 근거 확인이 쉬워짐. ② 운영 주기가 다르기 때문 — 매주 갱신되는 주제와 보고서 한 번 만들고 끝나는 주제를 섞으면 오래된 판단과 최신 판단이 충돌.
- 주제 분리 판단 기준(재구성 표):

| 후보 작업 | 같은 폴더 가능 여부 | 이유 |
|---|---|---|
| 회의록 실행항목 추출 | 가능 | 반복 업무 자동화라는 같은 목적 |
| 주간 보고서 초안 | 가능 | 같은 팀의 반복 문서 흐름 |
| 고객 문의 개인정보 처리 기준 | 분리 권장 | 보안·법무 검토, 접근 범위가 다름 |
| 신규 프레임워크 조사 | 분리 권장 | 기술 리서치는 성격이 다름 |
| 책 원고 집필 자료 | 분리 권장 | 산출물·독자가 다름 |
- 판단 기준은 파일 형식이 아니라 "같은 질문에 함께 쓰일 자료인가"이다.
- 좋은 주제 폴더는 "질문 하나"로 설명 가능해야 한다. 예: work-automation은 "반복 업무를 LLM으로 줄이려면 무엇부터 해야 할까?"라는 질문에 답하는 폴더. 처음엔 3~10개 자료 정도의 작은 범위로 시작하는 것을 권장(everything 같은 목적 없는 큰 폴더는 피함).
- 주제를 나누지 않았을 때의 위험 경로: 모든 자료를 한 폴더에 저장 → 서로 다른 주제 자료가 섞임 → LLM이 관련 없는 근거를 함께 사용 → 답은 그럴듯하지만 출처 확인이 어려움 → 산출물 수정 시 원문을 다시 찾기 힘듦. 즉 폴더 구조는 정리 습관이 아니라 답변 품질을 지키는 장치.
- index.md / log.md / output/의 역할: index.md는 위키의 첫 화면(이 위키가 다루는 질문 + 읽는 순서를 안내, 긴 원문 전체를 넣지 않음), log.md는 처리 이력(자료 추가·문서 생성·미확인 주장 기록), output/은 wiki에 쌓인 지식을 실제로 "꺼내 쓰는" 산출물 저장소.
- 실습은 `mkdir -p`로 raw/wiki/output을 만들고 index.md·log.md에 최소 안내문을 채우는 수준의 Bash 스크립트로 구성되어 있다.

## 2.3 좋은 위키 문서의 조건
원본: https://wikidocs.net/353384

- 좋은 위키 문서의 세 조건: ① 출처가 남아야 한다, ② 질문에 다시 쓰기 쉬워야 한다, ③ 다른 문서와 링크로 연결돼야 한다. 문서를 "길게" 쓰는 것이 아니라 "다시 확인·질문·연결 가능하게" 쓰는 것이 핵심.
- 나쁜 문서 vs 좋은 문서 비교(재구성):

| 항목 | 나중에 곤란한 문서 | 다시 쓰기 좋은 문서 |
|---|---|---|
| 출처 | 근거 없이 단정 서술 | 원본 파일 경로를 명시 |
| 주장 | 측정 안 된 수치를 단정 | "확인 필요"로 명시적 표시 |
| 구조 | 문장 몇 줄로 끝 | 요약/근거/확인됨/확인필요/다음질문으로 구분 |
| 연결 | 고립된 문서 | 관련 문서로 링크 |
- **최소 출처 블록**에 넣을 항목: 원천 자료 경로, 확인 날짜, 자료 성격(내부 회의록/공식 문서/개인 메모), 확인 필요 사항, 관련 문서 링크. 이 블록이 있으면 문서만 보고도 근거와 한계를 바로 파악할 수 있다.
- 위키 문서 예시 골격(재구성): "한 문장 요약 → 근거(원천 자료·확인일·자료성격·관련문서) → 확인된 내용 → 확인 필요"의 4단 구성. 이렇게 하면 LLM에게 "확인된 내용과 확인 필요를 구분해서 답하라"고 요청할 수 있다.
- **질문 재료로 쓰기 좋은 문서 구조**: 한 문장 요약 / 적용 조건 / 판단 기준 / 한계 / 다음 질문의 다섯 요소를 갖추면, 단순히 "읽는 글"이 아니라 "비교표·실험계획·보고서 초안을 만드는 재료"가 된다. 각 요소는 이후 구체적 질문("우리 회의록은 자동화에 적합한가?", "자동화 우선순위를 정해줘" 등)으로 바로 연결된다.
- 메모 → 위키 문서 전환 예시: 두세 줄짜리 자유메모("회의록 정리는 매번 귀찮다...")를 그대로 두면 근거·조건·다음질문이 불분명하다. 이를 "한 문장 요약 / 적용 조건 / 판단 기준표 / 확인 필요"로 재구성하면 다시 쓰기 좋은 문서가 된다. 판단 기준표에는 반복 빈도, 검토 시간, 오류 위험, 민감정보 포함 여부 같은 축을 사용할 수 있다.
