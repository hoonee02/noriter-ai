# 6장. 위키에 질문하고 답을 검증하기

> 원본: https://wikidocs.net/book/19830 (박승규, 「LLM위키 완벽 가이드」)

## 6.1 좋은 질문 만들기
원본: https://wikidocs.net/353398

- 위키를 만든다고 좋은 답이 자동으로 나오지 않는다. 위키는 자료 저장소이고, 질문은 그 자료를 업무 결과로 꺼내는 도구다. "요약해줘" 같은 단순 검색 질문과 "결정할 수 있게 근거 있는 선택지 3개로 정리해줘" 같은 업무 질문은 서로 다른 품질의 답을 만든다.
- **좋은 업무 질문의 3요소**: ① 확인할 주제, ② 사용할 자료 범위, ③ 원하는 결과물의 형태. 이 세 가지가 질문 안에 함께 들어가야 한다.
- 질문 유형 비교(재구성):

| 질문 유형 | 답변이 하는 일 | 업무에서 부족한 점 | 개선 방향 |
|---|---|---|---|
| 단순 검색("~가 뭐야?") | 개념 설명 | 업무 맥락 부재 | 위키의 어떤 자료를 기준으로 답할지 지정 |
| 단순 요약("회의록 요약해줘") | 핵심 문장 압축 | 결정·쟁점·다음행동이 섞임 | 목적과 산출물 형식 지정 |
| 업무 질문 | 자료를 업무 판단에 맞게 재구성 | 근거 요구 없으면 검증 약함 | 출처·확인필요·다음행동까지 요청 |
| 검토 질문("근거 약한 항목 찾아줘") | 답변 신뢰도 점검 | 원문 연결 없으면 확인 어려움 | 원천 자료 경로와 판단 이유 요청 |
- 좋은 질문은 "긴 질문"이 아니라 "답변이 할 일을 분명히 하는 질문"이다.
- **맥락을 좁히는 4가지 경계**: 시간 범위(이번 주/지난 2주/특정 월), 자료 범위(특정 위키 문서/원천 자료 폴더), 판단 기준(비용/반복빈도/고객영향/실행난이도), 제외 범위(미검토 자료/추측/오래된 정책). 이 네 경계를 지정하면 "우리 업무 개선점은?" 같은 막연한 질문이 검증 가능한 답변으로 좁혀진다.
- 개선 예시(재구성): "wiki/customer-inquiry-labeling.md와 raw/meeting-notes의 5월 회의록을 기준으로, 고객 문의 자동화에서 아직 결정 안 된 쟁점을 '쟁점/근거/추가확인/다음행동' 표로 정리하고, 근거 부족한 항목은 확인 필요로 표시해달라"는 식으로 질문을 완성한다.

## 6.2 답변의 근거 확인하기
원본: https://wikidocs.net/353399

- 위키가 만든 문장은 원본이 아니라 파생 지식이다. 답변을 그대로 믿기 전에 ① 출처 유무, ② 확인된 내용 vs 추정, ③ 최신성 여부 세 가지를 점검해야 한다.
- 답변 문장은 보통 세 종류가 섞여 있다: 원천 자료에 직접 근거한 문장, 위키 문서에는 있지만 원본 연결이 약한 문장, LLM이 문맥상 보충한 문장. "위키에 있으니 사실"이라는 착각을 막기 위해 이를 구분해야 한다.
- 근거 상태 구분표(재구성):

| 답변 문장 유형 | 판단 기준 | 활용 방식 |
|---|---|---|
| 출처 있는 답 | 원천 자료 경로·URL·날짜·문서명 제시 | 단정 가능(단 출처의 날짜·범위 명시) |
| 위키 근거만 있는 답 | wiki 문서엔 있으나 raw/외부 URL 연결 없음 | "위키 정리 기준"으로 제한 표현 |
| 출처 없는 답 | 근거 파일·링크 없음 | 단정 금지, 확인 필요로 표시 |
| 추정 답 | "아마", "가능성이 높다" 등 표현 | 추정으로 분리, 후속 확인 질문 남김 |
- 실습 예시: "고객 문의 분류 자동화를 먼저 해야 할까?"라는 질문에 대한 5개 문장짜리 답변을 문장별로 라벨링(출처있음/출처없음/추정포함/위키상태확인/실행제안)해보면, "응답 시간이 크게 줄어들 것"처럼 그럴듯하지만 근거 없는 문장을 걸러낼 수 있다. 그런 문장은 보고서에 그대로 넣지 말고 "가능성은 있으나 위키에 정량 근거 없음"으로 고쳐 써야 한다.
- **출처 요청 프롬프트 패턴**: 질문할 때부터 답변 형식을 "결론 / 결론의 근거 / 근거 있는 문장과 출처 / 출처 없는 문장 / 확인 필요 / 다음 확인 질문"으로 지정하고, "출처 없는 내용은 단정하지 말고 확인 필요로 표시하라"는 주의사항을 포함시킨다. 이는 답을 길게 만들기 위함이 아니라 업무에 쓰기 전 검토 가능한 형태로 받기 위함이다.
- 출처가 있다고 전부 같은 확실성은 아니다. 회의록의 "문의가 늘었다"는 서술도 실제 통계 확인이 필요하고, 공식 문서의 기능 설명도 내가 쓰는 버전에서 동작하는지 별도 확인이 필요하다 — 출처 존재와 사실 확인은 별개의 문제다.

## 6.3 답변을 다시 위키에 반영하기
원본: https://wikidocs.net/353400

- 좋은 답을 얻어도 대화창에만 두면 다음에 같은 질문을 반복하게 된다. 검증한 답변을 위키에 반영하는 세 가지 방법: ① 결정 사항 기록, ② 새 지식을 출처와 함께 추가, ③ 반복 질문의 템플릿화.
- 전체 흐름(재구성): 위키에 질문 → 답변 수신 → 근거 확인 → "반영할 가치가 있는가" 판단(없으면 대화 기록으로 종료) → 있으면 결정 사항 기록 / 새 지식 추가 / 반복 질문 템플릿화 → index.md·log.md 갱신. 이 순환이 있어야 위키가 "질문할수록 좋아지는 시스템"이 된다.
- **"좋은 답변이었다"와 "우리 업무 기준으로 결정했다"는 다르다.** 결정 기록에는 선택한 결론, 선택 이유, 근거 자료, 확인 날짜, 다음 행동까지 함께 남겨야 한다. 결정 기록이 없으면 같은 논의(예: "회의록 자동화 형식")를 매번 다른 답으로 반복하게 된다.
- 결정 기록 항목표(재구성):

| 항목 | 내용 | 예시 |
|---|---|---|
| 결정 | 실제 채택한 결론 | 실행 항목은 담당자/기한/검증방법으로 기록 |
| 이유 | 선택 배경 | 다음 회의에서 진행 여부를 바로 확인하기 위해 |
| 근거 | 확인한 원천/위키 문서 | raw/meetings/2026-05-16-sales-sync.md |
| 확인 날짜 | 검토 날짜 | 2026-05-16 |
| 남은 의문 | 아직 미확인 부분 | 외부 고객 회의에도 같은 형식을 쓸지 |
| 다음 행동 | 결정 이후 할 일 | 회의록 템플릿 문서 갱신 |
- 결정을 문장 하나로 남기지 않고 이유·근거·다음행동까지 함께 적어야, 결정이 실제 실행으로 이어지고 근거 없는 결정은 재검증 대상임을 알 수 있다.
- 실습은 `wiki/decisions.md`에 "회의록 실행 항목은 담당자·기한·검증방법을 함께 기록한다"는 결정을 근거(raw 회의록 경로)·확인일·확인필요 항목과 함께 기록하는 예제로 구성된다. 반복되는 질문은 `templates/` 폴더에 프롬프트 템플릿으로 남겨 다음에는 자료만 갈아끼워 재사용하도록 한다.
