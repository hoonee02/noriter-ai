# LLM 위키 구성도

일반적으로 "LLM 위키"(LLM을 활용해 문서를 축적·검색·정리하는 지식 베이스)를 구성할 때
필요한 요소와, 그 요소들이 어떻게 연결되는지를 정리한 개요.

> 이후 `구성도/` 폴더에 쌓인 RAG·에이전트·실전 가이드북 정리를 가로질러 반복 확인된 패턴은
> [통합_인사이트.md](통합_인사이트.md)에 별도로 종합했다. 이 문서(구성도.md)는 그 인사이트를
> 반영해 최초 버전보다 확장된 상태다 — 3.x 레이어(에이전트 오케스트레이션/도구함/운영 규칙
> 문서)와 4번 항목의 일부는 실전 검증 이후 추가되었다.

## 0. 목적

이 구성도를 실제로 적용할 대상 시스템의 목적은 다음과 같다.

- 대상 기업을 멀티에이전트를 통해 다각도로 분석하여 인사이트 도출
- 특정 형식의 재무제표 분석
- 뉴스 검색을 위한 키워드 분석
- 정해진 형식의 엑셀 생성 툴

즉 위 1~4번의 "일반적인 LLM 위키 구성 요소"는 이 목적을 달성하기 위한 기반(지식 축적·검색
계층)이며, 그 위에 2.8 에이전트 오케스트레이션(다각도 분석을 담당할 역할별 에이전트),
2.9 도구함/MCP(재무제표 파서, 뉴스 검색 API, 엑셀 생성기 같은 목적별 도구)가 실제로 얹히는
지점이 된다.

## 1. 전체 구성도

```
┌───────────────────────────────────────────────────────────────┐
│                          입력 소스 (Sources)                     │
│   대화 로그 / 문서 업로드 / 웹 스크랩 / 메모 / 외부 API 응답 등     │
└───────────────────────────────┬─────────────────────────────────┘
                                 │ raw text
                                 ▼
                    ┌───────────────────────┐
                    │   1. 수집·정제 (Ingest)  │
                    │  - 청크 분할 (chunking) │
                    │  - 노이즈 제거          │
                    │  - 메타데이터 추출       │
                    └───────────┬────────────┘

                    ┌───────────────────────┐
                    │  2. 구조화 (Structuring) │
                    │  LLM 호출:              │
                    │  제목/요약/태그/본문 생성 │
                    │  기존 문서와 중복·연관   │
                    │  판단 (병합 or 신규)     │

                                 │ 구조화된 문서(Document)
                                 ▼
        ┌────────────────────────────────────────────┐
        │              3. 저장소 (Storage)              │
        │  ┌───────────────┐   ┌────────────────────┐ │
        │  │  문서 저장소     │   │  임베딩/벡터 인덱스   │ │
        │  │ (제목/요약/본문/ │   │ (의미 기반 검색용)    │ │
        │  │  태그/출처/링크)│   │                     │ │
        │  └───────┬───────┘   └──────────┬──────────┘ │
        │          │   상호 참조(링크 그래프)  │            │
        │          └────────────┬───────────┘            │
        │                       ▼                         │
        │              ┌─────────────────┐                │
        │              │  활동 로그 (Log)   │                │
        │              │ 생성/수정/삭제 이력 │                │
        │              └─────────────────┘                │
        └────────────────────────┬─────────────────────────┘

              ┌───────────────────┼───────────────────┐
              ▼                   ▼                   ▼
     ┌────────────────┐ ┌──────────────────┐ ┌──────────────────┐
     │ 4. 검색/질의      │ │ 5. 유지보수        │ │ 6. 열람/편집 UI    │
     │  (Retrieval &    │ │ (Maintenance)     │ │ (Browse/Edit)     │
     │   Query)         │ │  - 중복/모순 점검   │ │  - 문서 목록/검색  │
     │  질문 → 관련 문서  │ │  - 고아 문서 탐지   │ │  - 그래프 뷰       │
     │  검색 → LLM 답변   │ │  - 오래된 문서 갱신 │ │  - 수동 편집       │
     │  → (선택) 새 문서  │ │    제안            │ │                   │
     │    로 재저장       │ │                   │ │                   │
     └────────┬─────────┘ └─────────┬─────────┘ └───────────────────┘
              │                     │
              └─────────┬───────────┘

                         │ 답변/점검 결과가 다시 저장소를 업데이트

                 (3. 저장소로 순환)
```

## 2. 핵심 구성 요소

### 2.1 입력 소스 (Sources)
위키에 들어갈 원재료. 대화 기록, 업로드한 문서, 웹 검색 결과, 사용자의 수동 메모 등
형태가 다양하므로 공통 포맷으로 정규화하는 전처리가 필요하다.

### 2.2 수집·정제 (Ingest)
- **청크 분할**: 긴 텍스트를 LLM 컨텍스트에 맞는 단위로 나눔.
- **노이즈 제거**: 불필요한 서식, 반복, 개인정보 등을 걸러냄.
- **메타데이터 추출**: 출처, 시각, 원문 링크 등 추적 가능한 정보를 남김.

### 2.3 구조화 (Structuring)
LLM을 호출해 비정형 텍스트를 문서 형태(제목/요약/태그/본문)로 변환하는 단계.
- 소형 로컬 모델일수록 자유형 JSON보다 `TITLE:`/`SUMMARY:`/`TAGS:`/`BODY:` 같은
  줄 단위 포맷을 안정적으로 따르는 경향이 있어, 파서를 단순하게 유지하는 것이 유리하다.
- 이 단계에서 기존 문서와의 중복/연관 여부를 판단해 **신규 생성**할지 **기존 문서에 병합**할지
  결정하는 로직이 있으면 위키가 무한히 파편화되는 것을 막을 수 있다.

### 2.4 저장소 (Storage)
- **문서 저장소**: 제목/요약/본문/태그/출처/연관 문서 ID/생성·수정 시각을 갖는 레코드 집합.
  파일(JSON) 기반이든 DB 기반이든 핵심은 "구조화된 문서의 단일 소스"라는 점.
- **임베딩/벡터 인덱스**: 태그·제목 일치만으로는 놓치는 의미적 유사도를 잡기 위한 보조 인덱스.
  문서가 많아질수록 중요도가 커진다.
- **링크 그래프**: 문서 간 `related_ids` 같은 상호 참조로 지식 네트워크를 형성.
  - 단순 연결 여부뿐 아니라 **관계의 종류**(예: "이것을 근거로 만들었다", "이것을 참조한다",
    "이것을 반박한다")까지 함께 기록하면, 답변 시 근거를 함께 제시할 수 있고 여러 문서를
    거쳐야 답이 나오는 다중 홉(multi-hop) 질문에도 대응할 수 있다.
  - 각 관계·사실에는 **신뢰도 등급**(원본에 명시됨=확실 / 합리적 추론=중간 / 근거 부족=낮음)을
    함께 남겨, 답변 시 "확실한 내용"과 "추론한 내용"을 구분해 전달할 수 있게 한다.
  - 주의: 이 "지식 그래프"(정리된 지식 자체의 관계 구조)는 **워크플로우 그래프**(에이전트의
    실행 흐름을 그래프로 표현하는 것, 예: LangGraph의 상태 그래프)와는 다른 축의 개념이다.
    전자는 "무엇을 아는가"를, 후자는 "어떤 순서로 처리하는가"를 표현한다.
- **활동 로그**: 생성/수정/삭제 이력을 append-only로 남겨, UI 없이도 최근 변화를 추적 가능하게 함.

### 2.5 검색/질의 (Retrieval & Query)
사용자 질문이 들어오면:
1. **라우터**가 질문의 성격(전체 개요를 묻는 거시적 질문 / 특정 문서 범위의 중간 질문 /
   구체적 사실을 묻는 미시적 질문)을 판단해 어느 계층부터 볼지 정한다.
2. 원칙적으로 저장소 전체를 뒤지지 않고, **요약/인덱스를 먼저 읽고 필요한 하위 문서 2~3개만
   선택적으로 펼쳐 읽는다** — 이것이 토큰 소비를 크게 줄이는 핵심 원리이며, "인덱스 우선
   탐색"이라는 동일한 아이디어가 여러 구현체에서 이름만 바꿔(요약 인덱스, 1페이지 지식 지도
   요약 등) 반복해서 등장한다.
3. 컨텍스트 예산에 맞게 요약본만 쓸지 전체 본문을 쓸지 결정한 뒤, LLM에 질문 + 컨텍스트를
   넣어 답변을 생성한다. 답변이 검색된 근거에 실제로 기반하는지 별도로 검증하는 평가 단계를
   두면 할루시네이션을 줄일 수 있다(2.6 참고).
4. (선택) 답변 자체를 새 문서로 저장해 "탐색 자체가 위키를 성장시키는" 구조를 만들 수 있다 —
   단, 무분별하게 쌓이면 노이즈가 되므로 자동 저장 여부는 설계 판단이 필요하다. 실무에서는
   질의 결과를 일단 로그로만 쌓아두고, 정식 지식으로의 승격은 사람이 검토 후 결정하는 절충이
   흔히 쓰인다.

### 2.6 유지보수 (Maintenance)
위키가 커질수록 자체 점검이 필요하다.
- 서로 모순되는 문서 탐지
- 다른 문서와 연결이 없는 고아 문서 탐지
- 자주 언급되지만 전용 문서가 없는 개념 발견
- 오래되었거나 최신 정보와 어긋나는 문서 갱신 제안
이 점검 결과는 보통 문서로 저장하지 않고 별도 리포트/로그로만 남겨, 위키 본문을 오염시키지 않는다.

### 2.7 열람/편집 UI (Browse/Edit)
사람이 최종적으로 신뢰하고 쓰기 위한 인터페이스.
- 문서 목록/검색
- 문서 간 관계를 보여주는 그래프 뷰
- 수동 편집·삭제 (LLM 생성 결과를 사람이 직접 고칠 수 있는 통로)

### 2.8 에이전트 오케스트레이션 (Multi-agent Orchestration)
위키가 커지거나 처리할 작업이 복잡해지면, 하나의 에이전트가 수집·구조화·검색·산출물 생성을
전부 떠맡기보다 역할을 나눠 분업시키는 편이 안정적이다.
- **역할 분리**: 예를 들어 조사(자료 탐색)형, 정리(구조화)형, 실행(산출물 생성)형처럼 역할을
  나누면 실패 양상도 역할별로 달라지므로 각각에 맞는 점검이 가능해진다.
- **위임 패턴**: 메인 에이전트가 작업을 서브 에이전트에게 위임하는 Supervisor 방식, 대화 상황에
  따라 담당 에이전트가 바뀌는 Handoffs 방식 등이 흔히 쓰인다.
- 이 레이어는 위키/저장소 자체와는 별개이며, 2.5 검색/질의와 2.2 수집·정제 단계 양쪽에서 호출될
  수 있는 상위 제어 계층으로 이해하는 것이 자연스럽다.

### 2.9 도구함 / 외부 연동 (Tools & MCP)
에이전트가 위키 바깥의 기능(외부 문서 도구, 메신저, 코드 실행, 웹 검색 등)을 쓰려면, 그 기능을
이름 붙은 호출 가능한 함수(Tool)로 추상화해 두어야 한다.
- 검색 기능도 이 레이어의 한 사례다 (예: "전체 요약 검색", "세부 문서 검색"을 별개 도구로 분리).
- 외부 서비스 연동은 개별 API를 직접 붙이기보다 표준화된 프로토콜(MCP 등)로 도구 서버를
  등록해두면, 위키/에이전트 구현을 바꾸지 않고도 연동 대상을 늘리기 쉬워진다.

### 2.10 운영 규칙 문서 (Operating Rules)
"AI가 이 위키를 어떻게 다뤄야 하는지"를 자연어로 명시해 둔 별도 문서(예: `CLAUDE.md`,
`AGENTS.md` 같은 규칙 파일)가 있으면, 2.2~2.9의 동작 방식을 코드 수정 없이 프롬프트 수준에서
조정할 수 있다.
- 예: "질문 전에 요약 인덱스부터 확인해라", "원본 폴더를 통째로 훑지 마라", "새 파일이 들어오면
  위키를 갱신해라" 같은 지시를 이 문서 하나에 모아 관리한다.
- 규칙 문서 자체도 저장소의 일부이므로, 2.6 유지보수 점검 대상에 포함하는 것이 좋다.

## 3. 요소 간 관계 요약

| 구성 요소 | 입력 | 출력 | 연결되는 다음 단계 |
|---|---|---|---|
| 수집·정제 | 원시 소스 | 정제된 텍스트 | 구조화 |
| 구조화 | 정제된 텍스트 | 구조화된 문서 | 저장소 |
| 저장소 | 문서 CRUD | 문서 목록 + 인덱스 | 검색/질의, 유지보수, UI |
| 검색/질의 | 질문 + 저장소 컨텍스트 | 답변 | (선택) 저장소로 되먹임 |
| 유지보수 | 저장소 인덱스 | 점검 리포트 | 로그 / 사람의 후속 조치 |
| 열람/편집 UI | 저장소 전체 | 사람이 보는 화면 | 사람의 수동 편집 → 저장소 |
| 에이전트 오케스트레이션 | 작업 요청 | 역할별로 분배된 하위 작업 | 수집·정제 / 검색·질의 |
| 도구함 / MCP | 도구 호출 요청 | 외부 기능 실행 결과 | 검색·질의 / 에이전트 오케스트레이션 |
| 운영 규칙 문서 | (없음, 정적 문서) | 각 단계에 적용되는 지시 | 전 단계에 횡단 적용 |

## 4. 설계 시 고려할 선택지

- **자동 저장 vs 명시적 저장**: 대화마다 자동으로 위키에 쌓을지, 사용자가 명시적으로
  "저장" 트리거를 눌러야 쌓을지 — 전자는 풍부하지만 노이즈가 크고, 후자는 깨끗하지만 손이 간다.
- **요약 컨텍스트 vs 전체 본문 컨텍스트**: 위키가 작을 때는 전체 본문을 컨텍스트로 넣고,
  커지면 제목/요약/태그 인덱스만 넣는 식으로 토큰 예산에 따라 전환하는 전략이 필요하다.
- **단일 페이지 통합 vs 다중 페이지 통합**: 하나의 소스가 문서 하나만 만들지, 관련된 여러
  기존 문서를 동시에 업데이트할지 — 후자가 이상적이지만 구현 복잡도가 크게 늘어난다.
- **저장 포맷**: 단순 JSON 파일이냐, 임베딩까지 포함한 벡터 DB냐 — 문서 수/검색 정확도
  요구 수준에 따라 선택.
- **관계에 신뢰도를 표시할 것인가**: 관계·사실마다 확실/추론/불확실 등급을 남기면 답변의
  신뢰도를 구분해 전달할 수 있지만, 그만큼 구조화 단계의 판단 부담이 늘어난다.
- **되먹임 결과의 승격 방식**: 질의 응답을 곧바로 위키 문서로 자동 승격할지, 로그로만 쌓아두고
  사람이 검토 후 승격할지 — 전자는 위키가 빠르게 성장하지만 오염 위험이, 후자는 안전하지만
  운영 부담이 따른다.
- **에이전트를 단일로 둘 것인가, 역할별로 분업할 것인가**: 처리할 작업이 단순하면 단일
  에이전트로 충분하지만, 수집·검증·산출물 생성처럼 성격이 다른 작업이 섞이면 역할별 분업이
  실패 지점을 진단하기 쉽게 만든다.
