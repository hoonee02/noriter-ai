# RAG(Retrieval-Augmented Generation) 개념 확장 정리

앞서 정리한 [LLM 위키 구성도](구성도.md) 및 [메이커 에반 구성도_확장](메이커%20에반%20Maker%20Evan-구성도_확장.md)에서 다룬
"원본을 매번 다시 읽지 않고, 정리된 지식을 검색해서 재사용한다"는 아이디어의 기술적 뿌리가 RAG다.
이 문서는 RAG의 기본 개념부터, LLM 위키/Graphify 방식과의 관계, 확장된 형태까지 정리한다.

## 1. RAG란 무엇인가

**R**etrieval-**A**ugmented **G**eneration(검색 증강 생성) — LLM이 답변을 생성하기 전에,
외부 지식 저장소에서 관련 정보를 **검색(Retrieval)** 해 프롬프트에 끼워 넣고, 그 정보를
근거로 **생성(Generation)** 하게 만드는 구조.

- 등장 배경: LLM은 학습 시점 이후 정보를 모르고(hallucination 위험), 특정 조직·개인의
  비공개 데이터도 알지 못함. 매번 파인튜닝하는 것은 비용이 크고 최신성을 유지하기 어려움.
- 핵심 아이디어: "모델 자체를 업데이트하지 말고, 모델이 참고할 자료를 질문 시점에 찾아서 넣어주자."

```
질문(Query)
   │
   ▼
┌─────────────┐      ┌──────────────────┐
│  검색 (Retrieval) │ ──▶ │  관련 문서/청크 N개  │
└─────────────┘      └────────┬──────────┘
                               │ 컨텍스트로 삽입
                               ▼
                     ┌──────────────────┐
                     │  생성 (Generation)  │  LLM이 질문 + 검색된 근거로 답변
                     └────────┬──────────┘
                               ▼
                            최종 답변 (+ 출처 표시 가능)
```

## 2. 표준 RAG 파이프라인 구성 요소

| 단계 | 역할 | 세부 내용 |
|---|---|---|
| ① 문서 수집 | Ingest | 원본 문서를 모음 (PDF, 웹페이지, DB 레코드 등) |
| ② 청크 분할 | Chunking | LLM 컨텍스트에 맞게 문서를 작은 단위로 자름 (문단/토큰 수 기준) |
| ③ 임베딩 | Embedding | 각 청크를 벡터(숫자 배열)로 변환 — 의미가 비슷한 텍스트는 벡터 공간에서 가까움 |
| ④ 인덱싱 | Vector Store | 임베딩을 벡터 DB(예: FAISS, Pinecone, Chroma 등 일반명)에 저장 |
| ⑤ 검색 | Retrieval | 질문도 임베딩으로 변환 → 벡터 유사도로 관련 청크 Top-K 검색 |
| ⑥ 컨텍스트 구성 | Prompting | 검색된 청크들을 프롬프트에 삽입 (질문 + 근거 텍스트) |
| ⑦ 생성 | Generation | LLM이 삽입된 근거를 바탕으로 답변 생성 |
| ⑧ (선택) 인용 | Citation | 어떤 청크에서 나온 답변인지 출처 표시 |

## 3. RAG의 한계 — "단순 유사도 검색"의 문제

표준(naive) RAG는 아래와 같은 한계가 있으며, 이는 이전 문서에서 다룬 LLM 위키/Graphify가
보완하려는 지점과 직접 연결된다.

- **의미 유사도 ≠ 정답 관련성**: 벡터 거리가 가까운 문장이 실제로 질문에 답이 되는 문장이
  아닐 수 있음 (표면적 유사어에 낚이는 문제).
- **청크 단위 단절**: 문서를 잘라서 저장하기 때문에, 원래 문맥(앞뒤 문단, 전체 구조)이
  끊긴 채로 검색됨 — "이 표는 어느 회사 것인지"같은 문맥 정보가 유실되기 쉬움.
- **관계 정보 부재**: 청크 간의 "이게 근거다", "이걸 반박한다" 같은 관계를 모름 — 단순히
  비슷한 청크들을 나열할 뿐, 개념 간 구조를 이해하지 못함.
- **매 질문마다 재검색**: 한 번 찾은 답을 재사용하는 구조가 기본적으로 없음 — 같은 질문이
  다시 오면 처음부터 다시 검색·생성.
- **정합성 관리 부재**: 원본 문서가 여러 개로 나뉘어 모순된 내용을 담고 있어도, RAG 자체는
  이를 점검하거나 정리해주지 않음.

## 4. RAG의 확장 형태

### 4.1 Graph RAG (지식 그래프 기반 RAG)
- 청크를 독립적으로 저장하는 대신, 개념·개체 간의 **관계**를 그래프로 구성해 저장.
- 검색 시 벡터 유사도뿐 아니라 그래프 순회(관련 노드 탐색)를 함께 사용 →
  "이 개념과 연결된 것들"까지 포함해 답변 근거를 구성.
- [LLM 위키/Graphify 구성도](구성도.md)에서 다룬 `graph.json` / 관계 유형(근거·참조·기반) / 신뢰도
  등급 개념이 바로 Graph RAG의 아이디어를 구체화한 예시다.

### 4.2 Hierarchical / Summary RAG (계층적·요약 기반 RAG)
- 원문 → 문서 요약 → 전체 요약(인덱스)까지 여러 레벨의 요약을 미리 만들어 둠.
- 질문이 오면 최상위 요약(예: `GRAPH_REPORT`, `INDEX.md`)을 먼저 보고, 필요한 하위 노드만
  선택적으로 펼쳐서 읽음 — 토큰 절감의 핵심 원리 (카파시 방식·Graphify가 71.5배 절감을
  주장하는 근거와 동일한 구조).

### 4.3 Agentic RAG
- 검색을 한 번만 수행하지 않고, LLM(또는 서브 에이전트)이 스스로 "이 정보로는 부족하다 →
  추가 검색이 필요하다"를 판단해 반복적으로 검색·추론을 수행.
- Graphify의 "서브 에이전트 여러 개가 동시에 문서를 읽어 관계를 추출" 방식이 여기 해당.

### 4.4 Self-updating / Memory RAG (자기 갱신형 RAG, = LLM 위키 개념)
- 검색 결과나 답변을 다시 지식 저장소에 기록해, 다음 질문에 재사용하는 **되먹임 루프**를 추가.
- 표준 RAG는 "검색 → 생성"에서 끝나지만, 이 확장형은 "검색 → 생성 → 저장(위키 갱신)"까지
  포함 — 카파시가 말한 "유지보수 비용이 거의 제로"라는 특징이 여기서 나옴.
- [메이커 에반 구성도.md](메이커%20에반%20Maker%20Evan-구성도.md)의 "질의 응답이 다시 새 위키
  페이지로 저장된다"는 설계가 바로 이 확장형의 사례.

## 5. RAG 확장 형태 비교

| 방식 | 저장 단위 | 검색 방식 | 재사용성 | 관계 정보 |
|---|---|---|---|---|
| 표준(Naive) RAG | 텍스트 청크 | 벡터 유사도 | 낮음 (매번 재검색) | 없음 |
| Graph RAG | 개념/개체 노드 + 관계 | 유사도 + 그래프 순회 | 중간 | 있음 (관계 유형 포함) |
| Hierarchical RAG | 원문 + 다단계 요약 | 요약 우선 탐색 후 하위 확장 | 중간 | 부분적 (계층 구조) |
| Agentic RAG | 청크/노드 (도구 호출 포함) | 반복적·적응적 검색 | 중간 | 도구 사용 이력에 한정 |
| Self-updating(LLM 위키) RAG | 위키 페이지(사람이 읽을 수 있는 문서) | 인덱스/요약 우선 탐색 | 높음 (답변이 지식으로 축적) | 있음 (related_ids/그래프) |

## 6. 결론 — LLM 위키는 RAG의 한 진화 형태

- LLM 위키 + Graphify 구조는 RAG의 "검색 후 생성" 기본 골격 위에,
  **Graph RAG(관계 구조)** + **Hierarchical RAG(요약 우선 탐색)** + **Self-updating RAG(결과의
  재축적)** 세 가지 확장을 결합한 형태로 이해할 수 있다.
- 표준 RAG가 "매번 벡터 DB에서 청크를 새로 찾아오는 검색 엔진"에 가깝다면, LLM 위키는
  "사람이 읽을 수 있는 문서로 지식을 정리해 두고, AI가 그 문서를 인덱스부터 탐색하며
  스스로 갱신하는 지식 베이스"에 가깝다.
- 두 방식은 배타적이지 않으며, 실제로는 위키 페이지 자체도 임베딩해 벡터 검색을 보조
  수단으로 결합하는 하이브리드 구성이 일반적으로 권장된다.
