### D-01. 오케스트레이터–서브에이전트 큐 재진입 교착

| 항목 | 내용 |
|---|---|
| 위치 | `src-tauri/src/queue.rs:20, 57` × 설계 §4.1 |
| 시나리오 | W-1 / 4단계 |
| 유형 | 구조적 결함 (신규 유입) |
| 상태 | ✅ **구현 완료** (2026-08-02) — `queue.rs`에 `call_llm()` 신설, 기존 직접 호출 7곳(web 채팅·텔레그램·위키 3종·메모리 요약·개인메모리 추출) 전부 경유 전환. **조치안보다 한 걸음 더**: `run_queued`를 `pub` 해제(private) — 다른 모듈은 컴파일 자체가 안 되므로 "하나의 헬퍼로 강제"가 관례가 아니라 컴파일러 수준 강제가 됨 |

**현상**: 오케스트레이터가 `run_queued`로 실행되면 `run_lock`을 쥔 채 서브에이전트를 호출하고,
서브에이전트가 같은 `run_lock`을 다시 요구한다. `tokio::sync::Mutex`는 재진입 불가이므로 영구 교착.
UI는 응답 없이 멈추고 큐 패널에 2건이 남는다.

**근본 원인**: `run_queued`의 실제 목적을 잘못 확장 적용했다. `run_queued`는 "지금 Ollama가
처리 중인 작업이 있는지 체크하고, 있으면 순서를 기다리게 하는" **단일 Ollama 호출용 게이트**일
뿐이다(`queue.rs:20`의 `run_lock`이 지키는 건 "Ollama를 동시에 두 번 부르지 않는다"는 것 하나뿐).
그런데 D1 설계는 이 게이트를 "사용자가 트리거한 작업 전체를 큐 패널에 항목 하나로 보여주자"는
용도로도 함께 썼다 — `main.rs`의 기존 커맨드(`ollama_chat`, `wiki_query` 등)가 전부 "명령어 1개 =
Ollama 호출 1번"이라 두 가지 목적이 우연히 겹쳐 보였을 뿐, 실제로는 별개의 관심사다.
오케스트레이터처럼 "명령어 1개 = Ollama 호출 여러 번"인 합성 작업에 이 관례를 그대로 옮기면서
결함이 드러났다.

**확정 조치안**: `run_queued`를 직접 호출하는 지점을 시스템 전체에서 **단 하나의 헬퍼 함수로
강제**한다 — 판단이 아니라 구조로 재진입을 원천 차단한다.

```rust
/// 시스템에서 이 함수만이 queue::run_queued를 호출한다. 모든 에이전트 모듈
/// (전처리부/Taxonomy/Research/검증/최신화·버전관리/SalesCS, 그리고 이사장의 승인 판단
/// 자체도)은 ollama::chat을 직접 부르지 않고 반드시 이 헬퍼를 거친다.
pub async fn call_llm(
    app: &AppHandle,
    source: &str,     // 큐 패널 표시용: "agent:finance", "verification", "chairman-review" 등
    preview: String,
    model: &str,
    messages: &[ChatMessage],
    num_ctx: u32,
) -> Result<ChatResult, String> {
    queue::run_queued(app, source, preview, ollama::chat(model, messages, num_ctx))
        .await
        .map_err(|e| e.to_string())
}
```

- `chair_process`(이사장), `run_team`, `synthesize`, `run_verification_agent`,
  `run_versioning_agent`, `deliver` 등 어떤 조율 함수도 `queue::run_queued`를 직접 호출하지
  않는다 — 오직 실제 LLM 호출이 필요한 최말단에서만 `call_llm`을 통해 큐를 거친다.
- 이렇게 하면 "오케스트레이터를 큐 밖에서 실행해야 한다"는 규칙을 매번 사람이 기억해서
  지킬 필요가 없다 — `queue::run_queued`를 호출할 수 있는 코드 경로가 애초에 하나뿐이라
  재진입 자체가 구조적으로 불가능해진다.
- **큐 패널 표시는 부작용일 뿐, 별도로 설계할 필요 없다**: 이사장이 "전체 분석 중"이라는
  하나의 항목을 보여주려 애쓸 필요가 없다 — 사용자는 큐 패널에서 `agent:finance` →
  `verification` → `chairman-review` → ... 가 순서대로 지나가는 것을 그대로 보게 되며,
  이것이 오히려 무슨 단계가 진행 중인지 더 투명하게 드러난다.
- **병렬 디스패치(00_v0.1.5.1 §2.1)와의 관계**: 전처리부(OCR 경로)와 최신화·버전관리(사전
  프리플라이트, 대부분 LLM 불필요)를 `tokio::join!`으로 동시에 기다리는 것은 문제 없다 — 두
  갈래가 각각 `call_llm`을 부르면 실제 Ollama 호출은 `run_lock` 덕분에 자연스럽게 순서대로
  처리될 뿐이고(동시 실행이 아니라 대기), 이는 버그가 아니라 "Ollama는 한 번에 하나씩만
  처리한다"는 게이트의 정의 그대로 작동하는 것이다.
- **D-09(병렬/순차 모순)와의 관계**: Research 산하 3서브롤(Finance/News/Market)을 코드상
  `tokio::join!`으로 동시에 실행해도, 각자 `call_llm`을 부르는 한 실제 Ollama 요청은
  `run_lock`이 자동으로 한 줄로 세운다 — "동시에 실행을 시도해도 안전하다"는 뜻이므로, D-09는
  이제 순수 성능/설계 취향 문제로 격하되고 안전성 문제는 아니다.

**폐기된 대안**: 태스크 로컬 플래그로 재진입을 허용하는 방식은 "Ollama를 동시에 두 번 부르지
않는다"는 큐의 본래 보증을 깨므로 채택하지 않는다.

### D-02. `WikiEntry` 필드 추가 시 기존 위키 무성 손실

| 항목 | 내용 |
|---|---|
| 위치 | `src-tauri/src/wiki.rs:16, 59-64, 66-70` × 설계 §3.1 |
| 시나리오 | W-2 / 7단계 |
| 유형 | 데이터 손실 |
| 상태 | ✅ **구현 완료** (2026-08-02) — `WikiEntry`에 구조체 수준 `#[serde(default)]` + `Default` derive. 회귀 테스트 `wiki_entry_tolerates_missing_fields`(구스키마 JSON 로드) 통과. `Confidence`/`RelationKind`의 `Default` 구현은 해당 타입이 코드에 추가되는 시점(v0.1.5 필드 확장)의 작업으로 남음 |

**현상**: 설계가 추가하는 4개 필드(`relations`/`confidence`/`company`/`period`)가 기존
`index.json`에 없어 역직렬화가 실패 → `load_entries()`가 오류를 삼키고 빈 Vec 반환 →
사용자에겐 위키가 비어 보이고, 이후 첫 저장이 파일을 덮어써 **기존 문서 전체가 영구 소실**된다.

**주목**: `config.rs:5-10` 주석에 동일 유형의 버그를 이미 겪고 `AppConfig`에 `#[serde(default)]`로
방어했다는 기록이 있다. 같은 방어가 `WikiEntry`에는 적용되지 않았다.

**사용자 결정 (2026-07-26)**: 기존 `index.json`의 보존/마이그레이션은 불필요 — v0.1.5 업그레이드
시점에 과거 위키 데이터가 초기화되어도 무방하다. 이에 따라 원래 조치안의 2번(필드명 마이그레이션)과
3번(백업 파일 보존)은 **불필요해져 폐기**한다.

**확정 조치안 (단순화)**: `WikiEntry`에 구조체 수준 `#[serde(default)]`만 적용한다
(+ `Confidence`, `RelationKind`에 `Default` 구현).

- 이번 한 번의 마이그레이션을 위해서가 아니라, **v0.1.5 이후에도 스키마가 계속 진화할 것이므로**
  붙여두는 것 — 비용이 사실상 0(속성 하나)인데, 앞으로 필드를 추가할 때마다 이 문제가 재발하는
  것을 막아준다.
- 이 속성 하나만으로도 결과가 개선된다: 기존 필드는 그대로 읽히고 신규 필드만 기본값으로
  채워지므로, 데이터가 사라져도 그만이라는 이번 결정과 무관하게 **오히려 부작용 없이 기존
  데이터가 보존되는 쪽으로 동작**한다 — "없어져도 된다"가 "일부러 없앤다"는 뜻은 아니므로,
  거의 공짜로 더 나은 결과를 얻는 선택이다.
- `related_ids`→`relations` 필드명 변경에 대한 별도 마이그레이션·별칭 처리는 하지 않는다 —
  옛 필드가 인식되지 않으면 그냥 빈 배열로 시작한다(허용됨).
- `load_entries()`의 `.ok().unwrap_or_default()` 무성 처리도 그대로 둔다 — 이제 이 결정 하에서는
  "파싱 실패 시 빈 상태로 시작"이 의도된 동작이므로 별도 경고·백업 로직이 필요 없다.

### D-03. 질의 답변 자동 승격 → 자기오염 루프

| 항목 | 내용 |
|---|---|
| 위치 | `src-tauri/src/wiki.rs:258-267` |
| 시나리오 | W-5 / 2~4단계 |
| 유형 | 지식 무결성 / 원칙 위반 |
| 상태 | ✅ **구현 완료** (2026-08-02) — `DraftState`(`wiki/draft.json`) 신설 + `save_draft`/`list_draft`/`promote`/`discard_draft`. `query()`가 `WikiState`에서 읽고 `DraftState`로 쓰도록 시그니처 변경(두 저장소를 서로 다른 타입으로 받으므로 **호출부에서 뒤바꿀 수 없다**). IPC 3종(`wiki_draft_list`/`wiki_promote`/`wiki_discard_draft`) + UI "📝 검토 대기" 목록(반영/버리기)까지 함께 반영 — 승격 경로가 없으면 draft가 영영 쌓이기만 하기 때문. 회귀 테스트 `take_entry_removes_once_and_preserves_id` 통과 |

**현상**: `query()`가 생성 답변을 조건 없이 위키 페이지로 저장하고, 그 페이지가 다음 질의의
컨텍스트가 된다. LLM 추론 결과가 다음 답변의 근거로 재순환하며, `Inferred` 수치가 시간이 지나면
위키에 적힌 사실처럼 인용될 수 있다. 재무 분석(G-2) 맥락에서 특히 위험하다.

**원칙 위반**: 구성도 §2.5/§4의 "질의 결과는 로그로만 쌓고 승격은 사람 검토" 및
체크리스트 C-4·C-5.

**사용자 결정 (2026-07-26)**: `query()`의 "무조건 저장" 로직 자체는 바꾸지 않는다. 대신
**저장소를 두 개로 분리**해서, "쓰는 곳"과 "다음 질의가 읽는 곳"을 구조적으로 다르게 만든다.

**확정 조치안 (2저장소)**:

| 저장소 | 파일 | 쓰는 시점 | 읽는(컨텍스트로 쓰는) 시점 |
|---|---|---|---|
| **미승격(Draft)** | `wiki/draft.json` (신규) | `query()`가 매번 조건 없이 저장 — **현재 로직 그대로** | 절대 읽지 않음(다음 질의 컨텍스트에서 항상 배제) |
| **승격(Promoted)** | `wiki/index.json` (기존) | 사람이 UI에서 명시적으로 "위키에 반영"할 때만, 또는 멀티에이전트 파이프라인의 최신화·버전관리(사후, D3 §6/8.1)가 이사장 승인을 받은 결과를 기록할 때만 | `query()`를 포함한 모든 컨텍스트 조회가 여기서만 읽음 |

```rust
pub struct DraftState(Mutex<Vec<WikiEntry>>);   // wiki/draft.json 백엔드, WikiEntry와 동일 구조 재사용

pub fn save_draft(state: &DraftState, entry: WikiEntry) { /* 현재 save()와 동일한 무조건 저장 */ }
pub fn list_draft(state: &DraftState) -> Vec<WikiEntry> { /* 검토 UI용 열람 */ }

/// 사람이 명시적으로 호출해야만 실행 -- draft에서 제거하고 승격 저장소(index.json)에 추가.
/// 멀티에이전트 파이프라인의 최신화·버전관리(사후) 역할이 내부적으로 부르는 함수와 동일하다.
pub fn promote(draft: &DraftState, wiki: &WikiState, id: &str) -> Result<(), String> { .. }
pub fn discard_draft(draft: &DraftState, id: &str) { .. }

pub async fn query(app: &AppHandle, wiki: &WikiState, draft: &DraftState, model: &str, num_ctx: u32, question: &str) -> Result<String, String> {
    let entries = list(wiki);              // ★ 승격 저장소만 컨텍스트로 사용 -- draft는 절대 안 읽음
    // ... 기존 컨텍스트 구성/LLM 호출 로직 그대로 ...
    save_draft(draft, WikiEntry { source: "query".into(), .. });  // ★ 목적지만 draft로 변경, 저장 자체는 무조건 실행(기존 그대로)
    Ok(answer)
}
```

- **코드 변경이 최소화된다**: "저장할지 말지 판단하는 조건문"을 새로 넣는 게 아니라, 저장 대상
  파일/상태만 바꾸는 것이므로 `query()`의 로직 흐름 자체는 그대로 유지된다.
- **다음 질의가 자동으로 안전해진다**: `query()`가 컨텍스트를 만들 때 여전히 `list(wiki)`(승격
  저장소)만 보므로, 별도 필터링 로직 없이 "이전 질의 답변이 다음 질의 근거가 되는" 경로 자체가
  사라진다.
- **멀티에이전트 파이프라인과 자연스럽게 통합**: 00_v0.1.5.1_설계서 §8.1의 최신화·버전관리
  (사후) 역할이 곧 이 `promote()`의 실제 호출자다 — 이사장 승인을 받은 draft만 `index.json`으로
  옮겨진다. 같은 §8.2의 프리플라이트 인덱스도 승격 저장소만 조회 대상으로 삼는다(초안을 근거로
  요약을 만들지 않게 됨).
- draft 저장소는 `wiki/draft.json` 하나로 단순하게 두고(질의 답변뿐 아니라 멀티에이전트의
  검증/승인 전 findings 초안도 같은 곳에 쌓아도 무방 — 어차피 컨텍스트로 읽히지 않으므로 구조를
  더 나눌 필요는 없다).

### D-04. 컨텍스트 임계값 all-or-nothing → 재무 수치 미전달

| 항목 | 내용 |
|---|---|
| 위치 | `src-tauri/src/wiki.rs:244` |
| 시나리오 | W-2 / 9단계 |
| 상태 | ✅ **구현 완료** (2026-08-02) — `preflight.rs` 신규. 6000자 2택을 **티어 랭킹 + 파생 예산**으로 교체 |

### D-06. `new_id()` 밀리초 정밀도 → ID 충돌

| 항목 | 내용 |
|---|---|
| 위치 | `src-tauri/src/wiki.rs:77, 104, 131, 153` |
| 시나리오 | W-1 / 7단계, W-4 / 4단계 |
| 상태 | ✅ **구현 완료** (2026-08-02) — 확정 조치안 그대로: `SEQ: AtomicU64` + `wiki_<ts>_<seq>`, ID 생성 락 안 이동. 회귀 테스트 `wiki::tests::new_id_unique_in_tight_loop`(1만 개 타이트 루프, 통과) 추가 |

**현상**: ID가 `wiki_%Y%m%d%H%M%S%3f`(밀리초). 동일 밀리초에 두 번 저장하면 ID가 겹친다.
충돌 시 `update()`(`wiki.rs:131` `find`)는 **첫 건만** 수정하고, `delete()`(`wiki.rs:153` `retain`)는
**두 건 모두** 삭제한다 — 사용자가 페이지 하나를 지웠는데 두 개가 사라진다.

**비동기 문제가 아니다**: 동기 코드에서도 발생한다. `for page in pages { save(..) }` 같은 타이트
루프에서 `save()` 한 번이 1ms 안에 끝나면(위키가 작고 `fs::write`가 페이지 캐시에 흡수될 때)
연속 반복이 같은 밀리초에 들어간다. 원인은 동시성이 아니라 **밀리초 해상도보다 빠르게 호출될 수
있는 함수에 밀리초 기반 ID를 쓴 것** 자체다.

**영향 범위 — ID는 단순 식별자가 아니다**

| 의존 대상 | 충돌 시 |
|---|---|
| `WikiRelation.target_id` (설계 §3.1) | "이것을 근거로 만들었다" 관계가 두 페이지를 동시에 가리킴 → 관계 그래프 신뢰 불가 |
| `VersionRecord.supersedes` (D3 §6) | 버전 체인이 끊기거나 잘못된 이전 버전을 가리킴 |
| 엑셀 `근거` 시트 (D1 §4.4) | 출처 페이지를 특정 불가 |

**확정 조치안 (2026-07-26)**: 타임스탬프 + 원자적 단조 카운터.

```rust
use std::sync::atomic::{AtomicU64, Ordering};

static SEQ: AtomicU64 = AtomicU64::new(0);

fn new_id() -> String {
    format!("wiki_{}_{}",
        chrono::Local::now().format("%Y%m%d%H%M%S%3f"),
        SEQ.fetch_add(1, Ordering::Relaxed))
}
```

- **재시작 시 카운터 리셋은 문제가 되지 않는다**: 충돌하려면 재시작 전후 저장이 같은 밀리초에
  일어나야 하는데, 프로세스 종료→Tauri 초기화→첫 저장까지 최소 수백 ms가 걸려 물리적으로
  불가능하다. 타임스탬프가 **거시적 유일성**(재시작·초 단위)을, 카운터가 **미시적 유일성**(같은
  밀리초 내)을 담당하는 조합이라 빈틈이 없다.
- **함께 적용 권장**: 현재 `wiki.rs:104`는 ID를 락 **밖**에서 만든다. 이를 락 안으로 옮기면
  추가 비용 없이 순서까지 보장된다. `save()` 내부를 어차피 수정해야 하므로, **D-07(비원자적
  전량 덮어쓰기)의 임시파일+rename 조치를 같은 작업에서 함께** 처리해 두 번 건드리지 않는다.

**폐기된 대안**

| 대안 | 폐기 사유 |
|---|---|
| **`save()`를 큐(`run_queued`)에 태우기** | 직렬화는 **순서**를 보장할 뿐 **고유성**을 보장하지 않는다 — 시계는 직렬화한다고 빨리 가지 않으므로 같은 밀리초 충돌이 그대로 남는다. 게다가 `WikiState`의 `Mutex`가 이미 저장을 직렬화하고 있어 계층만 두 겹이 된다. 부작용으로 ① D-01 불변식("`call_llm`만 `run_queued` 호출") 파기 ② 저장이 진행 중인 LLM 생성 뒤에서 수 초 대기 ③ 큐 패널 오염이 따른다 |
| 나노초 정밀도(`%9f`) | 문제의 성격을 바꾸지 못한다 — "1ms 안에 두 번이면 충돌"이 "1μs 안에 두 번이면 충돌"로 바뀔 뿐이고, 클록이 실제로 그 해상도를 준다는 보장도 없다. 암묵적 타이밍 가정에 의존하는 해결은 하드웨어가 바뀌면 조용히 재발한다 |
| UUID | 충돌은 확실히 막지만 `uuid` 크레이트가 추가되고, 시간순 정렬이 깨지며, 로그(`log.md`)·엑셀 `근거` 시트에 노출되는 ID를 사람이 읽을 수 없게 된다 |
| 순수 카운터(`wiki_7`) | 재시작 시 리셋되면 기존 ID와 충돌 — 시작 시 max+1 스캔이 필요하고 시간 정보도 소실된다 |

### D-07. `index.json` 비원자적 전량 덮어쓰기 + 조용한 초기화

| 항목 | 내용 |
|---|---|
| 위치 | `src-tauri/src/wiki.rs:66-70` (`fs::write`), `59-64` (`unwrap_or_default`) |
| 시나리오 | W-1 / 8단계 |
| 상태 | ✅ **구현 완료** (2026-08-02) — 확정 조치안 그대로: `index.json.tmp`에 완전히 쓴 뒤 `fs::rename` 교체. `load_entries`의 `unwrap_or_default`는 결정대로 유지. D-06과 같은 작업에서 처리됨 |

**현상**: 매 저장마다 전체 인덱스를 덮어쓴다. 쓰기 도중 종료되면 파일이 절단되고,
다음 기동 시 파싱 실패가 조용히 빈 위키로 처리되어(D-02와 동일 경로) 복구 기회 없이 손실이 확정된다.

**D-02 결정에 따른 범위 축소**: 원래 조치안은 ①원자적 쓰기 ②파싱 실패 시 백업 보존+오류 노출
두 갈래였다. 그러나 D-02에서 **"기존 index.json 보존 불필요"** 로 결정되면서 ②는 폐기된다 —
파싱 실패 시 빈 상태로 시작하는 것이 이제 의도된 동작이므로 백업·경고가 필요 없다.

남은 문제는 **진행 중인 세션의 손실**뿐이다. 앱을 쓰는 도중 쓰기가 중단되면, "지난번 데이터야
없어져도 된다"는 결정과 무관하게 **방금까지 작업한 내용**이 날아간다. 이건 여전히 막아야 한다.

**확정 조치안**: 임시 파일에 쓴 뒤 원자적으로 교체한다.

```rust
fn save_entries(entries: &[WikiEntry]) {
    let Ok(text) = serde_json::to_string_pretty(entries) else { return };
    let path = index_path();
    let tmp = path.with_extension("json.tmp");
    // 임시 파일에 먼저 완전히 쓴다 -- 여기서 중단돼도 기존 index.json은 온전하다.
    if fs::write(&tmp, text).is_err() { return; }
    // rename은 같은 볼륨 내에서 원자적이다. Rust의 fs::rename은 Windows에서도
    // 대상이 존재하면 교체한다(MOVEFILE_REPLACE_EXISTING).
    let _ = fs::rename(&tmp, &path);
}
```

- 중단 지점이 어디든 `index.json`은 **항상 완결된 이전 상태이거나 완결된 새 상태**다.
  절단된 중간 상태가 디스크에 남지 않는다.
- `load_entries()`의 `.ok().unwrap_or_default()`는 **그대로 둔다** — D-02 결정에 따라
  "파싱 실패 시 빈 상태로 시작"이 정상 동작이다.

**D-06과 함께 처리한다**: 두 결함 모두 `save()`/`save_entries()` 주변([wiki.rs:66](../../src-tauri/src/wiki.rs),
[wiki.rs:104](../../src-tauri/src/wiki.rs))을 수정하므로, ID 생성을 락 안으로 옮기는 작업과
원자적 쓰기 도입을 한 번에 처리해 같은 함수를 두 번 건드리지 않는다.

### 확정 조치안 ① — 빈 본문은 "명시적 실패"로 만든다

어설픈 빈 페이지를 만들지 않는다. **본문을 못 가져왔으면 페이지를 만들지 말고 실패를 반환한다.**

```rust
pub enum ParseError {
    /// 본문 수집 실패 -- 페이지를 만들지 않는다.
    EmptyBody { raw_response: String },
    /// 제목 수집 실패 -- 조치안 ③에 따라 이것도 실패로 취급한다.
    EmptyTitle { raw_response: String },
}

/// 반환형이 튜플에서 Result로 바뀐다 -- 실패를 호출자에게 전달할 수 있게 하는 것이 핵심.
fn parse_structured(text: &str) -> Result<ParsedPage, ParseError> {
    // 파싱 완화: 라인 trim() 후 대소문자 무시 접두사 매칭,
    //           `BODY:` 뒤 같은 줄 잔여 텍스트는 본문 첫 줄로 편입
    // 완화 후에도 본문이 비면 -> Err(EmptyBody), 원문을 함께 실어 보낸다
}
```

- 실패 메시지는 **"본문 수집 실패"** 로 명확히 드러낸다 — 어느 페이지의 문제인지가 아니라
  **수집 자체가 실패했다는 사실**을 알리는 것이 목적이다.
- `raw_response`(모델 원문)를 함께 반환해 재시도·진단이 가능하게 한다.
- 저장 로그(`wiki.rs:118`)에 본문 길이를 함께 남겨 사후 추적을 가능하게 한다.

### 확정 조치안 ② — 반복 실패 시 미결작업으로 이관

일시적 형식 흔들림은 재시도로 해결되지만, 계속 실패하면 사람이 봐야 한다.

```rust
const PARSE_RETRY_LIMIT: u32 = 3;

pub async fn ingest(...) -> Result<WikiEntry, String> {
    for attempt in 1..=PARSE_RETRY_LIMIT {
        let result = call_llm(app, "wiki-ingest", preview, model, &messages, num_ctx).await?;
        match parse_structured(&result.content) {
            Ok(page) => return Ok(save(state, page, ..)),
            Err(e) => { log_parse_failure(attempt, &e); continue; }
        }
    }
    // 3회 모두 실패 -> 처리 대기 목록으로
    save_pending_work(app, source_label, ParseFailureRecord { .. }).await;
    Err("본문 수집에 반복 실패해 미결작업으로 이관했습니다".into())
}
```

**기존 메커니즘을 재사용한다**: 이관 대상은 D3 §8.3에서 이미 만든
`<config dir>/noriter-ai/wiki/미결작업.md`이며, 새 저장소를 만들지 않는다. 재작업 상한도
이사장 승인 게이트의 3회(D3 §8.1)와 같은 값을 쓴다 — **"3회 시도 후 사람에게"** 라는 규칙이
시스템 전체에서 일관되게 적용된다.

> 두 루프는 목적이 다르다(승인 게이트는 *내용*의 합의 실패, 이쪽은 *형식* 파싱 실패)는 점에서
> 별개 상수·별개 코드 경로지만, **도달지와 상한값을 공유**해 사용자가 확인할 곳을 하나로 유지한다.

### 확정 조치안 ③ — 제목 정책: 폴백을 제거한다

**"제목이 없을 리 없다"** 는 판단에 따라 `wiki.rs:189-192`의 `"제목 없음"` 폴백을 **제거**하고,
제목이 비면 본문과 마찬가지로 실패로 처리한다.

| 항목 | 기존 | 변경 후 |
|---|---|---|
| 본문 비었을 때 | 조용히 빈 페이지 저장 | **실패** |
| 제목 비었을 때 | `"제목 없음"`으로 폴백 | **실패** |

폴백을 없애는 근거는 제목의 **역할이 바뀌기 때문**이다.

- **제목은 단어 형태로 저장한다** — 문장이 아니라 짧은 명사구/단어. 예: `"삼성전자의 2025년
  재무 실적에 대한 분석"`이 아니라 `"삼성전자"`, `"영업이익률"`처럼.
- **제목은 문서 간 연결의 키다** — 본문에서 고유한 규칙에 따라 다른 문서의 제목을 참조해
  **필요한 만큼만** 연결한다. 모든 언급을 자동 링크하지 않고 의미 있는 것만 잇는다는 절제가
  D-04의 "필요한 만큼만 펼친다"와 같은 원칙이다.

즉 제목은 단순 표시용 문자열이 아니라 **식별자 겸 링크 앵커**이므로, `"제목 없음"` 같은 폴백값이
들어가면 **서로 무관한 문서들이 같은 앵커를 공유**하게 되어 연결망이 오염된다. 폴백은 표시용
문자열에나 허용되는 편의이지, 식별자에는 허용될 수 없다.

### 확정 조치안 ④ — 제목 중복 시 `제목(분야:○○)` 형태로 구분

조치안 ③에서 제목이 **연결 앵커**가 되면서 새로 생긴 문제(동명 페이지가 둘이면 연결이 모호해짐)를
함께 해결한다. 위키에서 흔히 쓰는 괄호 구분 방식을 따르되, **내부 표현까지 하나로 통일**한다.

#### 저장 구조 — 기본 제목과 구분자를 분리한다

```rust
pub struct WikiEntry {
    /// 기본 제목 -- 단어 형태, 괄호 없음. 본문에서 링크를 작성할 때 쓰는 표기다.
    pub title: String,
    /// 동명 페이지가 있을 때만 채워진다. 단독이면 None.
    pub disambiguator: Option<Disambiguator>,
    // ...
}

/// 구분 축 -- 우선순위 순으로 시도한다(아래 판정 규칙).
pub enum Disambiguator {
    Industry(IndustrySection),  // 1순위: 산업 (Taxonomy 1단계)
    Company(String),             // 2순위: 기업 (corp_code)
    Period(String),              // 3순위: 회계기간
}

impl WikiEntry {
    /// 내부·표시·링크에 공통으로 쓰는 정규 제목. 이 함수가 유일한 제목 표현 경로다.
    pub fn canonical_title(&self) -> String {
        match &self.disambiguator {
            None => self.title.clone(),
            Some(d) => format!("{}({})", self.title, d.label()),  // "영업이익률(제조업)"
        }
    }
}
```

**분리 저장하는 이유**: `title`에 괄호까지 통째로 넣으면, 나중에 동명 페이지가 삭제돼 충돌이
해소돼도 괄호가 남는다. 기본 제목을 보존하면 구분자만 떼어내면 된다.

#### 구분 축 판정 규칙 — 산업만으로는 부족하다

Taxonomy 1단계(산업)를 1순위로 쓰되, 그것만으로 고정하지 않는다. **동명 페이지가 같은 산업에
속하는 경우**(예: 삼성전자와 LG전자의 `영업이익률` 페이지는 둘 다 `C.제조업`)가 흔하기 때문이다.

| 순위 | 축 | 적용 조건 | 결과 예 |
|---|---|---|---|
| 1 | 산업 | 두 페이지의 산업이 **다를 때** | `영업이익률(제조업)` / `영업이익률(금융업)` |
| 2 | 기업 | 산업이 같고 기업이 다를 때 | `영업이익률(삼성전자)` / `영업이익률(LG전자)` |
| 3 | 기간 | 기업까지 같고 기간이 다를 때 | `영업이익률(2025-FY)` / `영업이익률(2024-FY)` |
| — | (구분 불가) | 세 축이 모두 같을 때 | **진짜 중복 문서**로 보고 §2.6 lint의 병합 대상으로 표시 |

> 마지막 행이 중요하다. 산업·기업·기간이 전부 같은데 제목까지 같다면 구분자를 붙일 이유가 아니라
> **같은 내용을 두 번 저장한 것**이다. 억지로 일련번호를 붙이지 않고 중복으로 신고한다.

**복수 산업 기업의 처리**: 1단계는 `industries: Vec<IndustrySection>`(설계 §4.1.2)이므로 산업이
여럿일 수 있다. 이때는 **관련도 최상위 산업 하나**만 구분자로 쓴다 — 구분자는 사람이 읽는 짧은
꼬리표이지 분류 정보의 완전한 사본이 아니다. 전체 산업 목록은 `industries` 필드에 그대로 남는다.

#### 충돌 감지와 소급 적용

`save()` 시점에 같은 `title`을 가진 기존 페이지를 조회한다.

1. 없으면 → `disambiguator = None`으로 저장
2. 있으면 → **신규 페이지뿐 아니라 기존 페이지에도** 구분자를 부여한다

2번이 핵심이다. `영업이익률`이 이미 있는데 두 번째가 들어오면, 첫 번째를 그대로 두고 두 번째만
`영업이익률(금융업)`으로 만들면 **어느 쪽이 어느 것인지 알 수 없는 비대칭 상태**가 된다.
둘 다 구분자를 갖도록 소급 적용한다.

#### 링크가 깨지지 않는 이유 — 링크의 실체는 ID다

소급 적용으로 제목이 바뀌면 기존 링크가 깨질 것처럼 보이지만, 그렇지 않다.

| 계층 | 값 | 성질 |
|---|---|---|
| 본문 작성 표기 | `영업이익률` (기본 제목) | 사람이 쓰고 읽는 것 |
| 저장된 관계 | `WikiRelation.target_id` (설계 §3.1) | 실체 — **제목이 바뀌어도 불변** |
| 화면·리포트 표시 | `canonical_title()` | 표시 시점에 계산 |

저장 시 본문의 제목 참조를 **ID로 해석(resolve)해서 `relations`에 기록**하므로, 이후 제목이
바뀌어도 관계는 유지된다. D-06에서 ID 고유성을 확보한 것이 여기서 값을 한다.

**참조가 모호할 때**: 본문에 `영업이익률`이라고만 썼는데 후보가 여럿이면, 같은 기업·같은 산업
스코프 내 페이지를 우선 해석한다. 그래도 모호하면 **링크를 만들지 않는다** — 조치안 ③의
"필요한 만큼만 연결한다"는 절제를 여기서도 적용한다. 잘못 이은 링크는 안 이은 것보다 나쁘다.
