## 0. 이번 개정 요약

| 대상 | 변경 내용 |
|---|---|
| ① Ingestion | **"전처리부"로 재편** — 엑셀/PDF/이미지(OCR) 등 파일 추출 스킬·툴 저장소 신설. 단독 에이전트로서 이사장으로부터 "사용자 요청사항 + 파일"을 직접 받아 처리 |

| ③ Research | Taxonomy 산하이지만, 이사장이 직접 호출하는 **스탠드얼론 실행도 가능**(이중 접근 경로) |

| ⑤ SalesCS | **이사장의 유일한 엔드포인트**로 확정. 사용자 프롬프트의 "목적"을 기억해두었다가, 처리 완료된 산출물을 그 목적에 맞게 재처리해 출력 |
| 검증 | 기존 3항목(팩트체크/오류검수/출처검증)에 **4대 논리적 오류 체크리스트** 추가 |
| 최신화·버전관리 | 기존 사후(post-approval) 버전화·아카이빙 기능에 더해, **사전(pre-flight) 역할 신설** — 이사장이 프롬프트 처리를 시작하기 전에 5단계 우선순위 인덱스(사전 저장된 요약본)를 제공 |

### 2.2 "근거 기반 승인/반려"란?

이사장이 팀 산출물을 승인·반려할 때, **자기 스스로의 주관적 판단이 아니라 검증 에이전트가 만든
`VerificationReport`(D3 §4)를 근거로 판단**한다는 뜻이다.

- 검증 에이전트가 `FactVerdict::Contradicted` 항목을 보고하면 → 반려 사유로 그 항목을 그대로 인용
- 4대 논리오류(7절) 중 하나라도 플래그되면 → 반려 사유에 어떤 오류가 어디서 발견됐는지 명시
- 반대로 검증 리포트에 문제 항목이 없으면 → 승인

즉 "근거 기반"의 반대는 "이사장이 스스로 내용을 다시 읽고 감(feeling)으로 판단하는 것"이다.
이사장의 승인/반려 사유는 항상 검증 리포트의 특정 항목을 가리킬 수 있어야 하며, 근거 없이
"왠지 부족해 보임" 같은 반려는 설계상 허용하지 않는다.

### 2.3 "최종 게이트키퍼"란? — SalesCS의 "유일한 엔드포인트"와의 차이

이사장과 SalesCS는 각각 다른 의미로 "마지막"이다 — 혼동하기 쉬워 명확히 구분한다.

| 역할 | 무엇의 마지막인가 | 통과 못 하면? |
|---|---|---|
| **이사장 = 최종 게이트키퍼** | **내용(content)의 승인** — 검증을 거친 산출물이 위키에 정식 반영되고 다음 단계(최신화·버전관리)로 넘어갈 자격이 있는지 | 반려되어 재작업 루프로 (3회 상한 후 미결작업.md) |
| **SalesCS = 유일한 엔드포인트** | **전달 경로(delivery channel)** — 승인·버전화까지 끝난 산출물이 사용자에게 나가는 유일한 통로 | 다른 에이전트가 직접 사용자에게 응답할 방법 자체가 없음 (설계상 배제) |

즉 이사장은 "이 내용이 맞는가/신뢰할 만한가"를 최종 승인하는 문지기이고, SalesCS는 "승인된
내용이 사용자에게 나갈 때 반드시 거쳐야 하는 유일한 출구"다. 이사장을 통과하지 못하면 애초에
SalesCS까지 도달하지 못하므로 두 게이트는 순차적이며 서로를 대체하지 않는다.

### 2.4 데이터 모델

```rust
pub struct UserIntent {
    pub raw_prompt: String,
    /// 이사장이 접수 시점에 1차 판단한 목적 — SalesCS가 최종 출력 재처리 시 사용
    pub inferred_purpose: String,       // 예: "재무 건전성 판단", "뉴스 동향 파악", "보고서 제출용"
    pub desired_output: Option<OutputFormat>,
}

pub enum OutputFormat { Brief, DetailedReport, Excel, Unspecified }

pub struct UploadedFile {
    pub file_name: String,
    pub bytes: Vec<u8>,
}

/// 이사장 오케스트레이션 진입점. D-01 확정 조치안(03_결함기록부.md): 이 함수를 포함해 어떤
/// 조율 함수도 queue::run_queued를 직접 호출하지 않는다 -- 시스템 전체에서 run_queued를
/// 호출하는 지점은 call_llm() 헬퍼 하나뿐이며, 모든 에이전트는 ollama::chat 대신 call_llm을
/// 통해서만 LLM을 부른다. tokio::join!으로 병렬 대기하는 두 갈래(전처리부, 최신화 프리플라이트)
/// 중 실제 call_llm이 필요한 쪽(전처리부의 OCR)만 큐를 거치고, 최신화 프리플라이트는 알고리즘적
/// 조회라 애초에 call_llm을 부르지 않는다(8.2절). 두 갈래가 동시에 call_llm을 부르더라도
/// run_lock이 자연스럽게 순서를 매길 뿐 교착으로 이어지지 않는다.
pub async fn chair_process(
    app: &AppHandle,
    wiki: &WikiState,
    drafts: &DraftState,                // D-03 -- 승인 전 산출물은 여기에만 쓴다
    model: &str,
    num_ctx: u32,
    user_prompt: String,
    files: Vec<UploadedFile>,
    cancel: &CancelToken,               // §5.4 -- 각 단계 진입부에서 확인
) -> Result<GovernanceOutcome, String> {
    let intent = capture_user_intent(&user_prompt);

    // RD-01 조치(2026-08-02): 프리플라이트 1단계 기준이 "동일 대상(기업)"인데 기업은
    // Taxonomy가 나중에 확정한다 -- 순환 의존을 끊기 위해 접수 시점에 위키 기업명 사전과
    // 문자열 매칭으로 힌트를 뽑는다. LLM을 쓰지 않으므로 호출 수가 늘지 않고, 프리플라이트가
    // 큐 밖에서 돈다는 전제(§8.2)도 그대로다. 못 찾으면 None -- 억지로 추측하지 않는다(§8.2.3).
    let company_hint = wiki::match_known_company(wiki, &user_prompt);

    let (preprocessed, preflight_index) = tokio::join!(
        preprocessing::run(app, &user_prompt, &files),
        versioning::run_preflight(app, wiki, &user_prompt, company_hint.as_ref()),
    );
    let preprocessed = preprocessed?;
    let mut preflight_index = preflight_index?;

    // 라우팅 판단은 Taxonomy가 아니라 이사장 자신의 판단이다(사용자 결정, 4.3절).
    // chairman::decide_routing은 Taxonomy 모듈에 속하지 않고 이사장 모듈 소속 함수다.
    let classification = if chairman::decide_routing(&preprocessed, &user_prompt) == Routing::NeedsClassification {
        taxonomy::run(app, wiki, model, num_ctx, &preprocessed, &preflight_index).await?
    } else {
        ClassificationResult::from_standalone(
            research::run_standalone(app, wiki, model, num_ctx, &user_prompt, &preflight_index).await?
        )
    };

    // RD-01 2차 -- Taxonomy가 확정한 기업으로 티어 배정을 "재실행"한다(TD-07 정정:
    // 재분배가 아니다 -- 힌트 실패로 초기 티어에 못 들어간 확정 기업 페이지도 승격돼야 한다).
    // LLM 없는 인메모리 스캔이므로 비용이 사실상 없다(§8.2.3).
    versioning::rerank_after_taxonomy(wiki, &mut preflight_index, &classification.confirmed.company);

    // 검증 -> 승인 게이트 -> 재작업 루프(3회 상한, D3 §8) -> 최신화(사후) -> SalesCS
    // 정의는 바로 아래 §2.5 -- 호출과 정의를 같은 절 안에 붙여 둔다(RD-04 재발 방지).
    run_governance_pipeline(app, wiki, drafts, model, num_ctx, &intent, classification, cancel).await
}
```

#### 2.5.2 산출 단위(`TeamOutput`)의 개수 — 경로별 정리

D3의 재작업·부분 리포트는 `TeamRole` 단위로 카운트한다. v0.1.5.1에서 그 단위가 무엇인지
명시하지 않으면 상한 판정도 부분 리포트도 성립하지 않으므로 여기서 확정한다.

| 경로 | 산출 단위 | 개수 |
|---|---|---|
| Taxonomy 경유, 모호성 없음 | 분류·분석 산출 1건 | **1** |
| Taxonomy 경유, Research 위임 발생(§4.2) | 분류 산출 + Research 확정 산출 | **2** |
| Research 스탠드얼론(§4.3) | 조사 산출 1건 | **1** |

→ 검증·논리오류 검증은 **단위별로 리포트를 낸다**(두 구조체 모두 `team: TeamRole` 필드를
이미 갖고 있다). 게이트도 단위별로 판정하므로, 한 단위가 막혀도 나머지는 살아남는다.
**단위가 1개인 구성에서는 부분 리포트가 전부 플레이스홀더가 되므로** 리포트 대신 미결 안내로
축약한다(2.5.5 ③).

#### 2.5.3 게이트 판정 — 두 리포트의 집계 규칙

이사장은 여기서 **내용을 다시 읽지 않는다.** 판정은 이미 두 에이전트가 끝냈고, 이사장이 하는
일은 집계뿐이다(§2.2 "감으로 판단하지 않는다" + §7.3 "집계만 하면 된다").

| 입력 | 조건 | 결정 |
|---|---|---|
| `VerificationReport.fact_check` | `Contradicted` 1건 이상 | **반려** |
| `VerificationReport.fact_check` | `Unverifiable` | **반려 아님** — 신뢰도 하향으로 흡수(2.5.6 ①, 이행 지점은 §8.4 원자적 패키지 Step 2) |
| `VerificationReport.error_review` | 항목 1건 이상 | **재작성 지시** (TD-04, 사용자 확정 2026-08-02 — 최초 판은 이 항목을 집계에서 빠뜨렸다) |
| `VerificationReport.source_check` | `all_sources_traceable == false` | **재작성 지시** |
| `LogicFallacyReport.flags` | `SeverityVerdict::Reject` 1건 이상 | **반려** |
| `LogicFallacyReport.flags` | 전부 `RewriteRequest` 이하 | **재작성 지시** |
| `LogicFallacyReport.flags` | 전부 `NoteOnly` | 승인 진행(리포트에만 기록) |

**강한 쪽을 채택한다**: `반려` > `재작성 지시` > `승인`.

```rust
pub enum GateDecision {
    Approve,
    /// 전면 반려 대신 해당 문장만 다시 쓰게 한다(§7.3 RewriteRequest)
    Rewrite { target: TeamRole, reasons: Vec<String> },
    Reject  { target: TeamRole, reasons: Vec<String> },
}

/// LLM을 부르지 않는다 -- 3축 판정(§7.3)과 팩트 판정(§7.1)은 이미 끝난 상태로 도착한다.
/// 이사장이 여기서 LLM을 한 번 더 부르면 "근거 기반"이 아니라 3차 재판단이 되어 §2.2 위반이다.
pub fn aggregate_gate_decision(
    v: &VerificationReport,
    l: &LogicFallacyReport,
) -> GateDecision {
    debug_assert_eq!(v.team, l.team);   // 같은 산출 단위에 대한 두 리포트여야 한다
    let mut reject = Vec::new();
    let mut rewrite = Vec::new();

    // (1) 사실관계 -- 팩트 불일치는 무조건 반려. 기간만 달라도 Contradicted다(§7.1)
    for item in &v.fact_check {
        if item.verdict == FactVerdict::Contradicted {
            reject.push(format!("팩트 불일치: {}", item.claim));
        }
        // Unverifiable은 여기서 아무것도 하지 않는다 -- 2.5.6 ①
    }

    // (1b) 오류검수(TD-04, 사용자 확정 2026-08-02) -- 항목이 있으면 재작성 지시로 집계.
    // 심각도 축이 없는 자유 서술이라 전면 반려 근거로는 약하고, 기록만 하면 검증 3항목 중
    // 1항목이 게이트에서 무의미해진다. 26종 정밀 판정은 논리오류 에이전트 소관 그대로 --
    // 여기 항목은 "서술의 논리적 비약·모순 훑기"(D3 §5 (b))에서 걸린 것만 온다(경계 유지).
    rewrite.extend(v.error_review.iter().map(|e| format!("오류검수: {e}")));

    if !v.source_check.all_sources_traceable {
        rewrite.extend(v.source_check.flagged.iter().map(|f| format!("출처 불명/저작권 우려: {f}")));
    }

    // (2) 논리오류 -- verdict는 assess_severity()가 이미 계산해 넣어둔 값이다(§7.3)
    for flag in &l.flags {
        match flag.verdict {
            SeverityVerdict::Reject        => reject.push(format!("논리오류(반려): {:?} @ {}", flag.fallacy, flag.location)),
            SeverityVerdict::RewriteRequest => rewrite.push(format!("논리오류(재작성): {:?} @ {}", flag.fallacy, flag.location)),
            SeverityVerdict::NoteOnly      => {}   // 승인 진행, 리포트에만 남는다
        }
    }

    if !reject.is_empty()       { GateDecision::Reject  { target: v.team.clone(), reasons: reject } }
    else if !rewrite.is_empty() { GateDecision::Rewrite { target: v.team.clone(), reasons: rewrite } }
    else                        { GateDecision::Approve }
}
```

#### 2.5.4 결과 타입 — 취소를 정상 완료처럼 보이게 두지 않는다

`chair_process`가 `Result<String, String>`을 그대로 돌려주면 **취소·부분 완료·정상 완료가
전부 같은 `Ok(String)`** 이 된다. 이는 "조용히 틀리는" 유형(99 §4 패턴 3)이므로 결과를
열거형으로 구분한다.

```rust
/// 취소 시 "어디까지 갔는지" 통지에 쓴다(§5.4 -- "멈춘 단계까지 함께 통지")
pub enum PipelineStage {
    Preprocessing, Preflight, Classification,
    Verification, ApprovalGate, Rework, Versioning, Delivery,
}

pub enum GovernanceOutcome {
    /// 승인 -> 버전화 -> SalesCS 전달까지 정상 완료
    Delivered(String),
    /// 일부 단위가 재작업 상한에 걸려 미결 이관, 나머지만 전달(D3 §8.4)
    PartiallyDelivered { report: String, blocked: Vec<TeamRole> },
    /// 취소 -- 산출물 없음. request-cancelled는 이 시점에 이미 발행됐다(§5.4)
    Cancelled { at_stage: PipelineStage },
}
```

#### 2.5.5 본체

```rust
pub async fn run_governance_pipeline(
    app: &AppHandle,
    wiki: &WikiState,
    drafts: &DraftState,                // D-03 조치로 신설된 draft.json 저장소
    model: &str,
    num_ctx: u32,
    intent: &UserIntent,
    mut classification: ClassificationResult,   // mut -- 분류 단위 재작업 시 갱신된다(TD-06)
    cancel: &CancelToken,
) -> Result<GovernanceOutcome, String> {
    let mut outputs = classification.to_team_outputs();     // 2.5.2 -- 1개 또는 2개
    let mut history: HashMap<TeamRole, Vec<ReworkAttempt>> = HashMap::new();

    loop {
        // ── 취소 확인 ① 루프 진입부 ─────────────────────────────────────────
        if is_cancelled(cancel) {
            return finish_cancelled(drafts, cancel, PipelineStage::Verification, None);
        }

        // draft는 index.json이 아니라 draft.json에 쓴다(D-03 2저장소 분리).
        // 승인 전 산출물이 컨텍스트 조회 대상에 섞이면 자기오염이 된다.
        let draft = drafts.put(synthesize(app, model, num_ctx, &outputs).await?)?;

        // ── 취소 확인 ①-b 검증 진입부 (TD-12) ───────────────────────────────
        // 합성(LLM 1회) 중에 취소된 경우 여기서 멈춘다 -- 이 확인이 없으면 검증 한 라운드
        // (단위 수 × 2 호출)를 그대로 낭비한다. §5.4 "각 단계 진입부에서 확인"의 이행.
        if is_cancelled(cancel) {
            return finish_cancelled(drafts, cancel, PipelineStage::Verification, Some(&draft));
        }

        // ── 검증 2종 병렬 ───────────────────────────────────────────────────
        // 둘 다 내부에서 call_llm을 거치므로 run_lock이 알아서 순서를 매긴다.
        // 조율 함수인 이 함수는 run_queued를 직접 부르지 않는다(D-01 원칙).
        // 단위별 리포트를 내므로 반환은 Vec다(2.5.2).
        let (verifications, fallacy_reports) = tokio::join!(
            verification::run_all(app, model, num_ctx, &outputs, &draft),
            logic_fallacy_agent::run_all(app, model, num_ctx, &outputs, &draft),
        );
        let (verifications, fallacy_reports) = (verifications?, fallacy_reports?);

        // ── 취소 확인 ② 진행 중이던 LLM 호출이 끝난 직후 ──────────────────────
        // §5.4: 호출 자체는 끊지 않되 다음 단계로 넘어가지 않는다.
        if is_cancelled(cancel) {
            return finish_cancelled(drafts, cancel, PipelineStage::ApprovalGate, Some(&draft));
        }

        // ── 승인 게이트 (집계만, 2.5.3) ──────────────────────────────────────
        // run_all의 계약(§7.2): 단위당 리포트 정확히 1건, 만들지 못하면 전체 Err --
        // 조용한 누락 금지(TD-10, D-08 정신). 아래 expect는 계약 위반의 표시일 뿐
        // 정상 경로에서 도달하지 않는다.
        let decisions: Vec<GateDecision> = outputs.iter()
            .map(|o| aggregate_gate_decision(
                verifications.iter().find(|v| v.team == o.team).expect("단위별 리포트 누락"),
                fallacy_reports.iter().find(|l| l.team == o.team).expect("단위별 리포트 누락"),
            ))
            .collect();

        if decisions.iter().all(|d| matches!(d, GateDecision::Approve)) {
            // ── 취소 확인 ③ 버전화 진입부 ────────────────────────────────────
            if is_cancelled(cancel) {
                return finish_cancelled(drafts, cancel, PipelineStage::Versioning, Some(&draft));
            }
            // 검증 리포트를 함께 넘긴다(TD-03) -- confidence_adjustment가 승격 시점의
            // 메타데이터 확정 기입(§8.4 원자적 패키지 Step 2)에 반영된다. 안 넘기면
            // §2.5.6 ①("하향 흡수")이 약속으로만 남아 Unverifiable 콘텐츠가 Stated로 저장된다.
            let versioned = versioning::run_post_approval(app, wiki, &draft, &classification, &verifications).await?;
            drafts.promote(&draft, &versioned)?;             // draft.json -> index.json (D-03, 원자적 패키지는 §8.4)

            // ── 취소 확인 ④ 전달 진입부 ─────────────────────────────────────
            // 여기서 취소되면 위키 반영은 이미 끝났으므로 draft 폐기 대상이 없다.
            if is_cancelled(cancel) {
                return finish_cancelled(drafts, cancel, PipelineStage::Delivery, None);
            }
            let report = deliver_via_salescs(app, wiki, model, num_ctx, intent, &versioned).await?;
            return Ok(GovernanceOutcome::Delivered(report));
        }

        // ── 재작업 (D3 §8.1) ────────────────────────────────────────────────
        // 반려·재작성 지시를 구분하지 않고 같은 카운터에 넣는다 -- 2.5.6 ②.
        // 카운트는 "팀 단위 무조건 합산"이다(TD-11, 사용자 확정 2026-08-02) -- D3 §8.1
        // prose의 "사유 유사성" 조건은 채택하지 않는다. 유사성 판정 자체가 또 하나의
        // LLM 판단이 되고, 매번 새 사유가 나오는 무한 루프는 막지 못하기 때문이다.
        // 합산은 4번째에서 반드시 종결시킨다.
        //
        // ⚠ 상한 분기를 순회 "중간에" 반환하면 안 된다(TD-01) -- 이번 회차 전 단위의
        // 판정을 먼저 확정한 뒤 분기해야, 판정을 보지도 않은 단위를 버전화하는 일이 없다.
        let mut approved_now: Vec<TeamRole> = Vec::new();
        let mut redo_targets: Vec<(TeamRole, Vec<String>)> = Vec::new();
        let mut blocked_team: Option<TeamRole> = None;

        for (unit, d) in outputs.iter().zip(decisions) {
            match d {
                GateDecision::Approve => approved_now.push(unit.team.clone()),
                GateDecision::Reject { target, reasons } | GateDecision::Rewrite { target, reasons } => {
                    let attempts = history.entry(target.clone()).or_default();
                    attempts.push(ReworkAttempt {
                        team: target.clone(),
                        reason: reasons.join(" / "),
                        attempt_no: attempts.len() as u32 + 1,
                    });
                    if attempts.len() as u32 > REWORK_LIMIT {
                        blocked_team = Some(target);   // 3회 재작업 후 4번째 -> 이관 대상
                    } else {
                        redo_targets.push((target, reasons));
                    }
                }
            }
        }

        if let Some(blocked) = blocked_team {
            // 3회 재작업 후 4번째도 같은 단위에서 걸림 -> 미결 이관, 루프 종료
            save_pending_work(app, intent, &blocked, &history[&blocked]).await;

            // TD-01 조치(사용자 확정 2026-08-02): 버전화는 "이번 회차 Approve" 단위만.
            // 재작업 대기(redo_targets) 단위는 승인된 적이 없으므로 버전화하지 않고
            // "재작업 중 중단" 플레이스홀더로 표시한다 -- 상한에 걸린 것이 아니므로 미결
            // 이관도 하지 않는다. D3 §8.4의 "이미 검증·승인된 결과만"이 여기서 처음
            // 코드로 강제된다.
            //
            // D3 §8.4: synthesize를 다시 돌리지 않는다 -- 기존 draft에서 해당 단위
            // 섹션만 플레이스홀더로 치환한다(추가 LLM 호출 없음).
            let report = if approved_now.is_empty() {
                // 버전화할 단위가 하나도 없다 -- 2.5.6 ③("단위 1개" 케이스)의 일반형
                build_blocked_notice(intent, &blocked, &redo_targets)
            } else {
                build_partial_report(app, wiki, model, num_ctx, intent, &draft, &outputs,
                                     &approved_now, &verifications,   // 부분 경로의 버전화도 Step 2를 지난다(TD-03)
                                     &blocked, &redo_targets).await?
            };
            drafts.discard_draft(&draft)?;   // 리포트 구성이 draft를 읽으므로 폐기는 그 뒤다(TD-08)
            return Ok(GovernanceOutcome::PartiallyDelivered { report, blocked: vec![blocked] });
        }

        for (target, reasons) in redo_targets {
            let redo = rerun_producer(app, wiki, model, num_ctx, &target, &reasons).await?;
            // 분류 단위가 재작업된 경우 classification도 함께 갱신한다(TD-06) -- 그대로
            // 두면 사후 버전화·링킹(§8.1)이 옛 분류를 근거로 관계를 만든다(silent stale).
            if let Some(updated) = redo.classification_update() {
                classification = updated;
            }
            outputs.retain(|o| o.team != target);
            outputs.push(redo);
        }
        drafts.discard_draft(&draft)?;   // 이번 회차 draft는 폐기하고 다음 회차에서 다시 만든다
    }
}

/// 취소 마무리 -- 중간 산출물 폐기·정리 전담. §5.4의 "위키에도 draft에도 남기지 않는다".
/// request-cancelled 이벤트는 여기서 발행하지 않는다(TD-05 정정) -- 발행은 취소를 "접수한"
/// 시점에 이사장 커맨드 핸들러가 이미 했다(§5.4). 체크포인트에서 발행하면 진행 중이던 LLM
/// 호출이 끝날 때까지 사용자가 아무 알림도 못 받아 §5.4의 "즉각 알림"이 깨진다.
fn finish_cancelled(
    drafts: &DraftState,
    cancel: &CancelToken,
    stage: PipelineStage,
    draft: Option<&DraftHandle>,
) -> Result<GovernanceOutcome, String> {
    if let Some(d) = draft { drafts.discard_draft(d)?; }
    Ok(GovernanceOutcome::Cancelled { at_stage: stage })
}
```

| # | 판단 | 근거 |
|---|---|---|
| ① | **`Unverifiable`은 반려 사유가 아니다** — `confidence_adjustment`로 흡수 | 위키가 비어 있는 초기에는 거의 모든 주장이 `Unverifiable`이라 반려하면 파이프라인이 아무것도 통과시키지 못한다. §2.4 "근거 없는 것은 단정하지 않는다"는 **신뢰도를 낮추라는 뜻이지 버리라는 뜻이 아니다** |
| ② | **재작성 지시도 반려와 같은 카운터에 합산** | 따로 세면 `RewriteRequest`만 반복되는 무한 루프가 가능하다. §7.3이 신설되며 생긴 공백 — D3는 반려 한 종류만 있었다 |
| ③ | **산출 단위가 1개면 부분 리포트 대신 미결 안내** | 하나뿐인 단위가 막히면 부분 리포트가 전부 플레이스홀더가 되어, 사용자에게 빈 리포트를 산출물인 것처럼 건네게 된다 |
| ④ | **게이트 판정 대상은 산출 단위(`TeamRole`)** | D3의 상한 카운트가 팀 단위인데 v0.1.5.1에 팀 개념이 남아 있는지 불명확했다. 2.5.2에서 경로별 개수를 확정해 해소 |
| ⑤ | **취소 알림에 "진행 중 작업 완료 후 중단" 명시** (RD-07 해소) | Ollama 호출을 끊지 않으므로 `run_lock`이 잠시 더 점유된다. 알림에 이 사실이 없으면 "취소했는데 왜 안 멈추지"가 된다. **발행 시점은 접수 시점**(TD-05 정정, §5.4) |
| ⑥ | **`Rewrite`와 `Reject`는 파이프라인 동작이 동일** — 단위 전체 재실행 + 같은 카운터, 차이는 재작업 지시문뿐 (사용자 확정 2026-08-02) | 국소 문장 재작성 경로를 따로 만들면 경로가 둘이 되고, 부분 수정본이 앞뒤 맥락과 어긋날 위험이 생긴다. 어차피 재검증이 뒤따르므로 품질 게이트는 동일하다 |

> **미해소로 남긴 것**: `synthesize`·`rerun_producer`의 프롬프트 구성, `stage_label`의 사용자
> 표기 문구는 구현 단계에서 정한다. 파이프라인 **구조**는 이 절로 닫혔다.

### 3.1 설명 (개정)

> **이전 설명(D2)**: "① 뉴스 수집/모니터링팀 — 사용자 제공 원문 정리(크롤링 없음)"

## 4. Taxonomy ★ (+ 하위 Research)

### 4.1 3단계 분류 프로세스 (1단계 확정 — 사용자 제공 목록 반영)

> **개정 이력**: 최초에는 §0 목적(G-1~G-4)에 맞춰 잠정 제안 → 표준 정책분야 16종으로 1차 확정
> → **이번에 한국표준산업분류(KSIC) 대분류 체계로 전면 교체**(2026-07-26). 정책분야 16종은
> 폐기한다. 2·3단계는 아래 4.1.2에서 구조가 바뀌었다.

#### 4.1.1 1단계(대분류) — 산업분류로 교체 확정

> **표준 코드 기준 (2026-07-26 확정)**: 본 시스템의 `IndustrySection` 표준 코드는 **KSIC 11차
> (2024년 개정)를 따르며**, 10차 데이터 수집 시 10차–11차 연계표를 통해 **변환·보존**한다.

기존 정책분야 16종(공공행정·과학기술·교육 등)을 폐기하고, **한국표준산업분류 대분류**(사업 부문,
A~S 중 18개 섹션)로 교체한다.

> ✅ **D-14 검증 완료 (2026-07-26)**: 통계청 『제11차 기준 한국표준산업분류 실무 적용 가이드북』
> (2025-01) 원문과 대조했다. **중분류 코드 범위는 전 항목 일치**하며, 대분류 명칭 5건을 공식

> 외국기관, 99)를 제외한 **18개**만 사용한다 — 분석 대상이 기업이므로 비사업 부문은 제외한다.

#### 기준 차수 — KSIC **11차**로 통일 (사용자 결정, 2026-07-26)

한국표준산업분류는 개정 차수마다 코드 체계가 달라진다. 입력 문서(PDF·공시자료)에 10차와 11차가
섞여 들어오면 매핑이 꼬이므로, **11차를 유일한 기준 표준으로 삼는다.**

**적용 원칙**

| 원본 표기 | 처리 | `converted` |
|---|---|---|
| 11차 코드가 있음 | 즉시 사용 (변환 없음) | `false` |
| 10차 코드만 있음 | 10차 → 11차 연계표 적용 | `true` |

> ✅ **O-36-1 종료**: 위 검증으로 해소되었다. 중분류 코드 범위가 전부 일치했으므로 **기존 표는
> 10차가 아니라 11차 계열이었고**, 어긋난 것은 대분류 명칭 표기뿐이었다(H 섹션 1건 + 띄어쓰기 4건).

**혼재 입력 처리**: 원본이 10차로 표기된 경우 11차로 변환해 저장하되, **원본 차수를 함께
보존**한다 — [09 §2.5](09_재무수치_정의.md)에서 금액 단위를 정규화하면서 `source_scale`을
남긴 것과 같은 방식이다(정규화하되 출처를 잃지 않는다).

```rust
pub enum KsicRevision { Tenth, Eleventh }

pub struct IndustryClassification {
    /// 11차 기준으로 정규화된 값 -- 비교·집계는 항상 이 값으로 한다.
    pub section: IndustrySection,
    /// 원본 문서가 사용한 차수 (추적용)
    pub source_revision: KsicRevision,
    /// 10차 -> 11차 변환이 일어났는지. true면 변환표를 거친 값이라 검증 시 참고한다.
    pub converted: bool,
}
```

> [12 §2](12_기업정보_지표체계.md)에서 확인했듯 참조 자료는 **표준산업분류 10차와 11차를 모두
> 보관**한다. 두 값이 원본에 함께 있으면 변환할 필요 없이 11차 값을 그대로 쓰면 되므로,
> 변환표는 11차 표기가 없는 자료에만 적용된다.

**교체 이유**: 이 시스템의 분류 대상은 정책 문서가 아니라 **기업**이다(§0 목적 G-1~G-4). 정책분야
16종은 대상 문서 대부분이 "재정금융/산업고용" 두 칸에 몰려 분류로서 변별력이 거의 없었던 반면,
산업분류는 대상 기업이 어느 산업에 속하는지를 그대로 표현하므로 분류 축과 분석 목적이 일치한다.
또한 재무제표(G-2)·뉴스 키워드(G-3)를 산업별로 비교·집계하는 것이 자연스러워진다.

> 위 목록은 공공행정(O)·가구내 고용활동(T)·국제 및 외국기관(U)을 제외한 사업 부문 18개 섹션이다
> — 분석 대상이 기업이므로 비사업 부문은 제외한다.

#### 4.1.2 2단계(기업)는 1단계를 복수로 가질 수 있다 — 구조 변경

**사용자 결정 (2026-07-26)**: 2단계는 기업이며, **하나의 기업이 1단계 산업분류를 1개, 2개, 또는
그 이상 가질 수 있다.** 기업은 단일 산업에만 속하지 않기 때문이다(예: 제조업이면서 정보통신업,
도소매업을 겸하는 기업).

이는 단순한 값 변경이 아니라 **자료 구조의 변경**이다 — 기존 3단계 분류는 "1단계 하나 → 2단계
하나 → 3단계 하나"의 단일 경로 트리였으나, 이제 2단계(기업)가 여러 1단계(산업)에 동시에 속하는
**다중 부모 구조**가 된다.

| 단계 | 내용 | 개수 |
|---|---|---|
| 1단계 | 산업 대분류 (KSIC A~S) | **1개 이상 (복수 허용)** |
| 2단계 | 기업 | 1개 |
| 3단계 | **옵션 집합** (분류 아님 — 4.1.3 참고) | 그룹별 단일/복수, 해당 없으면 비움 |

pub struct ClassificationResult {
    pub confirmed: ClassificationCandidate,              // Research가 확정한 1개
    pub alternative_tags: Vec<ClassificationCandidate>,  // 모호성으로 탈락한 후보만 태그로 강등
}
```

`industries`를 단일값에서 `Vec`으로 바꾼 것이 이번 개정의 핵심 구조 변화다. 이에 따라 §2.4
저장소의 인덱스는 **하나의 기업 페이지가 여러 산업 인덱스에 동시에 등장**하게 되며, 산업 단위
검색(예: "제조업 기업들의 최근 이슈")이 자연스럽게 가능해진다.

#### 주력 산업 판정 — 매출 비중 기반 (O-42 확정, 2026-07-26)

복수 산업 소속을 허용하면서 남았던 문제 — **"그중 어느 것이 대표 산업인가"** — 를 참조 자료의
매출액구성비(%)로 해결한다(12 §9.2). 정성적 추측이 아니라 **정량 수치**를 근거로 삼는다.

```rust
pub struct WeightedIndustry {
    pub section: IndustrySection,
    /// 매출액구성비(%). 참조 자료의 매출구성 단락에서 확보한다.
    /// 비중 정보가 없으면 None -- 아래 폴백 규칙 적용.
    pub revenue_share: Option<f64>,
}
```

**판정 규칙**

| 상황 | 처리 |
|---|---|
| 매출 비중 정보 있음 | **비중 1위 산업**을 `primary_industry`로 자동 지정 |
| 비중 정보 없음 (비상장·소형사) | 비중 없이 저장하되, **DART 메인 표기 산업을 1순위로 폴백** |

이로써 **D-08 조치안 ④의 구현 차단이 해제된다** — 제목 중복 시 `영업이익률(제조업)`처럼 구분자를
붙일 때 "관련도 최상위 산업"을 실제로 계산할 수 있게 되었다. 그전까지는 규칙만 있고 판정 근거가
없었다.

#### 4.1.3 3단계는 분류가 아니라 "옵션"이다 — 성격 변경

**사용자 결정 (2026-07-26)**: 3단계는 분류(classification)가 아니라 **옵션(option)** 으로 정의한다.
1·2단계가 "이 대상이 어디에 속하는가"를 정하는 것이라면, 3단계는 **해당 기업에 해당되는 속성을
필요한 만큼 붙이는 태그 집합**이다.

상세 목록과 그룹별 단일/복수 선택 방식은 별도 문서로 분리한다 →
**[07_기업_옵션_정의.md](07_기업_옵션_정의.md)** (**14개 그룹**: 법인격·규모·생애주기·매출구간·
기술수준(기업/업종)·공업구분·업종성격·기업특성·협동조합유형·지식재산권·인증·협회소속(26종)·
관련기관(56종)).

> **정합성 정정 (재워크스루 §4 #1, 2026-08-02)**: 세목 10종은 O-18 결정으로 **기업 옵션에서
> 제외**되어 문서 속성(`DocumentTags.tax`, §8.4)으로 옮겨졌다. 그런데 이 목록은 15개 그룹으로
> 남아 세목을 계속 포함하고 있었다 — **14개 그룹**으로 정정한다.

이 성격 변경이 §4.2 모호성 처리에 미치는 영향:

| 단계 | 모호성 처리 적용 여부 |
|---|---|
| 1단계 (산업) | 적용 — 단, "정당한 복수 소속"과 구분 필요(4.2절) |
| 2단계 (기업) | 적용 — 어느 기업 얘기인지 불분명하면 Research 위임 |
| **3단계 (옵션)** | **적용 안 함** — 옵션은 "해당되면 붙이고 아니면 안 붙이는" 것이므로 "후보가 여럿이라 하나를 골라야 하는" 상황 자체가 성립하지 않는다. 단일 선택 그룹(예: 생애주기) 안에서 판단이 어려우면 그냥 비워둔다(`None`) |

> 옵션을 **비워두는 것이 정상 상태**라는 점이 중요하다 — 뉴스 원문 한 건에서 기업의 매출 구간이나
> 협회 소속을 알 수 없는 것이 당연하므로, 채우지 못한 옵션을 억지로 추측해 채우지 않는다.
> 이는 §2.4 신뢰도 등급의 "근거 없는 것은 단정하지 않는다" 원칙과 같은 방향이다.

### 4.2 모호성 처리 — Research로 위임 (판정 기준 개정)

> **O-14 해결 (사용자 확정, 2026-07-26)**: "1단계 후보가 여럿"이 두 가지 다른 의미를 갖던 문제는
> **판정 규칙이 아니라 필드 분리로 해결**했다(4.1.2). 하나의 `industries`에 서로 다른 두 질문의
> 답을 담고 있던 것이 원인이었으므로, 나누고 나니 구분 기준을 새로 만들 필요가 없어졌다.

| 상황 | 어느 필드의 문제인가 | 처리 |
|---|---|---|
| **정당한 복수 소속** (제조업 + 정보통신업) | `company_industries` | **모호성이 아니다.** OpenDART에서 조회한 값을 모두 담는다. Research를 부르지 않는다 |
| **문서 맥락 모호** (이 기사가 어느 산업 얘기인지 불명) | `document_industry` | 확정 가능하면 채우고, **확신이 없으면 `None`으로 비워둔다** |

**비워두는 것이 정상 상태다.** §2.4의 "근거 없는 것은 단정하지 않는다"에 따라, 문서 주제를
확정하기 어려우면 새 규칙을 만들어 억지로 채우지 않고 비워두는 것이 가장 안전하다
(07 §0의 "옵션은 비워두는 것이 정상"과 같은 정신).

#### 두 필드 불일치 = lint 탐지 신호 (신규)

필드를 나눈 부수 효과로, **`document_industry`가 `company_industries`에 없는 값일 때**를 자동
검사할 수 있게 되었다. 예: 삼성전자 기사인데 문서 주제가 부동산업으로 판정된 경우.

| 가능성 | 의미 | 후속 조치 |
|---|---|---|
| A | AI가 문서 맥락을 잘못 판정함 | 판정 재검토 |
| B | 해당 기업이 실제로 신사업에 진출함 | DART 정보 갱신 필요 |
| C | 동명의 다른 기업임 (기업 식별 오류) | corp_code 재확인 |

셋 중 어느 쪽이든 **점검할 가치가 있는 신호**이므로 §2.6 lint의 탐지 항목으로 추가한다.
자동으로 오류 판정하지 않고 사람이 확인하도록 신고만 한다 — 세 가능성 중 어느 것인지는
시스템이 판별할 수 없기 때문이다.

#### 여전히 Research에 위임하는 경우

`document_industry`를 정하기 어렵되 후보를 좁힐 수는 있는 경우(점수가 비슷한 후보들이 경합)는
기존대로 Research에 위임한다. 위임된 경우의 처리도 기존과 동일하다.

- Research는 후보들 중 **가장 근거가 확실한 1개를 최종 분류로 확정**한다.
- 확정되지 않은 나머지 후보들은 삭제되지 않고 **태그(`alternative_tags`)로 보존**된다 — 나중에
  "이 문서, 사실 이 카테고리로도 찾아볼 수 있지 않을까"라는 재발견을 가능하게 한다.
- 이 판단은 §2.4 저장소의 **신뢰도 등급** 체계와 연동된다 — 확정 분류는 `Stated`에 준하고,
  태그로 남은 후보는 `Uncertain`에 준하는 취급을 받는다(명시적 재정의는 아니고 유사한 정신).

> **미결(신규 O-14)**: "정당한 복수 소속"과 "모호성"을 Taxonomy가 무엇을 근거로 구분할지는
> 아직 정하지 않았다. 매출 비중·사업보고서상 주력 업종 표기 등이 후보이나, 뉴스 원문처럼 그런
> 근거가 없는 입력에서는 판정이 어렵다.

### 4.3 Research — 하위 에이전트이자 스탠드얼론

```rust
pub enum ResearchInvocation {
    /// Taxonomy가 분류 모호성 해소를 요청한 경우
    ViaTaxonomy { candidates: Vec<ClassificationCandidate> },
    /// 이사장이 Taxonomy를 거치지 않고 직접 요청한 경우
    Standalone { request: String },
}
```

**두 경로 모두 검증→승인 게이트를 동일하게 거친다** — 거버넌스(검증·승인·버전화)는 산출 경로가
무엇이든 동일하게 적용된다는 것이 이번 통합에서 새로 확정한 원칙이다(⚠ 확인 필요 — 사용자가
명시하지 않아 본 문서에서 채운 설계 판단).

**스탠드얼론 호출 조건 — 판단 주체 확정 (사용자 결정, 2026-07-26)**: 이 판단은 Taxonomy나
Research가 스스로 내리는 것이 아니라 **이사장 자신의 판단**이다. 즉 "분류가 필요한 요청인가?"는
이사장이 사용자 프롬프트를 접수한 시점에 스스로 결정하는 라우팅 권한의 일부이며, Taxonomy 모듈에
속한 함수(`taxonomy::needs_classification` 같은 형태)로 두지 않는다 — 이사장 모듈 소속의
`chairman::decide_routing`으로 소유권을 명시한다(2.4절 `chair_process` 코드 갱신 참고).

판단 기준 자체는 여전히 아래로 제안한 상태다(⚠ 확인 필요 — 판단 주체는 확정됐으나 구체 기준은
그대로임):
- 새로 유입된 원본 자료가 없고(즉 전처리부 산출물이 비어 있거나 이미 분류된 기존 자료만 참조),
- 요청이 이미 알려진 대상(예: 특정 기업)에 대한 **순수 분석/질의**일 때(예: "삼성전자 재무 분석해줘")

반대로 신규 원본 자료가 유입되어 분류가 필요한 경우엔 반드시 Taxonomy를 먼저 거친다.

```rust
pub enum Routing { NeedsClassification, StandaloneResearch }

/// 이사장(Chairman) 모듈 소속 -- Taxonomy·Research 어느 쪽 코드에도 두지 않는다.
/// 이사장이 "팀 소집의 주체"(§0 이번 개정 요약)라는 역할의 연장선이다.
pub mod chairman {
    pub fn decide_routing(preprocessed: &PreprocessedInput, user_prompt: &str) -> Routing { .. }
}
```

## 5. Platform

### 5.1 역할 (개정 — 신규 기능 + 기존 역할 유지)

Platform은 이번 개정으로 **상시 관찰자** 성격이 명확해졌지만(파이프라인의 순차 단계가 아님),
D2·D3에서 이미 부여된 기존 역할 3가지를 **대체하는 것이 아니라 그대로 유지한 채 추가**된다.
즉 Platform의 전체 업무는 아래 4가지다.

| # | 업무 | 신규/기존 | 근거 |
|---|---|---|---|
| 1 | **통신 카탈로그·로그 정리 + 통계 기반 품질관리** — 이사장으로 연결되는 모든 통신(전처리부·Taxonomy·Research·검증·최신화·버전관리·SalesCS ↔ 이사장)을 발신자·수신자·목적이라는 **프레임워크만 고정**하고, 실제 유형 가짓수는 제한 없이 무제한 누적 기록한 뒤 통계를 내 품질관리에 활용 | 신규 | 이번 개정(수정) |
| 2 | ~~라우터 규칙 관리~~ → **라우터 동작 관찰** | **변경**(2026-07-26) | 라우터가 최신화·버전관리 에이전트에 흡수(8.2.1)되면서 규칙 정의·실행 주체가 그쪽으로 넘어갔다. Platform에는 **결과 관찰**만 남는다 — 통신로그 통계로 "제외(`excluded`)가 잦은 질의 유형"을 탐지해 예산 배분 규칙의 개선 신호를 잡는 역할 |
| 3 | **lint 스코프 관리** — `wiki::lint`가 기업/주제 스코프를 인지하지 못해 서로 다른 대상을 모순으로 오탐하지 않도록 스코프 규칙 관리 | 기존 유지 | D2 §5 ④, D-14 |
| 4 | **미결작업.md 정기 점검** — 재작업 상한(3회)에 걸려 이관된 항목들을 §2.6 유지보수 주기에 맞춰 점검 | 기존 유지 | D3 §8.3 |
| 5 | **컨텍스트 예산 재점검** — `num_ctx` 상한이 여전히 유효한지 주기적으로 확인. 모델·양자화 변경, 드라이버·Ollama 버전 변경, 상시 점유 앱 변화로 VRAM 여유가 달라진다 | **신규**(2026-07-26) | [11_컨텍스트_예산_진단.md](11_컨텍스트_예산_진단.md) §5 |

### 5.3 유지보수 주기 — 2-Track (D-7 확정, 2026-07-26)

Platform의 업무는 **LLM을 쓰는 것과 안 쓰는 것**으로 성격이 갈린다. 하나의 주기로 묶으면
비용이 큰 쪽에 맞춰 전체가 느려지거나, 싼 쪽에 맞춰 비용이 폭증한다. **두 트랙으로 분리**한다.

| 트랙 | 주기 | 포함 업무 | LLM |
|---|---|---|---|
| **경량(Daily)** | 앱 시작 시 + **1일 1회** | ① 통신로그 통계 ② 미결작업.md 점검 ③ 라우터 결과 관찰(`excluded` 빈도) | ❌ 없음 (알고리즘 집계) |
| **중량(Weekly)** | **주 1회** 또는 사용자 수동 실행 | ④ lint 스코프 점검(모순·고아 문서·누락 개념) | ✅ 사용 |

**이 분리로 닫히는 것들**

| 항목 | 해소 내용 |
|---|---|
| 라우터 결과 관찰 | 매일 쌓이는 통계이므로 Daily 편입 → **개선 신호 유실 없음** |
| 미결작업 점검 | 부하가 거의 없어 앱 시작 + Daily → **작업 방치 리스크 해제** |
| 통신로그 통계 | DB 집계 수준이라 Daily → **로그 누적·오염 방지** |
| lint 스코프 점검 | 독립 Weekly/수동 트랙 → **비용 예측 가능(Predictable Cost)** |

> lint만 분리한 것이 핵심이다. 나머지 셋은 LLM 없이 도는 집계라 매일 돌려도 부담이 없지만,
> lint는 위키 전체를 모델에 태우므로 주기를 짧게 잡으면 비용이 그대로 곱해진다.

4가지 모두 **요청 경로(실시간 파이프라인)에는 참여하지 않는다** — 1번(통신 로그 수집)은 각
호출 지점에 얇게 심어 수동 개입 없이 상시 기록되고, 2~4번은 §2.6 유지보수 주기에 맞춰 주기적으로
실행된다는 점에서 성격이 같다. 이번 개정 이전에는 2~4번만 있었고, 이번에 1번이 추가된 것으로
이해하면 된다.

### 5.2 통신 유형 카탈로그 — 프레임워크 확정, 개수 무제한 (사용자 결정, 2026-07-26)

> "최대 50종"이라는 상한을 폐기한다. 발신자(from)·수신자(to)·목적(purpose) 3축의

## 5.4 취소 경로 (D-6 / O-3 확정, 2026-07-26)

**취소 단위는 "요청 전체"다.** 개별 LLM 호출만 끊는 것이 아니라 **파이프라인을 통째로 중단**한다.

**근거**: 사용자가 체감하는 단위는 "삼성전자 분석"이라는 요청 하나이지 그 안의 개별 호출이
아니다. 호출 하나만 취소하면 파이프라인이 다음 단계로 넘어가 계속 돌아, 사용자 입장에선
"취소했는데 왜 안 멈추지"가 된다.

```rust
pub struct CancelToken {
    pub request_id: u64,
    flag: Arc<AtomicBool>,
}

/// 파이프라인의 각 단계 진입부에서 확인한다. 취소되었으면 즉시 중단하고
/// 진행 중이던 작업 결과는 버린다(draft.json에도 남기지 않는다).
pub fn is_cancelled(token: &CancelToken) -> bool { .. }
```

- 각 단계(전처리 → Taxonomy/Research → 검증/논리오류검증 → 승인 → 최신화 → SalesCS) **진입 시점**에
  확인한다. 진행 중인 LLM 호출 자체를 강제 중단하지는 않고, **그 호출이 끝나면 다음 단계로
  넘어가지 않는다** — Ollama 요청을 중간에 끊으면 모델 상태가 불안정해질 수 있어서다.
- 취소 시 중간 산출물은 **위키에도 draft에도 남기지 않는다.** 미완성 분석이 나중에 근거로
  재사용되면 D-03(자기오염)과 같은 문제가 된다.

### ⚠ 사용자 즉각 알림 — "유일한 엔드포인트" 원칙의 예외

**문제**: §6에서 *"다른 어떤 에이전트도 사용자에게 직접 응답하지 않는다"* 고 못박았는데,
취소는 SalesCS까지 도달하기 전에 발생한다. 원칙을 그대로 적용하면 **취소 사실을 알릴 경로가 없다.**

**조치**: 취소 알림을 이 원칙의 **명시적 예외**로 둔다.

| 구분 | 경로 | 근거 |
|---|---|---|
| **산출물** 전달 | 반드시 SalesCS 경유 | §6 원칙 유지 |
| **시스템 이벤트**(취소·오류) | 이사장이 직접 통지 | SalesCS는 `UserIntent`에 맞춰 **산출물을 재처리**하는 역할인데, 취소에는 재처리할 산출물이 없다 |

```rust
/// 취소를 "접수한" 즉시 이사장 커맨드 핸들러가 발행한다(TD-05 정정, 2026-08-02).
/// 파이프라인 체크포인트(finish_cancelled)에서 발행하면 진행 중 LLM 호출이 끝날 때까지
/// 알림이 안 나가 "즉각 알림"이 깨진다 -- 최초 판은 발행 지점을 finish_cancelled로
/// 통일했다가 3차 트레이스에서 이 모순이 확인되었다. 접수 시점의 "현재 진행 단계"가
/// 곧 멈출 단계이므로(체크포인트는 항상 진행 중 호출 직후다) 단계 통지도 접수 시점에
/// 가능하다. finish_cancelled()는 산출물 폐기·정리만 전담한다(§2.5.5).
app.emit("request-cancelled", json!({
    "request_id": id,
    "cancelled_at_stage": "verification",   // 접수 시점의 진행 단계 = 멈출 단계
    // RD-07 해소(2026-08-02): 자원 해제가 즉시가 아니라는 사실을 문구에 넣는다
    "note": "진행 중이던 작업이 끝난 뒤 중단됩니다. 다음 요청은 그때부터 처리됩니다.",
}))?;
```

- 웹 UI: 이벤트 수신 즉시 표시 (📋 큐 패널의 해당 항목도 함께 제거)
- 텔레그램: 취소 사실을 메시지로 통지 — 사용자가 앱 화면을 보고 있지 않을 수 있으므로 **양쪽 모두** 발행한다
- **어느 단계에서 멈췄는지 함께 알린다** — "취소됨"만 보내면 얼마나 진행됐는지 알 수 없어,
  다시 요청할지 판단할 근거가 없다
- **"즉시 멈추지 않는다"는 사실도 함께 알린다** (RD-07): 진행 중이던 Ollama 호출은 끊지 않으므로
  그 호출이 끝날 때까지 `run_lock`이 점유된다. 알림에 이 사실이 없으면 사용자는 "취소했는데 왜
  다음 요청이 안 되지"로 받아들인다 — **알림은 즉시, 자원 해제는 지연**이라는 두 시점 차이를
  문구가 설명해야 한다
- **버전화가 끝난 뒤의 취소는 문구가 다르다** (TD-05): §2.5.5 취소 확인 ④ 시점에는 승인·버전화된
  결과가 **이미 위키에 반영**되어 있다 — 승인·버전화 완료분은 "중간 산출물"이 아니므로 되돌리지
  않으며, 문구는 "분석 결과는 위키에 반영되었고, 전달만 중단되었습니다"로 분기한다

## 6. SalesCS — 이사장의 유일한 엔드포인트

### 6.1 역할 (개정)

- 이사장이 사용자 요청을 접수하는 시점에 기록한 `UserIntent`(2.4절)를 그대로 물려받아 보관한다.
- 검증→승인→최신화·버전관리를 모두 통과한 **확정 산출물**을 입력으로 받는다(D3 §7 그대로 유지 —
  draft가 아니라 버전화된 확정본만 다룸).
- 확정 산출물을 `UserIntent.desired_output`(간단 요약 / 상세 리포트 / 엑셀 등)에 맞춰
  **재처리**한 뒤에만 사용자에게 반환한다.
- **다른 어떤 에이전트도 사용자에게 직접 응답하지 않는다** — 이사장 승인 게이트를 통과한
  산출물이라도, 반드시 SalesCS를 거쳐야 사용자에게 나간다. 이는 §2.3에서 정의한 "유일한
  엔드포인트"의 실질적 강제 규칙이다.
  - **예외: 시스템 이벤트**(취소·오류 통지)는 이사장이 직접 발행한다(§5.4). SalesCS는
    `UserIntent`에 맞춰 **산출물을 재처리**하는 역할인데, 취소에는 재처리할 산출물이 없기
    때문이다. **산출물은 예외 없이 SalesCS 경유**라는 원칙 자체는 그대로 유지된다.

```rust
pub async fn deliver_via_salescs(
    app: &AppHandle,
    wiki: &WikiState,
    model: &str,
    num_ctx: u32,
    intent: &UserIntent,
    versioned: &VersionedOutput,
) -> Result<String, String> {
    let reformatted = match intent.desired_output {
        Some(OutputFormat::Excel) => excel::export(versioned)?,      // D1 §4.4
        Some(OutputFormat::Brief) => summarize_for_brief(app, model, num_ctx, versioned).await?,
        Some(OutputFormat::DetailedReport) | None => format_detailed(versioned),
        Some(OutputFormat::Unspecified) => format_detailed(versioned),
    };
    Ok(reformatted)
}
```

## 7. 검증 (Verification) + 논리오류 검증 (신규 — 독립 에이전트로 분리)

> **사용자 결정 (2026-07-26)**: 검증 에이전트에 있던 "4대 논리적 오류" 체크리스트를 **폐기**한다.
> 대신 [06_논리적_오류_정의.md](06_논리적_오류_정의.md)에 정의된 목록(형식적/비형식적(귀납·심리·
> 언어·자료) 오류 총 26종 + 분류 체계 7종)을 검출 대상으로 삼는 **논리오류만 전담하는 독립
> 에이전트**를 새로 둔다. 기존 검증 에이전트는 팩트체크·AI 오류검수·출처검증 3항목만 유지한다.

### 7.1 검증 (Verification) — 축소, D3 §5 그대로 유지

D3 §5의 팩트체크·AI 오류검수·출처검증 3항목만 유지한다(4대 논리오류 항목은 삭제, 7.2로 이관).

```rust
pub struct VerificationReport {
    pub team: TeamRole,
    pub fact_check: Vec<FactCheckItem>,
    pub error_review: Vec<String>,
    pub source_check: SourceCheckResult,
    pub confidence_adjustment: Option<Confidence>,
    // fallacy_flags 필드 삭제 -- 7.2 LogicFallacyReport로 이관
}
```

**재무 수치 팩트체크 규칙 (사용자 확정, 2026-07-26)**: 팩트체크 대상 `claim`이 재무 수치인
경우, [09_재무수치_정의.md](09_재무수치_정의.md) §1의 **5요소(계정명·금액·단위·기간·출처)가
모두 일치해야** `Confirmed`로 판정한다.

- 금액만 맞고 **기간이 다르면** `Contradicted`다 — 작년 수치를 올해 것처럼 인용하는 오류를
  잡아내기 위함이며, 이것이 이 규칙의 실질적 목적이다.
- 단위가 다르면(천원 vs 백만원) 09 §2.5의 `to_thousand()`로 환산해 비교한다 — 환산 후
  같으면 일치로 본다.
- **예외**: `MonetaryUnit.rounded == true`인 수치(원 단위 원본을 천원으로 환산하며 반올림된
  경우)는 반올림 오차 범위 내 일치를 허용한다. 이 예외가 없으면 반올림 때문에 정상 수치가
  `Contradicted`로 오판된다(09 §2.5).

### 7.2 논리오류 검증 에이전트 (신규 — 독립 에이전트)

- **소속**: 이사장 직속의 별도 에이전트. 검증 에이전트의 하위 기능이 아니라 **검증과 나란히
  동작하는 별개 에이전트**다(사용자 지시: "논리오류만 전담하는 에이전트를 만들자").
- **입력**: 팀 산출물(`TeamOutput`, D2) — 검증 에이전트와 동일한 입력을 받되 별도로 독립 실행.
- **판정 근거**: [06_논리적_오류_정의.md](06_논리적_오류_정의.md) 문서 **그대로**를 검출 기준으로
  삼는다 — 이 문서에 없는 오류 유형은 검출 대상이 아니며, 문서가 갱신되면(문서 갱신 규칙 참고)
  코드의 `FallacyType`도 함께 갱신되어야 한다(문서와 코드 1:1 대응 원칙).
- **출력**: `LogicFallacyReport` — 검증 에이전트의 `VerificationReport`와 별개 산출물이며,
  이사장의 승인 게이트(§2.2)는 **두 리포트를 함께** 근거로 판단한다.

```rust
/// 06_논리적_오류_정의.md의 "총칭" 7개 행을 제외한 실제 검출 대상 26종.
/// 문서에 새 오류가 추가되면 이 열거값에도 대응 항목을 추가한다(1:1 대응 원칙).

    TuQuoque,                   // 그쪽이야말로주의
    RedHerring,                 // 논점일탈의 오류
    GamblersFallacy,            // 도박사의 오류
    NothingButXism,             // 만물XX설
    GordianKnotFallacy,         // 매듭 자르기의 오류
    Contradiction,               // 모순

    GeneticFallacy,              // 발생적 오류

    AppealToPerson,              // 사람에 호소하는 오류
    AppealToNoveltyOrTradition,  // 새로움에 호소하는 오류와 전통에 호소하는 오류
    HastyGeneralization,         // 성급한 일반화의 오류
    CircularReasoning,           // 순환 논법
    PoisoningTheWell,            // 원천봉쇄의 오류
    Antinomy,                    // 이율배반
    DoubleStandard,              // 이중잣대
    AdHominem,                   // 인신공격의 오류
    SelfContradiction,           // 자가당착
    HempelsRaven,                // 헴펠의 까마귀
    StorkAndNewborns,            // 황새와 신생아
    BlackAndWhiteThinking,       // 흑백논리
}

pub struct FallacyFlag {
    pub fallacy: FallacyType,
    pub location: String,       // findings 내 어느 문장/구절인지
    pub category: FallacyCategory, // 06_논리적_오류_정의.md "분류 체계" 참고
    pub severity: SeverityAssessment,   // 신규 -- 7.3절
    pub verdict: SeverityVerdict,        // 신규 -- severity로부터 계산된 판정
}

// ── 7.3 심각도 평가 (Severity) — 사용자 결정, 2026-07-26 ──────────────────────
//
// "얼마나 심각해야 반려인지"를 3개 축으로 평가한다. 논리오류 검증 에이전트가
// FallacyFlag를 만들 때마다 이 3축을 함께 판정해 넣는다.

/// 축 1 — 주장의 핵심성: 오류가 결론을 지지하는 핵심 근거에 있는가, 단순 부연/수식어인가.
pub enum Centrality { Core, Peripheral }

/// 축 2 — 논증의 파괴성: 이 오류를 제거하면 결론 전체가 무너지는가, 다른 건강한 근거로
/// 결론이 유효하게 유지되는가.
pub enum Destructiveness { Fatal, NonFatal }

/// 축 3 — 수용 불가능성: 단순한 표현상의 미숙함(뉘앙스)인가, 명백한 사실 왜곡·기만인가.
pub enum Acceptability { Unacceptable, Acceptable }

pub struct SeverityAssessment {
    pub centrality: Centrality,
    pub destructiveness: Destructiveness,
    pub acceptability: Acceptability,
    /// 축별 판정 근거 (사용자 결정, 2026-07-26 -- E-2 조치).
    /// 3축 판정 자체도 LLM이 내리는 판단이므로, 결과만 남기면 오판을 사후에 검증할 수 없다.
    /// 각 축을 왜 그렇게 판정했는지 짧게 함께 기록한다.
    pub rationale: SeverityRationale,
}

pub struct SeverityRationale {
    pub centrality: String,       // 예: "이 문장이 최종 투자의견의 유일한 근거"
    pub destructiveness: String,  // 예: "제거해도 재무지표 근거가 남아 결론 유지"
    pub acceptability: String,    // 예: "표현이 거칠 뿐 사실관계 왜곡은 없음"
}

pub enum SeverityVerdict {
    Reject,           // 이사장 반려 사유에 포함
    RewriteRequest,   // 전면 반려 대신 해당 문장 재작성 지시로 대체
    NoteOnly,          // 경미 -- 반려하지 않고 리포트에만 기록, 승인 진행
}

/// 3축 조합 -> 판정. 수용 불가능성(기만·사실왜곡)이 최우선 신호다 -- 표현이 아무리
/// 매끄러워도 기만이면 예외 없이 반려한다. 그 다음은 핵심성×파괴성 조합으로 세분한다.
pub fn assess_severity(a: &SeverityAssessment) -> SeverityVerdict {
    use Centrality::*; use Destructiveness::*; use Acceptability::*;
    match a.acceptability {
        Unacceptable => SeverityVerdict::Reject,
        Acceptable => match (&a.centrality, &a.destructiveness) {
            (Core, Fatal) => SeverityVerdict::Reject,
            (Core, NonFatal) | (Peripheral, Fatal) => SeverityVerdict::RewriteRequest,
            (Peripheral, NonFatal) => SeverityVerdict::NoteOnly,
        },
    }
}
```

| 핵심성 | 파괴성 | 수용가능성 | 판정 |
|---|---|---|---|
| — | — | 수용 불가(기만·왜곡) | **반려** (다른 축과 무관하게 최우선 적용) |
| 핵심 | 결론 붕괴 | 수용 가능(표현 문제) | **반려** (핵심 근거가 무너지면 표현 문제여도 결론 자체가 흔들림) |
| 핵심 | 결론 유지 | 수용 가능 | **재작성 지시** |
| 부연 | 결론 붕괴 | 수용 가능 | **재작성 지시** |
| 부연 | 결론 유지 | 수용 가능 | **기록만(NoteOnly)** — 승인 진행 |

## 8. 최신화·버전관리 — 사전(pre-flight) + 사후(post-approval) 이중 역할

### 8.1 사후 역할 (D3 §6 골격 유지 + `Refresh` 의미 확정)

승인된 draft를 받아 버전 부여·정정(`Correction`) 처리·아카이빙을 수행한다. 추가로 이번 개정에서
**Taxonomy의 분류 결과를 참고해 에이전트 산출물들을 서로 링크**하는 역할이 명확해졌다 —
`WikiRelation`(D1 §3.1)을 생성할 때 Taxonomy가 확정한 분류(4.1절)를 관계 판단의 근거로 쓴다
(같은 3단계 분류를 공유하는 페이지들을 `PartOf`/`Reference` 관계로 자동 연결).

#### `ChangeKind` — 현행 정의 (RD-02 조치, 사용자 결정 2026-08-02)

> **왜 여기에 다시 적나**: `ChangeKind`는 D3 §4에만 정의되어 있었는데 **D3는 이력 보존용
> 문서**다. 갱신되지 않는 문서를 현행 설계가 참조하는 구조는 RD-04를 만든 것과 같은 함정
> (99 §5 함정 #13)이므로, 의미가 바뀐 시점에 현행 문서로 옮겨 온다. **이 정의가 유효본이다.**

```rust
pub enum ChangeKind {
    New,          // 최초 생성
    Correction,   // 오보·정정 반영 (기존 내용이 "틀렸음"이 확인됨) -> supersedes 연결 + Uncertain 하향
    Refresh,      // 같은 사실의 "다른 기간" 값 -- 아래 확정 내용 참고
    Archived,     // 활성 인덱스에서 제외 (폐기 아님 -- 이력 보존)
}
```

**`Refresh`는 덮어쓰기가 아니라 레코드 추가다.**

| 구분 | `Correction` | `Refresh` |
|---|---|---|
| 무슨 일이 일어났나 | 기존 값이 **틀렸다** | 기존 값은 맞고, **기간이 달라졌다** |
| 이전 값 | `supersedes`로 연결 + `Uncertain` 하향 | **그대로 유효**하게 보존 |
| 저장 방식 | 대체 | **추가** (기간이 다른 새 레코드) |
| 활성 인덱스 | 최신본만 | 최신 기간이 대표, 과거 기간은 조회 가능 |

**근거**: 성장성 3종(매출액증가율·순이익증가율·총자산증가율)은 전기 값이 있어야 계산된다
([09 §2](09_재무수치_정의.md) 시계열 필수 계정 3종). `Refresh`를 덮어쓰기로 두면 **확정된 지표가
계산 불가능**해진다 — 확정 항목(성장성 3종)이 미결 항목(O-35-1)에 매달려 있던 것이 RD-02였고,
여기서 그 의존을 끊는다.

**두 값이 다르다고 `Correction`이 아니다.** 이 구분이 이 결정의 실질이다 — 2025년 매출과
2024년 매출이 다른 것은 정정 사유가 아니라 **정상적인 시계열**이다. 판정은 09 §1 5요소 중
**기간(④)이 같은지**로 한다.

| 기간 | 금액 | 판정 |
|---|---|---|
| 같음 | 다름 | `Correction` — 같은 기간에 두 값이 있을 수 없다 |
| 다름 | 다름 | **`Refresh`** — 레코드 추가 |
| 다름 | 같음 | `Refresh` — 값이 같아도 별개 기간 레코드다 |

> **적용 범위**: 시계열 보관이 필수인 것은 09 §2의 3종(`Revenue`·`NetIncome`·`TotalAssets`)이다.
> 나머지 L1 계정도 `Refresh` 규칙 자체는 동일하게 적용되나, 최소 2기간 보관을 **강제하지는
> 않는다** — 저장은 하되 계산이 요구하지 않으므로 아카이빙 대상이 될 수 있다.

### 8.2 사전(pre-flight) 역할 — 신규

이사장이 사용자 프롬프트 처리를 **시작하기 전에**, 그 프롬프트에 특화된 **5단계 우선순위 인덱스**를
제공한다. 목적은 이사장/Taxonomy/Research가 처음부터 다시 찾지 않고, 이미 위키에 쌓인 관련 요약을
우선순위별로 미리 받아보는 것 — §2.5(라우터·인덱스 우선탐색) 원칙의 실행 주체를 이 에이전트로
명확히 지정한 것이다.

### 8.2.1 라우터 흡수 — 예산 배분까지 이 에이전트가 담당 (사용자 결정, 2026-07-26)

D1 §4.3에서 별도 모듈(`router.rs`)로 두려던 라우터를 **최신화·버전관리 에이전트의 사전 역할에
흡수**한다. 별도 모듈을 만들지 않는다.

**판단 근거**: 프리플라이트가 이미 4단계 우선순위로 정렬을 끝내므로, 라우터에 남는 일은
"그중 몇 개까지 본문을 실을지"라는 **예산 배분**뿐이다. 순위를 매긴 주체와 예산을 배분하는
주체를 나누면 같은 데이터를 두 번 넘기게 되므로 한 곳에서 처리한다.

> 사용자 결정 시 **"나중에 문제가 생기면 그때 분리한다"** 는 단서가 붙었다 — 현 시점에서
> 분리 비용을 미리 지불하지 않겠다는 판단이며, 분리가 필요해지는 신호(예: 예산 배분 규칙이
> 버전 관리 로직과 얽혀 읽기 어려워질 때)가 나타나면 재검토한다.

```rust
/// 라우터 흡수 결과 -- 프리플라이트가 순위와 예산 배분을 한 번에 끝낸다.
pub struct RoutedContext {
    /// 본문 전체를 실을 페이지 (body_required=true인 것 우선, 09 §3.3 우선순위)
    pub full_body: Vec<String>,       // page id
    /// 요약만 실을 페이지
    pub summary_only: Vec<String>,
    /// 예산 부족으로 제외한 페이지 -- 응답에 제외 사실을 명시해야 한다(09 §3.3)
    pub excluded: Vec<String>,
}

pub mod versioning {
    /// LLM 호출 없이 순수 알고리즘으로 수행한다.
    ///   1. 예산 계산 (num_ctx - 프롬프트 오버헤드 - 출력 여유)
    ///   2. 1단계부터 순회하며 body_required=true 페이지를 우선 담는다
    ///   3. 예산이 남으면 나머지 본문을 채운다
    ///   4. 못 담은 페이지는 excluded에 넣는다 -- 요약으로 "대체"하지 않는다(09 §3.1)
    pub fn allocate_budget(index: &PreflightIndex, num_ctx: u32) -> RoutedContext { .. }
}
```

**LLM을 쓰지 않는다**는 점이 중요하다 — 라우터를 LLM 분류로 구현하면 매 질의마다 호출이 하나씩
늘어 E-3(파이프라인 호출 수 증가) 우려를 키운다. 프리플라이트가 이미 순위를 내주므로 그럴 필요가 없다.

### 8.2.2 경로 A/B 통일 — `query()`도 사전검사를 거친다 (사용자 결정, 2026-07-26)

D-04의 근본 원인 중 하나는 위키에 질문하는 **진입 경로가 두 개**라는 것이었다.

| 경로 | 기존 | 변경 후 |
|---|---|---|
| A. 이사장 파이프라인 | 프리플라이트 O | 그대로 |
| B. 📚 위키 패널 직접 질문 (`wiki::query`) | 프리플라이트 X → `wiki.rs:244` 6000자 2택 | **프리플라이트 경유로 통일** |

`wiki::query()`도 `match_known_company` → `run_preflight` → `allocate_budget`을 거치도록 바꾼다.
프리플라이트는 LLM을 쓰지 않는 알고리즘적 조회라 경로 B에 추가해도 비용 부담이 없다.

> **RD-01 반영(2026-08-02)**: 경로 B에도 기업 힌트 사전 매칭이 들어간다(§8.2.3). 경로 B는
> Taxonomy를 거치지 않아 **재순위 기회가 없으므로**, 매칭에 실패하면 1단계를 비운 채로 답변한다.
> 경로 A처럼 나중에 바로잡히지 않는다는 점이 두 경로의 유일한 차이다.

> **시험 성격**: 사용자 결정 시 **"일단 사전검사하는 걸로 하자(테스트 겸)"** 로 명시되었다.
> 즉 이 통일은 확정 아키텍처라기보다 **경로 B에서 프리플라이트가 실제로 잘 동작하는지 확인하는
> 검증 수단**을 겸한다. 경로 B는 이사장 파이프라인 전체를 돌리지 않고 프리플라이트만 단독으로
> 호출하므로, 프리플라이트의 순위·예산 배분 품질을 격리해서 관찰하기에 좋은 조건이다.

### 8.2.3 기업 힌트 — 순환 의존 해소 (RD-01 조치, 사용자 결정 2026-08-02)

**문제**: 1단계("동일 대상") 판정에 기업이 필요한데, 기업은 Taxonomy가 나중에 확정한다.
프리플라이트는 파이프라인 **시작 직후** 전처리부와 병렬로 돌므로 그 시점엔 기업을 모른다.

```
프리플라이트 ──(인덱스 제공)──► Taxonomy ──(기업 확정)──┐
     ▲                                                  │
     └──────────── 기업을 알아야 1단계 판정 가능 ─────────┘
```

**채택안 — 사전 매칭 + 재순위** (안①·안②를 합치되 "모르면 비운다"를 축으로 삼음)

| # | 시점 | 하는 일 | LLM |
|---|---|---|---|
| 1 | 이사장 접수 | 위키 **기업명 사전**과 프롬프트를 문자열 매칭 → `company_hint` | ✕ |
| 2 | 프리플라이트 | 힌트가 있으면 1·2단계를 채우고, **없으면 1·2단계를 비운다**(3단계는 키워드 근사) — TD-07 정정: 2단계도 "동일 대상" 판정이라 힌트 없이는 채울 수 없다 | ✕ |
| 3 | Taxonomy 확정 후 (경로 A) | 확정 기업이 힌트와 다르면 `rerank_after_taxonomy`가 같은 스냅샷 대상 **티어 배정 재실행** — 재분배가 아니다(TD-07) | ✕ |

**왜 이 방식인가 — 세 가지 근거**

① **LLM으로 "얕게 추출"하지 않는다.** 추출을 LLM에 맡기면 파이프라인 시작 전에 호출이 하나
늘고(E-3), 무엇보다 **프리플라이트가 큐 밖에서 돈다**는 §8.2의 전제가 깨진다. 사전 매칭은
순수 알고리즘이라 두 문제가 모두 없다.

② **위키에 없는 기업은 애초에 1단계에 올릴 페이지도 없다.** 사전 매칭이 실패하는 경우란
곧 "이 기업에 대해 위키가 아는 게 없다"는 뜻이므로, 매칭 실패와 1단계 공백이 정확히 겹친다.
**추측이 필요한 구간 자체가 존재하지 않는다** — 이것이 이 안을 택한 결정적 이유다.

③ **모르면 비우는 것이 정상이다.** 힌트 없이 프롬프트 문자열만 보고 기업을 추정하면, 틀렸을 때
**가장 신뢰도 높은 층(1단계)에 무관한 페이지가 조용히 올라간다** — 에러가 나지 않으므로 사용자가
인지할 수 없는 전형적 silent-wrong이다(99 §4 패턴 3). §4.1.3·§4.2의 "비워두는 것이 정상"과
같은 판단을 여기에도 적용한다.

**경로 B(§8.2.2)에서도 그대로 작동한다.** 사전 매칭은 프롬프트만 있으면 되므로 Taxonomy를
거치지 않는 `wiki::query()`에서도 동일하게 쓸 수 있다 — 재워크스루가 "경로 B는 보정 기회가
없다"고 지적한 부분(13 §RW-5)이 여기서 닫힌다. 다만 경로 B에는 3단계(재순위)가 없으므로
**힌트가 곧 최종값**이며, `hint_source`는 `DictMatch` 또는 `None`에서 끝난다.

**겹치는 이름(포함 관계)**: `LG`와 `LG에너지솔루션`처럼 **서로 다른 이름이 한 프롬프트에 동시
매칭**되면 **최장 일치를 채택**한다(TD-09) — 더 구체적인 이름이 이긴다. 다중 매칭을 일괄
`None` 처리하면 더 정확한 후보를 버리게 된다 (한국 기업명은 그룹명이 계열사명에 포함되는
구조가 흔해 실제로 자주 발생한다).

**동명이인 문제**: **같은 문자열**의 기업이 둘 이상이면 매칭을 **실패로 처리**한다(`None`).
D-05 조치로 기업 식별자가 `corp_code`로 바뀌면 동명 구분이 가능해지므로, 그때 이 규칙을
재검토한다 — 그전까지는 잘못 고르는 것보다 비우는 쪽이 안전하다.

```rust
pub mod wiki {
    /// 위키에 이미 존재하는 기업명 목록과 프롬프트를 대조한다. LLM 없음.
    /// 서로 다른 이름이 겹쳐 매칭되면 최장 일치 채택(TD-09: "LG" vs "LG에너지솔루션").
    /// 후보가 0개면 None, 같은 문자열의 동명 기업이면 None -- 잘못 고르느니 비운다.
    pub fn match_known_company(wiki: &WikiState, prompt: &str) -> Option<String> { .. }
}
```

**D-04(컨텍스트 예산)와의 관계**: 재워크스루는 "1단계 판정이 부정확하면 우선순위 체계 전체가
흔들린다"고 지적했다(13 §5.1). 이 조치로 **1·2단계는 근거가 있을 때만 채워지므로**(TD-07 정정:
힌트 부재 시 둘 다 비운다), 부정확한 상위 티어가 예산을 잠식하는 경로가 사라진다. 비어 있는
티어는 다음 티어가 그대로 예산을 쓰게 할 뿐 손해가 아니다(§8.2.1 `allocate_budget`은 1단계부터
순회하되 비어 있으면 그냥 다음으로 넘어간다).

### 8.3 두 역할의 관계

같은 에이전트(최신화·버전관리)가 파이프라인의 **서로 다른 두 시점**에 호출된다 — 시작 직후
(사전, 조회 전담) 한 번, 승인 직후(사후, 기록 전담) 한 번. 두 호출은 독립적이며 사전 호출의
실패가 사후 호출을 막지 않는다(사전 인덱스가 비어 있으면 그냥 "참고할 기존 자료 없음"으로
처리하고 진행).

#### 동시성 — 경고만 남기고 재실행하지 않는다 (O-13 해결, 2026-07-26)

**위험이 이미 크게 줄어 있다**: D-01 조치로 `call_llm()` 하나만 큐를 거치므로 LLM 호출이 전부
직렬화된다. 다른 요청이 끼어들어 위키를 갱신하려면 그 요청도 같은 락을 기다려야 한다.

**남는 위험은 하나**다 — 사전 프리플라이트는 LLM을 쓰지 않아(§8.2) 큐 밖에서 돈다. 그 사이
다른 요청의 사후 버전화가 위키를 바꿀 수 있다.

**조치**: 프리플라이트가 조회 시점의 `wiki_version`을 기록하고, 사후 단계에서 값이 달라졌으면
**경고만 남긴다**(재실행하지 않는다).

> **재실행하지 않는 이유**: 프리플라이트는 "참고용 우선순위"이지 정합성이 필수인 데이터가 아니다.
> 위키가 바뀌었다고 파이프라인을 되돌리면, 동시 사용이 잦을수록 계속 재시작해 진행이 안 된다.
> 과잉 대응이 오히려 시스템을 멈춘다.

### 8.4 위키 저장 구조 보강 — 새 필드의 자리 (RD-05·RD-06 해소 + TD-02 정정, 2026-08-02)

`document_tax_tags`(O-18)와 `CreditRiskSummary`(12 §5.1)는 **정의만 되고 어느 구조에 담기는지가
없었다.** 저장 구조는 최신화·버전관리 에이전트의 소관이므로 여기서 확정한다.

> **D1을 고치지 않는다.** `WikiEntry` 원형은 D1 §3.1에 있으나 D1은 이력 보존용이다
> (99 §5 함정 #13). 필드 추가는 **현행 문서인 여기에 기술**하며, 이 절이 유효본이다.

```rust
/// 현행 WikiEntry -- D1 §3.1 + 10 문서(CompanyRef 교체) + 이번 추가분의 "합집합"이다.
///
/// TD-02 정정(2026-08-02): 최초 판은 D1 §3.1의 신규 3필드(confidence·company·period)를
/// 빠뜨린 채 유효본을 선언했다. 유효본을 선언하는 목록은 반드시 전체를 다시 적어야 한다 --
/// 부분 목록에 권위를 주면 누락이 권위를 얻는다(함정 #13의 역방향).
///
/// D-02 조치로 신규 필드 전부 #[serde(default)] -- 기존 index.json을 깨지 않는다.
pub struct WikiEntry {
    pub id: String,
    pub title: String,
    pub summary: String,
    pub body: String,
    pub tags: Vec<String>,            // 기존 -- 사용자가 붙이는 자유 문자열 태그
    pub source: String,
    pub relations: Vec<WikiRelation>,  // D1 §3.1 -- related_ids 대체 (O-2 소멸로 마이그레이션 없음)
    pub created_at: String,
    pub updated_at: String,

    // ── D1 §3.1 신규 3필드 (TD-02 정정으로 목록에 복원) ──────────────────────
    /// 신뢰도 3등급. 승격 시점에 확정 기입된다(아래 원자적 패키지 Step 2) --
    /// 검증 리포트의 confidence_adjustment가 이때 반영된다(TD-03).
    #[serde(default)]
    pub confidence: Confidence,
    /// 기업 스코프. D1은 Option<String>이었으나 10 §4에서 CompanyRef로 교체 확정 --

    #[serde(default)]
    pub company: Option<CompanyRef>,

    #[serde(default)]
    pub period: Option<String>,

    // ── 이번 추가분 ──────────────────────────────────────────────────────────
    /// RD-05 -- 문서 속성 태그 (닫힌 목록). 자유 태그와 섞지 않는다.
    #[serde(default)]
    pub doc_tags: DocumentTags,

    /// RD-06 -- 기업 단위 페이지에만 채워진다. 문서 페이지에서는 None.
    #[serde(default)]
    pub credit_risk: Option<CreditRiskSummary>,

    /// 버전 상태(VersionRecord -- D3 §4 정의, 유효 정의는 §8.1). 저장 위치가 그동안
    /// 미기술이었는데, 별도 맵을 만들지 않고 엔트리에 인라인한다 -- RD-05·06과 같은
    /// 판단("분리 비용을 미리 지불하지 않는다"). None이면 아직 버전화 전이다.
    /// "현재 유효본" 판별은 별도 is_current 플래그가 아니라 version.archived == false --
    /// 같은 사실을 두 필드가 말하면 어긋나는 순간부터 정합성 관리 대상이 된다(Step 1).

#### RD-05 — `DocumentTags`는 자유 태그와 분리한다

```rust
/// O-14/O-18에서 갈라낸 "문서 속성"들의 집합. 원형은 07 §O.
/// 기업 속성(company_industries, CompanyOptions)은 여기 들어오지 않는다.
#[derive(Default)]
pub struct DocumentTags {
    /// 세목 10종 -- 이 문서가 어떤 세무 주제를 다루는가 (납부 세목이 아니다, O-18)
    pub tax_topics: Vec<TaxTopicTag>,
    /// 이 문서가 다루는 주제 산업 -- 확신 없으면 None (O-14).
    /// 07 §O의 원형에는 없던 필드. 같은 "문서 속성"이라 여기로 모은다.
    pub industry: Option<IndustrySection>,
}
```

**기존 `tags: Vec<String>`에 넣지 않는 이유**: 자유 태그는 사용자가 아무 문자열이나 붙이는
칸이고 세목은 **닫힌 목록**이다. 한 칸에 섞으면 *"국제조세 관련 문서만 찾아줘"* 라는 검색이
자유 태그에 우연히 같은 글자가 들어간 페이지까지 끌어온다. **한 필드에 성격이 다른 두 답을
담지 않는다**는 O-14 해결 방식(99 §4 패턴 1)을 그대로 적용한 것이다.

`document_industry`를 여기 함께 넣은 이유도 같다 — 둘 다 패턴 1로 갈라져 나온 **문서 속성**이라
타입 하나에 모아 두면 "이건 기업 얘기인가 문서 얘기인가"를 구조가 대신 답해 준다.

#### RD-06 — `CreditRiskSummary`는 기업 페이지에 붙인다 (별도 저장소 안 만듦)

| 안 | 판단 |
|---|---|
| **기업 단위 `WikiEntry`에 필드로** | ✅ **채택** |
| 별도 저장소(`credit.json` 등) | 보류 — Phase 2에서 재검토 |

**근거**

① **Phase 1은 레코드가 1건뿐이다.** O-34로 이력을 Phase 2로 미뤘으므로 기업당 현재 상태
스냅샷 하나만 남는다. 1건을 위해 저장소·로딩·정합성 로직을 새로 만드는 것은 **분리 비용을 미리
지불하는 것**이다 — §8.2.1에서 라우터를 흡수할 때와 같은 판단이다.

② **갱신 규칙이 이미 있다.** `checked_at`이 시점을 담고 있으므로, 새로 조회한 요약은
`Refresh`(§8.1 확정 = 기간이 다른 레코드 추가)로 처리된다. 별도 저장소를 만들면 이 규칙을
두 번 구현하게 된다.

**부착 대상의 판별 (TD-02 보완)**: "기업 단위 페이지" = 해당 `corp_code`의 **기업개황 페이지**다
(10 §5 캐시 정책 — 기업개황은 위키 페이지로 저장된다). `company` 필드만으로는 같은 기업의
여러 문서 페이지와 구분되지 않으므로, 판별 기준을 여기 명시해 둔다.

**분리해야 할 신호 (Phase 2 재검토 조건)**

- 신용 **사건 이력**이 들어오기 시작할 때 — 1:N이 되면 페이지 인라인이 무너진다
- **접근 제어**가 필요해질 때 — 신용정보만 따로 잠그려면 페이지 단위 권한으로는 부족하다
  (12 §5.1 ⚠ 민감 정보 취급)

> 이 두 신호는 **둘 다 Phase 2에서 함께 온다**(O-34가 이력과 접근 제어를 한 묶음으로 미뤘다).
> 그래서 Phase 1에서 미리 나눌 이유가 없고, 나눠야 할 때는 한 번에 나누게 된다.

#### 유효본 선언은 원자적 패키지다 — `promote()` (사용자 제안, 2026-08-02)

TD-02를 계기로 사용자가 제안한 구조: **유효본 선언 시 관련 상태 변경 전부가 하나의
ALL-OR-NOTHING 단위로 묶여야 한다.** 제안의 3단계를 기존 결정과 대조해 다음과 같이 확정한다.

| 제안 | 확정 | 근거 |
|---|---|---|
| **Step 1** — 승격 상태 변경 | ✅ 채택 (형태 조정) | 신규본 활성 + 구버전 `version.archived = true` + `supersedes` 연결. 제안의 `is_current` 별도 필드는 두지 않는다 — `archived`에서 파생 가능한 상태를 중복 저장하면 두 값이 어긋나는 순간부터 정합성 관리(lint) 대상이 된다 |
| **Step 2** — 메타데이터 동기화 | ✅ 채택 | `confidence`·`company`·`period`를 **승격 시점에 확정 기입**하고 이후 별도 갱신 없음. `confidence`의 입력이 바로 검증 리포트의 `confidence_adjustment`다 — **TD-03이 이 단계에서 함께 해소된다**(§2.5.5의 `run_post_approval`이 검증 리포트를 전달받는 이유). 정상 승격·부분 리포트 두 경로 모두 이 단계를 지난다 |
| **Step 3** — 참조 포인터 재배선(Re-indexing) | ▶ **"재배선 불필요"로 대체** | 문서가 기업을 가리키는 키는 `corp_code`(**불변**)이지 기업 페이지의 entry ID가 아니다 — D-05c의 canonical_key 결정이 재배선할 대상 자체를 없앴다. `WikiRelation`의 ID 링크도 바꾸지 않는다 — "이 리포트는 v3 기준"(D3 §7)의 버전 추적성이 **구버전 링크 보존을 요구**하기 때문이다. "현재본 찾기"는 조회 시점에 `(corp_code, version.archived == false)` 해석으로 달성한다 |

**원자성의 구현**: 별도 트랜잭션 계층을 만들지 않는다. `promote()`가 Step 1~2의 변경을 전부
**인메모리에서** 완료한 뒤 **단일 save 한 번**으로 기록한다 — index.json 저장은 D-07 조치
(임시파일 + `fs::rename`)로 파일 수준 all-or-nothing이 이미 보장되므로, "한 번에 저장"만
지키면 중간 상태가 디스크에 남을 수 없다. 트랜잭션을 새로 짜는 것이 아니라 **이미 있는
원자성 위에 올라타는** 것이다.

```rust
impl DraftState {
    /// 유효본 선언 -- 사용자 제안의 set_current_valid에 해당하는 함수는 §2.5.5가 이미
    /// 쓰고 있는 promote()다(이름 유지). Step 1~2의 전 변경을 인메모리에서 끝낸 뒤
    /// save 1회로 기록한다.
    /// ⚠ 이 함수가 save를 여러 번 부르면 D-07의 보장이 "각 save"에만 적용되어 패키지
    /// 전체의 원자성이 깨진다 -- save는 반드시 마지막에 한 번.
    pub fn promote(&self, draft: &DraftHandle, versioned: &VersionedOutput) -> Result<(), String> { .. }
}
```
