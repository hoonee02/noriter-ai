**❌ 3단계 상세 — 프리플라이트·Taxonomy 순환 의존 (RD-01)**

설계 §2.4는 프리플라이트를 전처리부와 **병렬로, 파이프라인 시작 직후** 실행한다.

```rust
let (preprocessed, preflight_index) = tokio::join!(
    preprocessing::run(app, &user_prompt, &files),
    versioning::run_preflight(app, wiki, &user_prompt),   // ← prompt만 받는다
);
```

그런데 프리플라이트의 **1단계 우선순위 기준은 "동일 대상(기업 등)·동일 요청 유형"**(§8.2)이다.
"동일 대상"을 판정하려면 대상 기업을 알아야 하는데, **기업은 Taxonomy 2단계에서 확정**되고
Taxonomy는 프리플라이트 결과를 컨텍스트로 받는다.

```
프리플라이트 ──(인덱스 제공)──► Taxonomy ──(기업 확정)──┐
     ▲                                                  │
     └──────────── 기업을 알아야 1단계 판정 가능 ─────────┘
```

현재 프리플라이트는 프롬프트 문자열만 보고 기업을 추정해야 하는데, 그 추정이 틀리면
**1단계(가장 신뢰도 높은 층)에 무관한 페이지가 올라간다.** D-04(컨텍스트 예산)의 우선순위
1~3순위가 전부 이 판정에 의존하므로 영향이 크다.

**❌ 4단계 — Guard 1이 존재하지 않는 지표를 방어한다 (RD-03)**

Guard 1(09 §2.6)은 종업원수 기준일 차이가 6개월 이상이면 `is_estimated`를 붙이도록 한다.
목적은 **생산성 지표**(종업원 1인당 매출액 등) 오염 방지다.

그런데 O-40에서 채택한 **재무진단 5축에 생산성 축이 없다.**

| 원본 상세 재무비율 (5카테고리) | 채택한 재무진단 5축 |
|---|---|
| 성장성 · 수익성 · 안정성 · 활동성 · **생산성** | 성장성 · 수익성 · 재무구조 · 부채상환능력 · 활동성 |

둘 다 5개지만 구성이 다르다 — 재무진단은 안정성을 둘로 쪼개는 대신 **생산성을 뺐다.**
O-40 결정 시 이 차이를 짚지 않았다.

→ Guard 1은 지금 **계산하지 않는 지표를 지키고 있다.** 둘 중 하나가 잘못됐다.

**❌ 6단계 — 시계열 보관 방식이 미결인 채 지표가 확정됐다 (RD-02)**

성장성 3종은 전기 값이 필수인데, D3 §6의 `Refresh`(최신 수치로 갱신)가 **이전 값을 덮어쓰면
계산이 불가능**하다. 12 §8.4에서 "`Refresh`를 레코드 추가로 재해석"하는 안을 제시했으나
**O-35-1로 미결 등록된 상태**다.

즉 **확정된 지표(성장성 3종)가 미결 항목(O-35-1)에 의존**한다. 구현 시 여기서 막힌다.

| # | 단계 | 관찰 | 판정 |
|---|---|---|---|
| 1 | 1차 반려 | 검증·논리오류 리포트 근거 | ✅ |
| 2 | 재작업 루프 진입 | **구현 위치를 특정할 수 없다** | ❌ **RD-04** |
| 3 | 3회 초과 → `save_pending_work` | 미결작업.md 이관 | ✅ |
| 4 | `build_partial_report` | 완료 팀만 버전화, 막힌 팀은 플레이스홀더 | ✅ |
| 5 | 부분 리포트도 SalesCS 경유 | 산출물이 있으므로 원칙 준수 | ✅ |

**❌ 2단계 — `run_governance_pipeline` 내부 미정의 (RD-04)**

현행 설계서 §2.4의 `chair_process`는 거버넌스 구간을 한 줄로 위임한다.

```rust
// 검증 -> 승인 게이트 -> 재작업 루프(3회 상한, D3 §8) -> 최신화(사후) -> SalesCS
run_governance_pipeline(app, wiki, model, num_ctx, &intent, classification).await
```

그런데 **이 함수의 정의가 어디에도 없다.** 참조된 D3 §8.2의 `chair_analysis` 코드는:

```rust
let verification = run_verification_agent(...).await?;
match chairman_review_with_evidence(app, model, num_ctx, &draft, &verification).await? {
```

**논리오류 검증 에이전트가 빠져 있다** — D3는 §7.2 신설 **이전**에 작성된 코드이고, 문서 상단에
"이력 보존용"으로 명시되어 있다. 즉 **현행 설계에는 재작업 루프의 구체 구현이 없고, 참조 가능한
유일한 코드는 구버전**이다.

이 구간에 담겨야 할 것: 검증 2종 병렬 호출 · 승인 판정 · 재작업 3회 상한 · 미결작업 이관 ·
부분 리포트 · 취소 확인. **파이프라인에서 가장 복잡한 부분이 미정의 상태다.**

알림 문구에 이 사실이 반영되어야 사용자가 혼란스럽지 않다.

## 5. 판정 및 조치 우선순위

### 5.1 판정

**조건부 반려.** 설계 방향과 대부분의 구조는 타당하나, **High 2건이 구현을 실제로 막는다.**

- RD-04는 **파이프라인의 핵심 구간이 통째로 미정의**다 — 구현자가 참조할 코드가 구버전뿐이다
- RD-01은 **D-04 조치(컨텍스트 예산 우선순위)의 전제를 무너뜨린다** — 1단계 판정이 부정확하면
  우선순위 체계 전체가 흔들린다

### 5.2 착수 전 필수

| 순위 | 항목 | 이유 |
|---|---|---|
| 1 | **RD-04** | 미정의 구간이라 구현 자체가 불가 |
