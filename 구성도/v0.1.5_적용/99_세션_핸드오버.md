## 3. 결정 이력 — 주제별 요약

### 3.1 에이전트 조직 (8종)

```
이사장(Chairman) ─ 오케스트레이터 + 근거 기반 승인 게이트
  ├ 전처리부      파일 추출(엑셀/PDF/OCR), 크롤링 없음
  ├ Taxonomy ★    3단계 분류 (산업/기업/옵션)
  │   └ Research  하위 겸 스탠드얼론 (이중 경로)
  ├ 검증          팩트체크·오류검수·출처검증
  ├ 논리오류 검증  26종 검출 (검증과 별개 에이전트)
  ├ 최신화·버전관리 사전(프리플라이트) + 사후(버전화) 이중 역할
  └ SalesCS       유일한 엔드포인트
  
  [Platform] 상시 관찰자 — 파이프라인 단계 아님
```

| 결정 | 내용 |
|---|---|
| 전처리부 | 실제 크롤링 **안 함**. 사용자 제공 파일만 |
| Research | Taxonomy 하위 + 이사장 직접 호출 **둘 다 가능**, 거버넌스는 동일 |
| 논리오류 검증 | 검증의 하위 기능이 아니라 **별개 에이전트** |
| 최신화팀 | **라우터를 흡수**(별도 `router.rs` 안 만듦) |
| SalesCS | 좁은 범위(포맷·전달). **취소 알림은 예외**(§5.4) |
| Platform | 2-Track 유지보수 (경량 Daily / lint Weekly) |

### 3.2 Taxonomy 3단계

| 단계 | 내용 | 특이사항 |
|---|---|---|
| 1단계 | KSIC **11차** 대분류 18종 | 공식 문서 대조 검증 완료(D-14). O·T·U 제외 |
| 2단계 | 기업 | **복수 산업 + 매출비중 가중치**, 1위가 `primary_industry` |
| 3단계 | **분류가 아니라 옵션** | 그룹별 단일/복수, **비워두는 게 정상** |

### 3.3 재무 데이터

| 항목 | 결정 |
|---|---|
| L1 계정 | **19종** (손익 7 + 재무상태 9 + 현금흐름 3) |
| L2 지표 | **재무진단 6축 18종** (안정성→재무구조+부채상환능력 분리, **생산성 추가**) |
| 저장 원칙 | **L1만 저장, 비율은 계산** |
| 단위 | 저장은 원 단위 정밀값, **반올림은 표시 시점만** |
| 시계열 | `Revenue`·`NetIncome`·`TotalAssets` 3종만 이력 |
| 가드레일 | 6종(Guard 0~5), **작동 지점이 3곳으로 나뉨** |

### 3.4 결함 해소 (Critical 3 + High 5)

| ID | 확정 조치 |
|---|---|
| D-01 큐 교착 | `call_llm()` 헬퍼 **하나만** `run_queued` 호출 |
| D-02 데이터 소실 | `#[serde(default)]` 적용 (마이그레이션 불필요로 결정) |
| D-03 자기오염 | **2저장소 분리** (`draft.json` / `index.json`) |
| D-04 컨텍스트 임계 | 재무수치 정의 + 프리플라이트 + 경로 통일 |
| D-05 기업 스코프 | OpenDART `corp_code`로 b·c 해소, **a(읽기 필터)만 남음** |
| D-06 ID 충돌 | 타임스탬프 + `AtomicU64` 카운터 |
| D-07 비원자적 쓰기 | 임시파일 + `fs::rename` (**D-06과 함께 처리**) |
| D-08 파서 취약 | 빈 본문 **명시적 실패** + 3회 후 미결작업 + 제목 구분자 |

### 3.5 RD 결함 해소 (2026-08-02) — 사용자 결정 3건

재워크스루에서 나온 7건 중 **셋은 갈림길**이었고 사용자가 직접 골랐다. 나머지 넷은 방향이
이미 정해져 있어 기술만 했다.

| ID | 갈림길 | 선택 | 결정적 이유 |
|---|---|---|---|
| **RD-01** | 2단계 분리 / 얕은 추출 | **사전 매칭 + 재순위** (제3안) | 위키에 없는 기업은 **1단계에 올릴 페이지도 없다** — 매칭 실패와 1단계 공백이 정확히 겹쳐, 추측이 필요한 구간 자체가 사라진다 |
| **RD-03** | 생산성 축 추가 / Guard 1 보류 | **6축으로 확장** | Guard 1과 09 §2 종업원수 서술 **두 곳이 이미 축의 존재를 전제**하고 있었다 (함정 #16) |
| **RD-02** | `Refresh` 재해석 / 별도 시계열 테이블 | **`Refresh` = 레코드 추가** | 저장 경로를 둘로 가르지 않는다. `Correction`과의 판정은 **기간이 같은지**로 한다 |

**기술만 한 4건**: RD-04(§2.5 신설) · RD-05·RD-06(§8.4 저장 위치) · RD-07(취소 문구).

> **RD-05·RD-06에 공통으로 적용한 판단**: 둘 다 "별도 구조를 만들까"였고 **둘 다 안 만들었다.**
> §8.2.1에서 라우터를 흡수할 때와 같은 이유 — **분리 비용을 미리 지불하지 않고, 분리해야 할
> 신호를 문서에 적어 둔다.** RD-06은 그 신호를 두 개(이력 1:N화 / 접근 제어) 명시했다.

## 4. 반복된 설계 패턴 — 다음 판단의 기준

이 세션에서 **같은 구조의 문제가 반복해서 나왔다.** 새 항목을 만날 때 먼저 이 패턴에 대입해 보면
답이 빨리 나온다.

### 패턴 1 — "기업 속성이냐 문서 속성이냐"

한 필드에 서로 다른 두 질문의 답이 섞여 있으면, **판정 규칙을 만들지 말고 필드를 나눈다.**

| 사례 | 해결 |
|---|---|
| O-14 산업 분류 | `company_industries` / `document_industry` |
| O-18 세목 | 기업 옵션에서 제외 → `document_tax_tags` |
| O-16 업종 성격 | 1단계에서 파생 → 3단계 중복 제거 |

> 나누고 나면 "무엇으로 구분할지"라는 질문 자체가 사라진다.

### 패턴 2 — "정규화하되 흔적을 남긴다"

값을 보정할 때는 반드시 플래그를 함께 남긴다. 검증 시 **우선 확인 대상**이 된다.

| 플래그 | 위치 | 의미 |
|---|---|---|
| `rounded` | 09 §2.5 | 표시용 반올림 |
| `converted` | 00 §4.1.1 | KSIC 10차→11차 변환 |
| `adjusted_tax_rate` | 09 Guard 3 | 실효세율 캡핑 |
| (신뢰도 하향) | 09 Guard 0 | OCR 저신뢰 |

### 패턴 3 — "조용히 틀리는 것이 가장 위험하다"

발견된 High 결함 5건이 **전부 silent-wrong**이었다. 판단 기준:

> 에러가 안 나고 결과가 나오는데 그 결과가 틀린 것 > 에러가 나는 것

D-08 조치에서 "빈 본문이면 폴백 대신 **명시적 실패**"를 택한 것이 이 원칙의 적용이다.

### 패턴 4 — "L1만 저장, 파생은 계산"

O-35에서 질문을 뒤집은 사례. **"뭘 저장할까"가 아니라 "뭘 확보해야 계산되나"** 를 먼저 묻는다.

### 패턴 5 — "작동 지점을 구분한다"

가드레일 6종이 입력/계산/표시 세 지점으로 갈렸다. **자본잠식은 잘못된 데이터가 아니라 정상
사실**이므로 입력단에서 막으면 안 된다 — 이런 구분을 놓치면 정상 데이터를 거부하게 된다.

## 5. 함정 — 이미 밟았거나 밟을 뻔한 것

다음 작업자가 같은 실수를 반복하지 않도록 남긴다.

| # | 함정 | 교훈 |
|---|---|---|
| 1 | **체크리스트에 High 5건이 누락**되어 있었다 | 결함기록부와 체크리스트가 어긋날 수 있다. **정기적으로 대조** |
| 2 | `run_queued`를 이사장에 씌우려 했다 | 기존 관례를 성격이 다른 곳에 그대로 옮기면 안 된다 |
| 3 | 큐로 ID 충돌을 막으려 했다 | **직렬화는 순서를 보장하지 고유성을 보장하지 않는다** |
| 4 | 가드레일을 전부 입력단에 두려 했다 | 정상 데이터를 거부하게 된다 |
| 5 | L2 지표 목록을 먼저 정했다 | 절반이 계산 불가였다. **L1부터 역산** |
| 6 | 산업분류 표의 차수를 확인 안 하고 진행 | 검증 결과 명칭 5건이 달랐다(코드는 일치) |
| 7 | 원본 자료를 한 번만 보고 정리 | **재검에서 정정 4·발견 4건**이 나왔다 |
| 8 | 백그라운드 에이전트가 계획만 세우고 끝냄 | 실제 도구 호출을 지시에 명시해야 한다 |
| **9** | **위임 한 줄이 미정의를 가렸다** (RD-04) | `run_governance_pipeline(...)` 같은 호출 한 줄이 있으면 "정의됐다"는 착시가 생긴다. **호출과 정의를 별도로 대조**해야 한다 |
| **10** | **병렬화가 순서 의존을 가렸다** (RD-01) | `tokio::join!`으로 묶으면 두 작업이 독립적이라고 가정하게 된다. 실제로는 한쪽이 다른 쪽 결과를 필요로 했다 |
| **11** | **"둘 다 5개"라는 표면적 일치**가 구성 차이를 가렸다 (RD-03) | 개수가 같다고 같은 게 아니다. 원본 5카테고리에는 생산성이 있고 채택한 5축에는 없다 |
| **12** | **확정 항목이 미결 항목에 의존**했다 (RD-02) | 성장성 3종(확정)이 O-35-1(미결)에 종속. **의존 방향을 추적**해야 한다 |
| **13** | **현행 문서가 "이력용" 문서를 참조**했다 (RD-04) | D3는 이력 보존용이라 갱신되지 않는데 현행 설계서가 그 코드를 참조했다 — **이력 문서는 참조 대상이 될 수 없다** |
| **14** | **미정의를 펼쳤더니 그 안에서 또 5건이 나왔다** (RD-04 조치) | `run_governance_pipeline`을 실제로 써 내려가자 `Unverifiable` 처리·`RewriteRequest` 카운트·산출 단위 개수 등 **한 겹 아래의 미정의**가 줄줄이 나왔다. **한 번 펼쳤다고 바닥이 아니다** — 남은 위임 4건(`synthesize` 등)도 같은 상태일 가능성이 높다 |
| **15** | **"둘 중 하나 고르기"로 제시된 문제에 답이 둘뿐인 게 아니었다** (RD-01) | 안①(2단계 분리)·안②(얕은 추출) 중 하나를 고르는 문제로 보였으나, **§4.2의 "모르면 비운다"** 를 대입하니 둘을 합치고 추측을 없앤 제3안이 나왔다. **선택지를 받으면 먼저 §4 패턴에 대입해 볼 것** |
| **16** | **무엇을 지울지 정할 때 "그것을 전제하는 문서"를 안 셌다** (RD-03) | 생산성 축을 넣을지 뺄지 정할 때, 이미 **Guard 1과 09 §2 종업원수 서술 두 곳이 축의 존재를 전제**하고 있었다. 빼면 두 곳을 고쳐야 하고 넣으면 두 곳이 그냥 맞아떨어진다 — **전제하는 곳의 개수가 판단 근거가 된다** |

## 8. 이 설계를 이해하는 데 꼭 알아야 할 것 3가지

**① `run_queued`는 "Ollama가 처리 중인지 확인하는 게이트"일 뿐이다.**
작업 전체를 대표하는 단위가 아니다. 이걸 오해해서 D-01이 생겼다.

**② 신뢰도 3등급(`Stated`/`Inferred`/`Uncertain`)이 설계 전체를 관통한다.**
L1/L2/L3 계층, 검증 판정, OCR 하향, 분류 확정/태그 강등이 모두 이 축 위에 있다.

**③ "비워두는 것이 정상"이라는 원칙이 여러 곳에 적용된다.**
옵션·문서 맥락 산업·계산 불가 지표 모두, 억지로 채우지 않는 것이 맞다. §2.4의
"근거 없는 것은 단정하지 않는다"에서 나온다.
