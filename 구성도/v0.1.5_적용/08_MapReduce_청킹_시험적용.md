# Map-Reduce 청킹 — 시험 적용안

> 사용자 제안(2026-07-26)을 **시험 적용(experimental)** 으로 문서화한 것이다. 확정 설계가 아니라
> 적용 범위를 좁혀 먼저 검증해 볼 대상이며, 검증 결과에 따라
> [00_v0.1.5.1_설계서.md](00_v0.1.5.1_설계서.md)에 정식 반영 여부를 결정한다.

## 1. 제안 내용

### 단계 ① 청킹 및 맵(Map) — 데이터 쪼개기

| 주체 | 역할 |
|---|---|
| 라우터 | 전체 원본 데이터를 12B 모델이 한 번에 소화 가능한 **8k~16k 토큰 청크**로 기계적 분할 |
| 배치 | 에이전트 1·2·3에 청크를 하나씩 분산 |
| 프롬프트 | "네가 맡은 파트에서 핵심 키워드·수치·주장만 뽑아 압축 요약해(초안 생성)" |

### 단계 ② 리듀스(Reduce) — 종합 및 정제

| 주체 | 역할 |
|---|---|
| 라우터 | 1·2·3번의 1차 압축 결과를 수집 (총합이 12B 안전 구간 8k 이내에 들어옴) |
| 배치 | 4번 **총괄 마스터 에이전트**에 요약본 전달 |
| 프롬프트 | "각 파트 요약본을 합쳐 전체 흐름이 통일된 최종 완성본을 만들어라" |

---

## 2. 이 패턴이 푸는 문제 — D-04와는 다른 문제다

**이것이 이 문서에서 가장 중요한 구분이다.** Map-Reduce는 D-04(컨텍스트 임계값 all-or-nothing)를
해결하지 못한다 — 둘은 방향이 반대인 문제다.

| 구분 | 투입(Ingestion) 측 과부하 | 조회(Retrieval) 측 선택 |
|---|---|---|
| 문제 | **입력 문서 1건이 컨텍스트보다 크다** (200쪽 PDF, 대용량 재무제표) | **위키에 페이지가 많은데 어느 것을 읽을지 모른다** |
| 해결 방향 | 쪼개서 **전부** 처리 후 합침 | 관련된 **일부만** 골라 읽음 |
| 해당 패턴 | **Map-Reduce (이 제안)** | 라우터·선택적 확장 (O-1, 미해결) |
| 우리 결함 ID | — (기존에 정식 식별 안 됨) | **D-04** |

> **핵심**: Map-Reduce를 `query()` 조회 경로에 그대로 적용하면 **질문할 때마다 위키 전체를
> 재처리**하게 된다. 이는 LLM 위키 패턴이 애초에 피하려던 것(카파시의 "매번 원본을 다시 읽지
> 말자")과 정면으로 배치되며, 현재의 인덱스 전용 모드보다 오히려 토큰을 더 쓴다.

## 3. 적용 위치 — 어디에 붙이고 어디엔 붙이지 않는가

### ✅ 적합 — 전처리부 (§3)

가장 자연스러운 자리다. 사용자가 대용량 파일(PDF·엑셀)을 올렸을 때, 그 **한 건**을 처리하는 문제이므로
"쪼개서 전부 처리"가 정확히 맞는 해법이다.

```
사용자 업로드 (200쪽 PDF)
      │
      ▼
  전처리부: 텍스트 추출 (skills/preprocess/pdf/)
      │
      ▼
  [Map] 8k~16k 청크로 분할 → 청크별 압축 요약
      │
      ▼
  [Reduce] 요약본 통합 → PreprocessedInput.extracted_files[].extracted_text
      │
      ▼
  이사장 → Taxonomy/Research (기존 파이프라인 그대로)
```

### ✅ 적합 — 위키 Ingest (구성도 §2.2~2.3)

큰 원본 1건을 위키 페이지로 구조화할 때도 같은 이유로 적합하다.

### ✅ 조건부 적합 — 논리오류 26종 검사 (E-1)

[06_논리적_오류_정의.md](06_논리적_오류_정의.md)의 26종 정의를 한 번에 프롬프트에 넣기 부담스러운
문제(E-1)에, Map 단계를 **오류 카테고리별 5분할**(형식/귀납/심리/언어/자료)로 적용할 수 있다.
단, 검사 대상 findings는 보통 작으므로 청킹이 아니라 **검사 기준 쪽을 분할**하는 변형이다.

### ❌ 부적합 — `query()` 조회 경로 (D-04)

2절에서 설명한 이유로 적용하지 않는다. D-04는 라우터 규칙(O-1)으로 별도 해결해야 한다.

## 4. 기존 설계·결함과의 충돌 검토

### 4.1 D-01(큐)과의 관계 — 병렬성은 얻지 못한다

`call_llm()`을 통한 모든 Ollama 호출은 `run_lock` 하나로 직렬화된다([03_결함기록부.md](03_결함기록부.md)
D-01 확정 조치안). 따라서 에이전트 1·2·3을 `tokio::join!`으로 동시에 띄워도 **실제 LLM 호출은
순차 처리**된다.

- **교착은 없다** — D-01 조치안대로 `call_llm`만 큐를 거치므로 안전하다.
- **속도 이득은 없다** — Map 단계의 병렬성은 이 시스템에서 실현되지 않는다.
- **그래도 가치는 있다** — 이 패턴의 본질적 이득은 병렬 속도가 아니라 **"컨텍스트를 넘기지 않고
  큰 문서를 처리할 수 있다"** 는 점이므로, 순차 실행이어도 목적은 달성된다.

> 즉 "에이전트 1·2·3에 분산"은 **동시 실행**이 아니라 **작업 분할** 로 이해해야 한다.

### 4.2 에이전트 1·2·3·4는 기존 조직도의 누구인가

제안의 "에이전트 1·2·3·4"는 역할이 없는 **익명 워커**다. 반면 우리 조직도(§1)의 에이전트들은
전부 역할 기반(전처리부·Taxonomy·Research·검증·논리오류검증·최신화·SalesCS)이다.

**권장**: 새 상설 에이전트를 만들지 말고, **전처리부 내부의 일회성 워커 풀**로 둔다.

```rust
pub mod preprocessing {
    /// Map 단계 -- 청크 수만큼 워커를 만든다(상설 에이전트 아님).
    /// 워커 수는 청크 수에 따라 결정되며 3개로 고정되지 않는다.
    async fn map_chunks(app: &AppHandle, model: &str, num_ctx: u32, chunks: &[String])
        -> Result<Vec<String>, String> { .. }

    /// Reduce 단계 -- 요약본 통합. 제안의 "4번 총괄 마스터"에 해당.
    async fn reduce_summaries(app: &AppHandle, model: &str, num_ctx: u32, summaries: &[String])
        -> Result<String, String> { .. }
}
```

청크가 3개보다 많거나 적을 수 있으므로 **워커 수를 3으로 고정하지 않는다** — 제안의 "1·2·3번"은
예시로 이해한다.

### 4.3 ⚠ 하드웨어 제약 — VRAM 6GB가 청크 크기 전제를 무너뜨린다

**사용자 확인(2026-07-26): 이 시스템의 실행 환경은 VRAM 6GB다.** 이 제약이 제안의 "8k~16k 청크"
전제와 직접 충돌한다.

#### 왜 충돌하는가

`num_ctx`를 키우면 **KV 캐시가 VRAM을 추가로 점유**한다. 즉 컨텍스트 확장은 공짜가 아니라
모델 가중치와 같은 VRAM을 두고 경쟁한다.

이 프로젝트는 이미 6GB를 기준으로 모델을 고르고 있다 — `CHANGELOG.md` v0.1.2에 12B급 모델이
"6GB 예산을 살짝 넘겨 일부 레이어가 시스템 RAM으로 밀린다"는 기록이 있다. **모델 가중치만으로도
빠듯한 상태**이므로, 여기서 `num_ctx`를 8k~16k로 올리면 KV 캐시가 남은 여유를 잠식해 더 많은
레이어가 시스템 RAM으로 밀리고 속도가 급격히 떨어진다.

#### 더 제약이 심한 이유 — `num_ctx`는 요청마다 바꿀 수 없다

"논리오류 검증만 큰 `num_ctx`를 쓰면 되지 않나"는 해법이 통하지 않는다. `CHANGELOG.md` v0.1.2에
기록된 대로, **KV 캐시는 모델 로드 시점에 할당되므로 실행 중인 모델의 컨텍스트 크기를 바꾸려면
모델을 다시 로드해야 한다**(v0.1.2에서 "Apply 버튼"이 도입된 이유가 바로 이것이다).

따라서:

| 시도 | 결과 |
|---|---|
| 에이전트마다 다른 `num_ctx` 사용 | 매번 모델 리로드 → 수 초~수십 초 지연. 파이프라인이 에이전트를 여러 번 거치므로 비현실적 |
| **단일 `num_ctx`를 모든 에이전트가 공유** | ✅ 현실적인 유일한 선택 |

즉 `num_ctx`는 **VRAM이 허용하는 상한 안에서 한 번 정해 고정**해야 하고, 모든 에이전트(전처리부·
Taxonomy·Research·검증·논리오류 검증·최신화·SalesCS)가 그 하나의 예산을 나눠 쓴다.

#### 조치

1. **청크 크기 고정값 폐기** — 제안의 "8k~16k"를 상수로 두지 않는다. 4.4절의 `chunk_size_for(num_ctx)`
   파생 방식을 채택한다(원래 조치안 그대로이며, VRAM 제약이 이 판단을 더 강하게 뒷받침한다).
2. **실측 후 확정(O-29)** — 6GB에서 사용 모델이 실제로 감당 가능한 `num_ctx` 상한을 측정한다.
   이 값이 정해지기 전에는 청크 크기도 확정할 수 없다.
3. **예산 경쟁을 인지한다** — 하나의 `num_ctx`를 여러 용도가 나눠 쓴다:

```
[ num_ctx 총예산 ]
  ├─ 시스템/역할 프롬프트
  ├─ 논리오류 26종 정의 (E-1 결정으로 전량 주입 -- 06 §프롬프트 공급 참고)
  ├─ 검사·분석 대상 본문 (재무 수치 포함, 09 §3.3 우선순위)
  └─ 출력 여유분
```

**E-1(26종 전량 주입) 결정과 이 제약이 같은 예산을 두고 경쟁한다.** 정의가 예산을 많이 차지할수록
정작 검사할 본문이 들어갈 자리가 줄어든다 — 이 때문에 06 문서에 **프롬프트용 축약본**을 별도로
두기로 했다(06 참고).

### 4.4 `num_ctx` 기본값이 4096이다

[config.rs:38-41](src-tauri/src/config.rs:38)의 기본 설정:

```rust
Err(_) => AppConfig {
    context_size: 4096,   // ← 기본값
    ..Default::default()
},
```

제안은 **8k~16k 청크**를 전제하는데, 현재 기본 `num_ctx`는 **4096**이다. 이 상태로 8k 청크를
보내면 Ollama가 컨텍스트를 넘긴 부분을 **조용히 잘라낸다** — 에러도 나지 않고, 요약은 생성되지만
청크 뒷부분이 통째로 누락된 요약이 나온다. D-04와 똑같은 유형의 silent-wrong이다.

**조치**: 청크 크기를 `num_ctx`에서 **파생**시킨다. 고정 상수로 두지 않는다.

```rust
/// 청크 크기는 num_ctx의 20~25%로 잡는다(가이드라인, 11_컨텍스트_예산_진단.md §1).
/// 나머지는 시스템 프롬프트 / 논리오류 26종 프롬프트판(06) / 출력 여유가 나눠 쓴다.
/// 8k~16k는 num_ctx가 그만큼 확보된 경우에만 성립하는 값이므로 상수로 두지 않는다.
fn chunk_size_for(num_ctx: u32) -> usize {
    (num_ctx / 4) as usize   // 25% -- 예: 4096 -> 1024, 16384 -> 4096
}
```

> **비율이 60%에서 25%로 조정된 이력**: 초안에서는 여유를 40%만 뒀으나, E-1(논리오류 26종 전량
> 주입) 결정으로 프롬프트가 차지하는 몫이 커지면서 청크 비중을 낮췄다. 하나의 `num_ctx`를
> 여러 용도가 나눠 쓴다는 사실이 확인된 결과다(11 §4의 `ContextBudget` 참고).

### 4.4 Reduce 단계 오버플로 — "8k 안에 들어온다"는 보장이 없다

제안은 요약본 총합이 8k 안전 구간에 들어온다고 전제하지만, 청크 수가 많으면 성립하지 않는다
(예: 20청크 × 500토큰 = 10k). 대용량 PDF에서 실제로 발생 가능한 상황이다.

**조치**: 요약본 총합이 예산을 넘으면 **Reduce를 계층적으로 반복**한다.

```
청크 20개 → 요약 20개 (총 10k, 예산 초과)
              │
              ▼ 1차 Reduce: 5개씩 묶어 4그룹
          중간 요약 4개 (총 2k)
              │
              ▼ 2차 Reduce
            최종 통합본
```

## 5. 시험 적용 계획

| 단계 | 내용 | 성공 판정 |
|---|---|---|
| 1 | 전처리부에만 적용 (§3, PDF·엑셀 대용량 파일) | 컨텍스트 초과 없이 전체 문서가 요약에 반영되는가 |
| 2 | 청크 크기를 `num_ctx` 파생값으로 구현 (4.3절) | `num_ctx` 4096에서도 조용한 절단이 발생하지 않는가 |
| 3 | 계층적 Reduce 구현 (4.4절) | 청크 20개 이상 문서에서 Reduce 단계가 예산을 넘지 않는가 |
| 4 | 손실 측정 | 원본의 핵심 수치(재무제표 계정 금액 등)가 최종 통합본까지 살아남는가 — **G-2 목적상 가장 중요** |

### 4단계가 핵심인 이유

Map 단계에서 "핵심 키워드·수치·주장만 압축"하라고 지시하지만, **어떤 수치가 핵심인지는 청크
하나만 봐선 알 수 없다.** 재무제표를 쪼갰을 때 특정 청크의 워커는 자기가 본 계정과목이 나중에
지표 산출(§3.2 `Metrics`)에 쓰일지 모른 채 버릴 수 있다.

**보완안**: Map 프롬프트에 "이 문서는 재무제표이며, 최종적으로 산출할 지표는 ○○○이다"라는
**전역 목표(global objective)** 를 함께 제공한다 — 각 워커가 무엇을 남겨야 할지 판단할 근거를 준다.
이는 [하이브리드_에이전트_RAG.md](../하이브리드_에이전트_RAG.md)의 부모-자식 청크에서
"자식으로 검색하고 부모로 문맥 보존"하는 것과 같은 취지의 보완이다.
