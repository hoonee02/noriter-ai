## 1. 왜 비상장 기준이 맞는가

상장사는 OpenDART에서 정형화된 공시 데이터를 받지만, 비상장사는 이런 신용정보 보고서 형태로만
정보가 존재한다. 두 집단의 **정보 가용량이 다르다.**

| 기준 선택 | 결과 |
|---|---|
| 상장사 기준(DART 전 필드) | 비상장사는 빈 필드가 태반 → 스키마 대부분이 무의미 |
| **비상장사 기준** ✅ | 상장사는 이 스키마의 **상위집합** → 빈칸 없이 채워지고, 추가 정보는 얹으면 됨 |

즉 **정보가 가장 적은 쪽을 공통 최소 스키마로 삼는 것**이 옳다. 이래야 두 집단을 같은 틀로
비교·집계할 수 있다.

## 3. 발견 — 생명주기가 두 축이다

07 문서 C항목의 생애주기와 이 자료의 생명주기는 **서로 다른 축**이다. 하나로 합치면 안 된다.

| 축 | 값 | 성격 | 출처 |
|---|---|---|---|
| **법적 생명주기** (신규) | 설립 / 운영 / 변경(구조조정) / 해산·청산 | 등기·법률상 상태 | 법인등기, 상법 |
| **사업 생애주기** (기존 07 §C) | 시장진입기 / 성장기 / 성숙기 / 쇠퇴기 | 사업 성숙도 판단 | 분석적 추정 |

예를 들어 **법적으로는 "운영" 중이면서 사업적으로는 "쇠퇴기"** 일 수 있고, 합병으로 "변경"
단계에 있으면서 "성장기"일 수도 있다. 두 값을 각각 보관한다.

> 법적 생명주기는 **등기 정보에서 사실로 확인**되므로 신뢰도 `Stated`, 사업 생애주기는
> 분석적 판단이므로 `Inferred`가 자연스럽다.

## 4. 09 재무수치 문서 확장안

### 4.1 `Account` 보완 — 자본금 누락

현재 09 §2의 표준 계정 9종에 **자본금(납입자본금)** 이 빠져 있다. 자료의 요약 재무상태표는
`자산총계 / 부채총계 / 자본금 / 자본총계` 4종을 기본으로 삼는데, 자본금은 자본총계와 다른
개념(주주 납입 액면총액 vs 자본 전체)이므로 별도 계정이 필요하다.

```rust
pub enum Account {
    // 기존 9종 ...
    PaidInCapital,   // 자본금 -- 신규
}
```

### 4.2 `Metrics` 확장 — 요약 12종을 기본으로

상세 재무비율은 약 200종에 달해 전부 담을 수 없다. 자료가 **"요약 재무비율"로 따로 추려둔 12종**이
실용적 기본 집합이다.

| 카테고리 | 지표 |
|---|---|
| 성장성 | 총자산증가율 · 매출액증가율 · 순이익증가율 |
| 수익성 | 영업이익률 · ROE · ROIC |
| 안정성 | 부채비율 · 이자보상배수 · 차입금의존도 |
| 활동성 | 매출채권회전율 · 재고자산회전율 · 총자본회전율 |

현재 09 `Metrics`의 5종(영업이익률·순이익률·ROE·부채비율·유동비율)과 비교하면 **성장성·활동성
카테고리가 통째로 빠져 있었다.** 시계열 비교(L3 비교값)를 하려면 성장성 지표가 필수다.

> 나머지 상세 비율(약 200종)은 **필요 시 계산하는 파생값**으로 두고 저장하지 않는다 — L1 원천값이
> 있으면 언제든 계산 가능하므로, 전부 저장하면 09 §1의 5요소를 200번 반복해야 한다.

### 4.3 단위 표기 일치 확인

자료의 요약 재무상태표가 **"(단위: 백만원)"** 으로 명시되어 있고, 생산성 지표도 백만원/천원
단위를 쓴다. 09 §2.5에서 정한 표시 단위(천원·백만원 2종)와 **정확히 일치**한다 — 저장은
원 단위 정밀값, 표시는 백만원/천원이라는 설계가 실제 업계 관행과 맞는다는 확인이다.

## 5. 신규 영역 — 신용정보 (설계에 없던 것)

현재 설계에는 **리스크·신용 관련 정보를 담을 자리가 아예 없다.** G-1(기업 다각도 분석) 목적에
비추면 중요한 공백이다.

| 항목 | 성격 |
|---|---|
| 연체·신용도판단·공공정보 | 재무 건전성의 선행 지표 |
| 당좌거래정지 이력 | 결제 능력 위험 신호 |
| 휴폐업 정보 | 존속 여부 |
| 회생절차·워크아웃 | 부실 진행 상태 |
| 행정처분 | 규제 리스크 |

**설계 반영 방향**: 07 기업 옵션에 그룹을 추가하기보다, **별도 리스크 영역**으로 분리하는 것이
맞다 — 옵션은 "해당되면 붙이는 정적 속성"인 반면, 신용정보는 **시점이 있는 사건(event)** 이고
변동을 추적해야 하기 때문이다. 09의 `Period` 개념이 여기에도 필요하다.

### 5.1 프로토타입 범위 — 요약 필드만 (O-34 확정, 2026-07-26)

**사용자 결정**: 프로토타입에서는 `CreditRiskSummary`라는 **현재 상태 위주의 요약 필드만**
포함하고, **복잡한 신용 사건 이력은 Phase 2로 이관**한다.

| 구분 | 프로토타입 (Phase 1) | Phase 2 |
|---|---|---|
| 데이터 성격 | **현재 상태 스냅샷** | 시계열 사건 이력 |
| 저장 형태 | 단일 요약 구조체 | 사건 레코드 + `Period` |
| 예 | "현재 휴폐업 여부 = 정상" | "2024-03 휴업 → 2024-09 영업재개" |

```rust
/// Phase 1 -- 현재 상태만 담는 요약. 이력·시점 추적은 하지 않는다.
pub struct CreditRiskSummary {
    pub credit_grade: Option<String>,        // 기업신용등급
    pub is_operating: Option<bool>,          // 휴폐업 여부 (현재 상태)
    pub has_overdue: Option<bool>,           // 연체 정보 존재 여부
    pub has_rehabilitation: Option<bool>,    // 회생·워크아웃 진행 여부
    pub checked_at: String,                  // 이 요약을 확인한 시점
}
```

**이 축소가 타당한 이유**: 신용 사건 이력을 제대로 다루려면 사건 유형별 스키마·시계열 저장·
변동 감지가 모두 필요한데, G-1(기업 다각도 분석)의 1차 목표에는 **"현재 위험한가"** 만
답해도 충분하다. `checked_at`을 남겨 요약이 언제 기준인지는 잃지 않는다.

> **저장 위치 확정 (RD-06 해소, 2026-08-02)**: **기업 단위 `WikiEntry`의 필드**로 붙인다
> (`#[serde(default)] pub credit_risk: Option<CreditRiskSummary>`). 별도 저장소는 만들지 않는다 —
> Phase 1은 기업당 스냅샷 1건뿐이라 저장소를 새로 만들 실익이 없고, 갱신은 `Refresh`
> (설계서 §8.1 = 기간이 다른 레코드 추가)로 이미 처리된다. **분리 신호는 두 개**이며 둘 다
> Phase 2에서 함께 온다: ① 신용 사건 이력이 1:N이 될 때 ② 신용정보만 따로 잠그는 접근 제어가
> 필요할 때. 상세는 [설계서 §8.4](00_v0.1.5.1_설계서.md).

> ⚠ **민감 정보 취급**: 축소하더라도 신용정보라는 성격은 그대로다. 위키 저장 시 접근 제어가
> 필요할 수 있으며, 이는 [메이커 에반 구성도_확장.md](../메이커%20에반%20Maker%20Evan-구성도_확장.md) §7의
> "권한 분리" 항목과 연결된다. Phase 2에서 이력까지 다루게 되면 이 문제가 커지므로, 그때
> 접근 제어를 함께 설계한다.

## 6. 관계·거래 정보 — 관계 그래프의 실제 재료

자료의 **주요주주 / 관계회사 / 구매처 / 판매처**는 설계 §2.4의 `WikiRelation`(관계 유형을 가진
링크)에 그대로 대응한다. 지금까지 관계 그래프는 "문서 간 참조"만 다뤘는데, 여기서 **기업 간
실제 거래 관계**라는 구체적 재료가 생긴다.

```rust
pub enum RelationKind {
    // 기존: Basis / Reference / Contradicts / PartOf
    Shareholder,   // 주요주주 -- 신규
    Affiliate,     // 관계회사 -- 신규
    Supplier,      // 구매처 -- 신규
    Customer,      // 판매처 -- 신규
}
```

구매처·판매처 항목에 **거래비중(%)** 이 포함되어 있어, 단순 연결이 아니라 **가중치 있는 관계**로
저장할 수 있다. 이는 D-04의 우선순위 판정(09 §3.3)에서 "관련도"를 정하는 실제 근거가 될 수 있다.

## 7. O-28 해결 — DART에 없는 기업의 처리

비상장·해외 기업은 `company_industries`를 공식 조회할 수 없다(설계 §4.1.2).

**확정 조치 (사용자 결정, 2026-07-26)**:

1. 문서 원문을 바탕으로 **추정해서 채운다** — 비워두지 않는다
2. 단, 신뢰도를 **`Inferred`(추정됨)** 로 표시해 나중에 유의해서 볼 수 있게 한다
3. 이 지표 체계(비상장 기준)를 기준 틀로 삼아 정리한다

> `document_industry`(문서 맥락)는 확신이 없으면 비워두는 반면, `company_industries`(기업 업종)는
> 추정해서라도 채우는 이유는 **역할이 다르기 때문**이다. 전자는 없어도 분석이 진행되지만,
> 후자는 기업을 분류·검색하는 기준이라 비어 있으면 그 기업이 어떤 인덱스에도 잡히지 않는다.
> 다만 추정이라는 사실은 반드시 남긴다.

> 그 구조를 반영해 매핑한다.

#### 왜 단순 동의어 사전으로는 안 되는가

D-12를 처음 등록할 때는 "매출액 / 수익(매출액) / 영업수익" 같은 **표기 변형** 문제로 봤다.
그러나 참조 자료를 보면 더 근본적인 문제가 있다 — **같은 라벨이 상위 항목에 따라 완전히 다른
계정을 가리킨다.**

| 라벨 | 상위 경로 A | 상위 경로 B | 성격 차이 |
|---|---|---|---|
| 급여 | 손익계산서 › 판매비와관리비 | 제조원가명세서 › 노동관계비용 | **기간비용** vs **제조원가 산입** |
| 복리후생비·보험료·운반비·지급수수료·소모품비·차량유지비 | 판매비와관리비 | 제조원가명세서 › 경비 | 위와 동일한 이분 |
| 매출액·자산총계·자본금·당기순이익 | 요약 재무제표 (자사) | 구매처/판매처 현황 | **주체가 다른 기업** |
| 매출액·총자산·영업이익 | 요약 재무제표 (자사) | 동종업계 경영규모 비교 | 자사 vs 비교군 |
| 감사의견 | 재무상태표 | 손익계산서 / 제조원가명세서 | 각 재무제표별로 따로 존재 |

**판관비의 급여와 제조원가의 급여를 같은 계정으로 합치면 영업이익이 틀어진다** — 전자는 그대로
비용 처리되지만 후자는 제품원가에 산입돼 재고로 남을 수 있기 때문이다. 라벨만 보고 매핑하면
이런 오류가 조용히 들어온다(D-04·D-08과 같은 부류의 silent-wrong).

#### 매핑 구조 — (경로 + 라벨) → (계정 + 주체)

```rust
pub struct AccountMapping {
    /// 자료상 상위 경로. 같은 라벨이라도 경로가 다르면 다른 계정이다.
    /// 예: ["손익계산서", "판매비와관리비", "급여"]
    ///     ["제조원가명세서", "노동관계비용", "급여"]
    pub path: Vec<String>,
    /// 원본 라벨 (표기 변형 포함 -- 여기서 동의어를 흡수한다)
    pub labels: Vec<String>,
    /// 매핑 결과 계정
    pub account: Account,
    /// 이 수치가 누구의 것인가 -- 아래 설명 참고
    pub subject: FigureSubject,
}

/// 참조 자료에는 자사 외 기업의 재무 수치도 함께 실린다(거래처 현황·동종업계 비교).
/// 주체를 구분하지 않으면 타사 매출액이 자사 값으로 섞인다 -- D-05와 같은 유형의 혼입이다.
pub enum FigureSubject {
    Subject,          // 분석 대상 기업 본인
    Counterparty,     // 구매처·판매처 등 거래 상대
    Peer,             // 동종업계 비교 대상
    IndustryAverage,  // 업종 평균·업계순위
}
```

#### 주체(`FigureSubject`) 구분이 특히 중요한 이유

거래처 현황·업계순위 항목에는 **다른 기업의 매출액·자산총계·순이익**이 함께 실린다. 이를
`FigureSubject` 없이 저장하면:

- 자사 분석에 거래처 수치가 섞여 들어간다 (D-05 기업 스코프 혼입과 동일한 사고)
- 검증 에이전트(§7.1)가 "위키에 그 숫자가 있다"는 이유로 **오염된 인용을 `Confirmed` 판정**한다

거꾸로, 주체를 제대로 구분해 두면 **거래처 재무 정보가 관계 그래프(§6)의 가중치**로 활용 가능한
자산이 된다. 같은 데이터가 구분 여부에 따라 오염원이 되기도 하고 자산이 되기도 한다.

#### 매핑 작업 순서

1. 자료의 **트리 구조를 그대로 경로로 옮긴다** (평탄화하지 않는다)
2. 경로 말단의 라벨마다 `Account` 열거값을 배정한다 — 대응 계정이 없으면 `Account` 확장
3. 같은 라벨이 여러 경로에 나타나면 **각각 별도 매핑**으로 등록한다
4. 각 매핑에 `FigureSubject`를 지정한다
5. 표기 변형(동의어)은 `labels` 배열에 모은다 — 경로가 같은 것끼리만 묶는다

### 8.4 요약 12종의 계산 가능성 점검 (O-35 분석)

§4.2에서 요약 재무비율 12종을 기본 집합으로 정했다. 그런데 **현재 `Account` 계정으로 실제
계산이 되는지** 확인해 보면 절반이 불가능하다.

| 요약 지표 | 필요한 원천값 | 현재 확보 여부 |
|---|---|---|
| 총자산증가율 | 자산총계 (2개 기간) | ✅ (시계열 필요) |
| 매출액증가율 | 매출액 (2개 기간) | ✅ (시계열 필요) |
| 순이익증가율 | 당기순이익 (2개 기간) | ✅ (시계열 필요) |
| 영업이익률 | 영업이익 · 매출액 | ✅ |
| ROE | 당기순이익 · 자본총계 | ✅ |
| 총자본회전율 | 매출액 · 자산총계 | ✅ |
| **ROIC** | 투하자본 | ❌ **없음** |
| **이자보상배수** | 이자비용 | ❌ **없음** |
| **차입금의존도** | 차입금(단기+장기) | ❌ **없음** |
| **매출채권회전율** | 매출채권 | ❌ **없음** |
| **재고자산회전율** | 매출원가 · 재고자산 | ❌ **둘 다 없음** |

**12종 중 5종이 계산 불가**다. 원인은 비율 목록을 먼저 정하고 원천값을 나중에 본 데 있다 —
순서가 뒤집혀 있었다.

#### 추가 확보가 필요한 L1 계정

```rust
pub enum Account {
    // 기존 9종 + PaidInCapital(§4.1)
    // ── 요약 12종 계산을 위해 추가 필요 ──
    CostOfSales,          // 매출원가
    TradeReceivables,     // 매출채권
    Inventories,          // 재고자산
    Borrowings,           // 차입금 (단기+장기 합산 또는 각각)
    InterestExpense,      // 이자비용
    // ROIC의 투하자본은 위 계정들로부터 산출 가능한지 별도 확인 필요
}
```

모두 참조 자료의 상세 재무제표(재무상태표 유동자산·부채, 손익계산서 매출원가·영업외비용)에
존재하므로, **자료에서 뽑을 수 있는데 우리가 목록에 안 넣었을 뿐**이다.

#### 시계열 요구 — 증가율 3종은 2개 기간이 필요하다

성장성 지표 3종은 전기 값이 있어야 계산된다. 09 §1의 5요소 중 **기간(④)이 다른 같은 계정을
2건 이상 보관**해야 한다는 뜻이며, 이는 D3 §6 최신화·버전관리의 `Refresh`(같은 사실의 최신
수치로 갱신) 처리와 충돌할 수 있다 — **갱신 시 이전 값을 덮어쓰면 증가율을 계산할 수 없다.**

> ✅ **확정 (RD-02 / O-35-1 해소, 사용자 결정 2026-08-02)**: `Refresh`는 "이전 값을 버리는 갱신"이
> 아니라 **"기간이 다른 새 레코드 추가"** 다. 09 §2의 L3(비교값) 계층이 성립하려면 과거 기간 값이
> 남아 있어야 한다. 유효 정의는 [설계서 §8.1](00_v0.1.5.1_설계서.md)에 있다 — `Correction`과의
> 판정 기준(기간이 같은지)도 거기에 표로 정리했다.

## 9. 재검 결과 (2026-07-26, 원본 재확인)

원본을 트리 구조로 다시 확인하면서 **정정 4건 · 신규 발견 4건**이 나왔다.

### 9.1 정정 — 잘못 정리했던 것

#### ① 현금흐름 항목을 1종으로 축소한 것은 오류

09 §2의 L1 목록에 `OperatingCashFlow`(영업활동현금흐름) 1종만 넣었으나, 원본의 실제 구조는 다르다.

| 원본 위치 | 실제 내용 |
|---|---|
| **요약 현금흐름분석** | 현금영업이익 · 경상활동후의 현금흐름 · 투자활동후의 현금흐름 · 현금흐름등급 (4종) |
| 상세 **현금 흐름표** | **세부 항목이 없다** — 표 제목과 설명만 존재 |

두 가지 문제가 있다.

- **매핑 불일치**: `OperatingCashFlow`에 정확히 대응하는 원본 항목이 없다. 가장 가까운 것은
  **"경상활동후의 현금흐름"** 이며, 명칭이 다르므로 매핑을 명시해야 한다.
- **현금영업이익 누락**: 원본 설명에 따르면 *영업이익에 감가상각비 등 비현금성 비용을 더해 산출한
  현금 기준 영업이익*이다. 이는 **EBITDA에 준하는 값**으로, §8.4에서 "감가상각비를 제외했으므로
  EBITDA 계열은 포기"라고 판단한 것을 **뒤집을 수 있는 항목**이다 — 감가상각비를 따로 받지 않고도
  현금 기준 수익성을 확보할 수 있다.

> **결정 필요(O-39)**: L1을 17종에서 **19종으로 확장**할지 — `CashOperatingProfit`(현금영업이익),
> `CashFromOperations`(경상활동후의 현금흐름) 추가. 요약 12비율만 보면 불필요하지만, 원본이
> 이 둘을 "요약" 세트에 넣었다는 것은 중요도가 높다는 신호다.

#### ② 재무진단 5축은 요약 재무비율 4축과 다르다

§2 표에 "재무진단 5개 축"이라고만 적고 차이를 짚지 않았다. 두 분류는 실제로 어긋난다.

| 요약 재무비율 (4축) | 재무진단 (5축) |
|---|---|
| 성장성 · 수익성 · **안정성** · 활동성 | 성장성 · 수익성 · **재무구조 · 부채상환능력** · 활동성 |

재무진단은 요약의 "안정성"을 **재무구조**(자본 조달 구조의 건전성)와 **부채상환능력**(현금창출력
대비 상환 능력)으로 **쪼갠다**. 지표를 그룹핑할 때 어느 체계를 따를지 정해야 한다.

> ⚠ **여기서 한 번 더 놓친 것 (RD-03, 2026-08-02 해소)**: 위 표는 요약 4축과 재무진단 5축만
> 비교했는데, **상세 재무비율은 5카테고리(성장성·수익성·안정성·활동성·생산성)** 다. O-40에서
> 재무진단 5축을 채택하면서 **생산성이 탈락한다는 사실을 아무도 짚지 않았다** — 상세 5개와
> 재무진단 5개가 "둘 다 5개"라 표면적으로 일치해 보였기 때문이다(99 §5 함정 #11).
>
> | 상세 재무비율 (5카테고리) | 재무진단 (5축) | 최종 채택 (**6축**) |
> |---|---|---|
> | 성장성·수익성·**안정성**·활동성·**생산성** | 성장성·수익성·**재무구조·부채상환능력**·활동성 | 성장성·수익성·재무구조·부채상환능력·활동성·**생산성** |
>
> **조치**: 생산성을 6번째 축으로 되살렸다 — 지표 15종 → **18종**([09 §2](09_재무수치_정의.md)).
> **개수가 같다고 같은 게 아니다**는 것이 이 건의 교훈이다.

#### ③ 계속사업이익(손실) 누락

상세 손익계산서의 손익 흐름은 `법인세차감전순이익 → 법인세비용 → 계속사업이익 → 당기순이익`
순이다. **중단사업이 있으면 계속사업이익 ≠ 당기순이익**이므로, 계속사업 기준 수익성을 보려면
별도 계정이 필요하다. 현재 L1 17종에 없다.

#### ④ 신용 정보가 두 영역에 분산되어 있다

§5에서 "신용정보" 단락만 다뤘으나, **기업개요 영역에도 신용 관련 항목이 있다**.

| 영역 | 항목 |
|---|---|
| 기업개요 | 기업신용등급 · **EW등급**(조기경보) · **CREVIEW**(신용조회 검토결과) · 휴폐업정보 · 법인등기정보 |
| 신용정보 | 연체·신용도판단·공공정보·당좌거래정지·회생/워크아웃·행정처분 등 |

휴폐업정보·법인등기정보는 **양쪽에 중복 등장**한다. §5.1의 `CreditRiskSummary`를 채울 때
두 영역을 모두 훑어야 한다.

### 9.2 신규 발견 — 활용 가능한 것

#### ① 매출구성의 "매출액구성비(%)" → O-14 가중치 근거

O-14(복수 산업 소속 vs 모호성)를 논의할 때 *"매출 비중 같은 근거가 뉴스 원문에는 없다"* 고
했는데, **이 자료에는 있다.** 매출구성 단락이 `사업부문 / 주요제품 / 매출액구성비(%)`를 제공한다.

따라서 `company_industries`를 단순 목록이 아니라 **가중치 있는 목록**으로 만들 수 있다.

```rust
pub struct WeightedIndustry {
    pub section: IndustrySection,
    pub revenue_share: Option<f64>,   // 매출액구성비 -- 주력 산업 판정 근거
}
```

주력 산업을 정할 수 있으면 D-08 조치안 ④의 **제목 중복 구분자**(`영업이익률(제조업)`)에서
"복수 산업 기업은 관련도 최상위 산업 하나를 쓴다"는 규칙이 **실제로 계산 가능**해진다.

#### ② 결산월 필드 존재 → Guard 5 구현 가능 확인

09 §2.6 Guard 5(시계열 불연속 탐지)는 `fiscal_month_count`를 요구하는데, 기업개요에
**"15. 결산월"** 이 있다. 결산기 변경을 실제로 탐지할 수 있다는 확인이다.

#### ③ 각 단락에 "취지" 설명이 붙어 있다

24개 단락 전부에 *"취지: …를 정리한 단락입니다"* 형태의 목적 설명이 있다. 이는 **에이전트
프롬프트에 그대로 쓸 수 있는 재료**다 — 각 영역을 왜 보는지 LLM에 설명할 때 별도로 작성할
필요가 없다.

#### ④ A회사 예시 데이터 존재

법인 생명주기 각 단계에 구체 예시(설립 시점·자본금·증자·배당·본점 이전·대표이사 변경 등)가
