| 2 | 커맨드가 오케스트레이터를 큐에 등록 | 설계 §4.1 `queue::run_queued(app,"orchestrator",..)` | 큐 항목 1개 등록, `run_lock` **획득** | ✅ |
| 3 | `analyze_company` 내부에서 재무 서브에이전트 호출 | 설계 §4.1 `run_agent(..)` | — | — |
| 4 | 서브에이전트가 자기 LLM 호출을 큐에 등록 | 설계 §4.1 → `queue.rs:39` `run_queued` | `queue.rs:57` `state.run_lock.lock().await` 재시도 | ❌ |

**❌ 4단계 상세 — 교착(deadlock)**

`queue.rs:20`의 `run_lock: tokio::sync::Mutex<()>` 은 **재진입 불가(non-reentrant)** 뮤텍스다.
2단계에서 오케스트레이터가 획득한 가드는 `analyze_company`가 반환될 때까지 유지되는데,
`analyze_company`는 4단계에서 같은 락을 다시 기다리므로 **영원히 반환되지 않는다.**

- 사용자 관점: 응답 없음. 📋 큐 패널에 `orchestrator`(running) + `agent`(waiting) 2건이 영구 표시.
- 복구 경로 없음 (취소 기능 부재 → D-16과 연쇄).

**대조 확인 — v0.1.4는 왜 멀쩡한가**: `main.rs:104`의 `memory::build_messages(..).await`가
내부적으로 `memory.rs:135`에서 `run_queued`를 쓰지만, 그 호출이 **완전히 끝난 뒤** `main.rs:106`에서
바깥 `run_queued`가 시작된다. 즉 현행은 중첩이 아니라 **순차**다(`telegram.rs:142`→`155`도 동일 패턴).
따라서 이 결함은 기존 버그가 아니라 **v0.1.5 설계가 새로 유입시키는 구조적 결함**이다.
→ **D-01 (Critical)**

| 7 | 위키 저장 시 신규 필드 기록 | `wiki.rs:16` `#[derive(..Deserialize)]` | **`#[serde(default)]` 없음** — 상세는 아래 | ❌ D-02 |

**❌ 7단계 상세 — 기존 위키 무성 손실 (최우선 결함)**

설계 §3.1은 `WikiEntry`에 `relations`/`confidence`/`company`/`period` 4개 필드를 추가한다.
그런데 `wiki.rs:16`의 `WikiEntry`에는 구조체 수준 `#[serde(default)]`가 없다.

1. 사용자의 기존 `wiki/index.json`에는 신규 4개 필드가 존재하지 않음
2. v0.1.5 기동 시 역직렬화 **실패**
3. `wiki.rs:59-64` `load_entries()`가 `.ok()`로 오류를 삼키고 `unwrap_or_default()` → **빈 Vec 반환**
4. 사용자에겐 "위키가 텅 빔"으로 보임
5. 이후 아무 페이지나 저장하면 `wiki.rs:66` `save_entries()`가 그 빈 상태 기준으로 파일을 덮어씀 → **기존 위키 영구 소실**

주목할 점: `config.rs:5-10` 주석에 **정확히 같은 버그를 이미 한 번 겪고 고쳤다**고 기록되어 있다
(“…discarding the user's saved token/model/etc, not just the new field”). `AppConfig`에는 방어가
적용됐지만 `WikiEntry`에는 적용되지 않았고, v0.1.5가 필드를 추가하는 순간 동일 사고가 재현된다.
설계서 미결사항 **O-2(마이그레이션 미정)**가 이 결함의 직접 원인이다.
→ **D-02 (Critical)**

|---|---|---|---|---|
| 8 | 저장된 재무 페이지를 질의로 조회 | `wiki.rs:232` `query()` | `list(state)` **전량** 대상. `company` 필터 없음 → 삼성전자 질의에 타 기업 페이지 혼입 | ❌ D-05 |
| 9 | 컨텍스트 구성 | `wiki.rs:244` | 아래 상세 | ❌ D-04 |

**❌ 9단계 상세 — 임계값 all-or-nothing**

```rust
let context = if full_context.chars().count() < 6000 { full_context } else { index_context };
```

재무제표 한 건만 들어와도 6000자를 쉽게 넘긴다. 넘는 순간 **본문 전체가 통째로 버려지고**
제목/요약/태그만 모델에 전달된다 → 실제 재무 수치가 모델에 도달하지 않은 채 답변이 생성된다.
사용자는 답을 받으므로 정상 동작으로 오인한다(전형적 silent-wrong).

또한 구성도 §2.5가 요구하는 **"인덱스를 먼저 읽고 필요한 하위 문서 2~3개만 선택적으로 펼친다"**가
현행 코드에는 존재하지 않는다 — 전량이냐 인덱스냐의 2택뿐이다. 설계 §4.3이 `router.rs`로
이를 해결하려 했으나 D-19대로 규칙이 비어 있어, 현 상태로는 체크리스트 **C-2 미충족**.
→ **D-04 (High)**

## W-5. (횡단) 분석 3회 반복 후 위키 상태 점검

| # | 단계 | 통과 지점 | 정적 관찰 | 판정 |
|---|---|---|---|---|
| 1 | 1회차 질의 실행 | `wiki.rs:232` `query()` | 정상 | ✅ |
| 2 | 답변 저장 여부 | `wiki.rs:258-267` | **무조건** 새 페이지로 저장 (`tags:["query"]`, `source:"query"`) — 조건·승인 없음 | ❌ D-03 |
| 3 | 2회차 질의의 컨텍스트 | `wiki.rs:233` `list(state)` | 1회차 답변 페이지가 **컨텍스트에 포함됨** | ❌ D-03 |
| 4 | 3회차 | 동일 | 2회차 답변까지 누적 포함 | ❌ D-03 |

**❌ 2~4단계 상세 — 자기오염(self-contamination) 루프**

`query()`는 생성된 답변을 예외 없이 위키 페이지로 승격시키고, 그 페이지는 다음 질의의 컨텍스트가 된다.
즉 **LLM이 추론한 내용이 다음 답변의 "근거"로 재사용**된다. 재무 분석 맥락에서 이는 특히 위험하다 —
`Inferred`로 도출된 수치가 몇 턴 뒤에는 위키에 적힌 사실로 취급되어 `Stated`처럼 인용될 수 있다.

이는 구성도 §2.5/§4가 새로 명시한 원칙 — *"질의 결과를 일단 로그로만 쌓아두고, 정식 지식으로의
승격은 사람이 검토 후 결정"* — 과 정면으로 배치된다. 체크리스트 **C-4·C-5 위반**.
→ **D-03 (Critical)**

| # | 단계 | 통과 지점 | 정적 관찰 | 판정 |
|---|---|---|---|---|
| 5 | 페이지 증가에 따른 컨텍스트 변화 | `wiki.rs:244` | 질의 N회 = 페이지 N개 누적 → 6000자 임계 조기 도달 → 이후 **모든** 질의가 인덱스 전용 모드로 전락 (D-04 가속) | ❌ D-03↔D-04 연쇄 |
| 6 | `lint` 실행 | `wiki.rs:280` | 결과를 페이지로 저장하지 않고 로그만 남김 — 본문 오염 없음 | ✅ C-8 |
| 7 | `lint` 판정 품질 | `wiki.rs:286-297` | 전체 목록을 기업 구분 없이 점검 → "삼성 매출 ≠ LG 매출"을 모순으로 오탐할 소지. company 스코프 미인지 | ❌ D-14 |
| 8 | 구조화 단계 재확인 | `wiki.rs:161-193` `parse_structured` | 아래 상세 | ❌ D-08 |

**❌ 8단계 상세 — 구조화 파서 취약점**

```rust
if let Some(rest) = line.strip_prefix("TITLE:") { ...
} else if line.trim() == "BODY:" { in_body = true; }
```

- `BODY:` 는 **단독 라인 정확 일치**만 인정한다. 소형 로컬 모델이 흔히 쓰는 `BODY: 본문시작…`
  형태(같은 줄에 내용 이어 쓰기)는 매칭되지 않아 `in_body`가 끝까지 `false` → **본문이 빈 문자열로 저장**된다.
- `TITLE:`/`SUMMARY:`/`TAGS:`는 `strip_prefix`를 trim 없이 적용해, 선행 공백(`  TITLE:`)이나
  마크다운 강조(`**TITLE:**`) 형태를 놓친다.
- `wiki.rs:189-192`에 제목 공백 시 `"제목 없음"` 폴백은 있으나 **본문에는 폴백이 없다** →
  빈 본문이 그대로 저장되고 오류도 나지 않는다.

재무제표 본문이 곧 수치 그 자체인 G-2에서 이 조용한 실패는 치명적이다.
→ **D-08 (High)**
