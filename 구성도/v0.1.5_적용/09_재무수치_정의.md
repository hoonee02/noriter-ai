# 재무 수치 정의 문서

> **왜 이 정의가 필요한가**: [03_결함기록부.md](03_결함기록부.md) D-04는 "재무 수치가 조용히
> 미전달"되는 결함이다. 이를 고치려면 라우터가 **"무엇은 절대 빠뜨리면 안 되는가"** 를 알아야
> 하는데, 그 "무엇"이 정의되어 있지 않았다. 이 문서가 그 공백을 메운다.
>
> 즉 이 문서는 D-04 해결의 **선결 조건**이며, 동시에
> [08_MapReduce_청킹_시험적용.md](08_MapReduce_청킹_시험적용.md)의 청크 경계 규칙과
> §7.1 검증 에이전트의 팩트체크 대상을 함께 규정한다.

---

## 1. 핵심 정의 — 재무 수치는 "숫자 하나"가 아니다

**재무 수치(Financial Figure)** 는 숫자 단독이 아니라, 그 숫자를 해석 가능하게 만드는
**5개 요소가 결합된 하나의 불가분 단위**다.

```
                    ┌─────────────────────────────┐
                    │      재무 수치 1건            │
                    ├─────────────────────────────┤
   ① 계정명    ───► │  "영업이익"                   │
   ② 금액      ───► │  35,000                      │
   ③ 단위·통화 ───► │  백만원 (KRW)                 │  ← 빠지면 숫자가 무의미 (2.5절: 2종으로 제한)
   ④ 기간·시점 ───► │  2025 회계연도 (FY)           │  ← 빠지면 비교 불가
   ⑤ 출처·신뢰도 ─► │  손익계산서 / Stated          │  ← 빠지면 검증 불가
                    └─────────────────────────────┘
```

### 왜 5요소를 묶어야 하는가

| 빠진 요소 | 결과 |
|---|---|
| ③ 단위 | "매출 300"이 300억인지 300조인지 알 수 없다 — **틀린 것보다 나쁘다.** 모델은 임의로 단위를 가정해 그럴듯한 분석을 만들어낸다 |
| ④ 기간 | 전기 대비 증감을 계산할 수 없고, 서로 다른 연도 수치를 같은 해로 오인해 비교한다 |
| ⑤ 출처·신뢰도 | 원본에 적힌 값(`Stated`)과 계산·추정값(`Inferred`)이 구분되지 않아, 추론이 사실로 굳는다(D-03과 같은 위험) |

> **불가분성 원칙**: 5요소 중 하나라도 빠진 채로 모델에 전달하느니, **그 수치를 아예 전달하지
> 않는 편이 낫다.** 불완전한 수치는 모델이 빈칸을 상상으로 메우게 만든다.

## 2. 계층 — 세 종류의 재무 수치

신뢰도 등급(설계 §2.4)과 1:1로 대응한다.

| 계층 | 정의 | 예 | 신뢰도 | 출처 |
|---|---|---|---|---|
| **L1. 원천값** | 재무제표에 그대로 적힌 금액 | 매출액 300조, 영업이익 35조 | `Stated` | 원본 문서 |
| **L2. 산출값** | L1으로부터 정해진 공식으로 계산한 지표 | 영업이익률 11.7%, ROE 8.2% | `Inferred` | 계산 |
| **L3. 비교값** | L1·L2를 다른 기간·기업과 대조해 나온 값 | 전년 대비 +12%, 업종 평균 대비 상위 | `Inferred` | 대조 |

#### 현금흐름 (3종) — O-39 확정으로 확장 (2026-07-26)

원본의 "요약 현금흐름분석" 구성을 그대로 따른다. 상세 "현금 흐름표"에는 세부 항목이 없고
현금흐름 값은 전부 이 요약 단락에 있다(12 §9.1).

| # | 계정 | `Account` | 필요 이유 |
|---|---|---|---|
| 17 | 현금영업이익 | `CashOperatingProfit` | **EBITDA 계열 지표군 전체를 여는 열쇠** (아래 참고) |
| 18 | 경상활동후의 현금흐름 | `CashFromOperations` | 영업 현금창출력. 기존 `OperatingCashFlow`를 **이 항목으로 대체**한다 |
| 19 | 투자활동후의 현금흐름 | `CashFromInvesting` | 설비투자 규모 파악 + **FCF 산출**(= 영업 − 투자) |

> **`OperatingCashFlow` 폐기**: 원본에 "영업활동현금흐름"이라는 항목이 없다. 가장 가까운 것이
> "경상활동후의 현금흐름"이므로 명칭을 원본에 맞춘다 — 없는 항목명을 쓰면 매핑 단계에서
> 대응 실패가 나고, D-08 계열의 조용한 누락으로 이어진다.
>
> "현금흐름등급"은 수치가 아니라 등급이므로 L1 계정에 넣지 않는다(별도 평가 지표로 취급).

**현금영업이익이 여는 것 — 감가상각비 없이 EBITDA 계열 확보**

`현금영업이익 = 영업이익 + 감가상각비 등 비현금성 비용`이므로, 감가상각비를 별도로 받지 않고도
아래 지표군이 전부 계산 가능해진다(원본 상세 재무비율에 실제로 존재하는 항목들이다).

| 계열 | 계산 |
|---|---|
| EBITDA마진율 | `CashOperatingProfit` ÷ `Revenue` |
| EBITDA/금융비용 | `CashOperatingProfit` ÷ `InterestExpense` |
| EBITDA/총차입금 | `CashOperatingProfit` ÷ `Borrowings` |
| 현금흐름/매출액 | `CashFromOperations` ÷ `Revenue` |
| FCF/매출액 · FCF/차입금 | (`CashFromOperations` − `CashFromInvesting`) ÷ 각 분모 |

> ⚠ **현금영업이익 ≠ EBITDA**: 엄밀한 EBITDA는 `영업이익 + 감가상각비 + 무형자산상각비`인 반면,
> 현금영업이익의 "비현금성 비용 등"이 정확히 무엇을 포함하는지는 원본 정의에 따른다. **대용 지표로
> 쓰되 EBITDA와 동일시하지 않는다** — 리포트 표기 시 "현금영업이익 기준"임을 명기한다
> (§2.6 Guard 4의 `(기말)` 표기와 같은 취지).

```rust
pub enum Account {
    // 손익계산서 (7)
    Revenue, CostOfSales, OperatingProfit, InterestExpense,
    ProfitBeforeTax, IncomeTaxExpense, NetIncome,
    // 재무상태표 (9)
    TotalAssets, CurrentAssets, TradeReceivables, Inventories,
    TotalLiabilities, CurrentLiabilities, Borrowings, TotalEquity, PaidInCapital,
    // 현금흐름 (3) -- O-39 확정으로 1종에서 확장, OperatingCashFlow는 폐기
    CashOperatingProfit, CashFromOperations, CashFromInvesting,
}
```

#### 시계열 필수 계정 (3종)

성장성 지표는 전기 값이 있어야 계산되므로, 아래 3종은 **최소 2개 기간을 보관**해야 한다.

| 계정 | 대상 지표 |
|---|---|
| `Revenue` | 매출액증가율 |
| `NetIncome` | 순이익증가율 |
| `TotalAssets` | 총자산증가율 |

> ✅ **확정 (RD-02 / O-35-1 해소, 사용자 결정 2026-08-02)**: `Refresh`는 "이전 값 폐기"가 아니라
> **"기간이 다른 레코드 추가"** 다. 판정은 **기간(09 §1 5요소 ④)이 같은지**로 하며, 기간이 다르면
> 금액이 달라도 `Correction`이 아니다. 유효 정의는
> [설계서 §8.1](00_v0.1.5.1_설계서.md)로 옮겼다 — D3 §4는 이력 보존용이라 참조 대상이 아니다.

#### 확정 시 내린 판단

| 항목 | 결정 | 근거 |
|---|---|---|
| 차입금 단기/장기 분리 | **하지 않음** (총액 1종) | 요약 12종에 "단기성차입금/총차입금"이 없다. 필요해지면 그때 분리 |
| 감가상각비 | **제외 (유지)** — 다만 이유가 바뀜 | 처음엔 "EBITDA를 포기하므로 불필요"였으나, O-39로 **현금영업이익을 확보해 EBITDA 계열을 살렸다.** 이제 감가상각비를 따로 받지 않아도 되는 것이지, 지표를 포기한 것이 아니다 |
| 계속사업이익 | **제외 확정** (O-41, 2026-07-26) | 중단사업손익 발생은 **극소수 케이스**다. 이를 위해 L1 수집 파이프라인과 파싱 스펙을 늘리는 것은 비효율이다. 대신 중단사업이 있는 기업이 들어오면 **L2 계산·검증 단계에서** 당기순이익과 손익계산서 세부항목을 대조해 `has_discontinued_operations: true` 플래그로 처리한다 — L1을 비대하게 만들지 않고 특수 케이스를 잡는 방식 |
| 매출총이익 | **제외** | `Revenue - CostOfSales`로 계산 가능 — L1에 둘 이유가 없다 |
| 순운전자본 | **제외** | `CurrentAssets - CurrentLiabilities`로 계산 가능 |
| 종업원수 | **L1 아님** | 재무제표 계정이 아니라 **기업개요 항목**(12 §2 B영역). 생산성 지표는 두 영역을 결합해야 계산된다 — **생산성 축이 실재하므로 이 서술은 유효하다**(RD-03 해소, 2026-08-02. 그전까지는 축이 없는 상태에서 이 문장만 남아 있어 재워크스루 정합성 지적 #2를 받았다) |

> 표준 계정에 매핑되지 않은 원본 계정(`AccountLine.canonical == None`)도 **L1으로 취급한다** —
> 매핑 실패는 분류 문제이지 신뢰도 문제가 아니다. 원본에 적힌 값이라는 사실은 변하지 않는다.

### L2 — 산출 지표: **재무진단 6축** 체계 (O-40 확정 2026-07-26 → RD-03으로 생산성 축 추가 2026-08-02)

> **그룹핑 축 결정**: 요약 재무비율의 4축(성장성·수익성·**안정성**·활동성) 대신
> **재무진단 5축**을 채택한다 — 안정성을 **재무구조**와 **부채상환능력**으로 분리한다.
>
> **이유**: 4축의 "안정성"은 *자본 조달 구조가 건전한가*와 *원리금을 갚을 수 있는가*라는
> 성격이 다른 두 질문을 한 칸에 뭉뚱그린다. 기업 신용분석(G-1)에서 이 둘은 별개 판단이며,
> L1 19종 확보로 이자보상배수·차입금의존도·유동비율이 모두 계산 가능해졌으므로 나눌 실익이 있다.
> 리포트 시각화(레이더 차트 등)에서도 5축이 더 명확한 인사이트를 준다.

| 축 | 지표 | 계산식 |
|---|---|---|
| **성장성** | 매출액증가율 | (당기 `Revenue` − 전기) ÷ 전기 |
| **성장성** | 순이익증가율 | (당기 `NetIncome` − 전기) ÷ 전기 |
| **성장성** | 총자산증가율 | (당기 `TotalAssets` − 전기) ÷ 전기 |
| **수익성** | 영업이익률 | `OperatingProfit` ÷ `Revenue` |
| **수익성** | ROE | `NetIncome` ÷ `TotalEquity` |
| **수익성** | ROIC | 세후영업이익 ÷ (`TotalEquity` + `Borrowings`)<br>세후영업이익 = `OperatingProfit` × (1 − `IncomeTaxExpense` ÷ `ProfitBeforeTax`) |
| **재무구조** | 부채비율 | `TotalLiabilities` ÷ `TotalEquity` |
| **재무구조** | 차입금의존도 | `Borrowings` ÷ `TotalAssets` |
| **재무구조** | 유동비율 | `CurrentAssets` ÷ `CurrentLiabilities` |
| **부채상환능력** | 이자보상배수 | `OperatingProfit` ÷ `InterestExpense` |
| **부채상환능력** | EBITDA/금융비용 | `CashOperatingProfit` ÷ `InterestExpense` |
| **부채상환능력** | EBITDA/총차입금 | `CashOperatingProfit` ÷ `Borrowings` |
| **활동성** | 매출채권회전율 (기말) | `Revenue` ÷ `TradeReceivables` |
| **활동성** | 재고자산회전율 (기말) | `CostOfSales` ÷ `Inventories` |
| **활동성** | 총자본회전율 | `Revenue` ÷ `TotalAssets` |
| **생산성** | 1인당 매출액 | `Revenue` ÷ 종업원수 |
| **생산성** | 1인당 영업이익 | `OperatingProfit` ÷ 종업원수 |
| **생산성** | 1인당 순이익 | `NetIncome` ÷ 종업원수 |

> **5축 전환으로 지표가 12종 → 15종이 되었다.** 새로 들어온 3종(유동비율·EBITDA/금융비용·
> EBITDA/총차입금)은 모두 **이미 확보한 L1으로 계산 가능**하다 — 축을 나누면서 빈 칸이 생기는
> 것이 아니라, 오히려 L1 19종이 지탱할 수 있는 지표를 제대로 배치한 결과다.

#### 생산성 축 추가 — 6축 18종 (RD-03 해소, 사용자 결정 2026-08-02)

**왜 추가하나**: O-40에서 재무진단 5축을 채택할 때 원본 상세 재무비율의 **5카테고리(성장성·
수익성·안정성·활동성·생산성) 중 생산성이 빠진다는 사실을 짚지 않았다.** 둘 다 "5개"라 표면적으로
일치해 보였을 뿐, 재무진단은 안정성을 둘로 쪼개는 대신 생산성을 뺀 구성이었다
([13 §RW-2](13_재워크스루_결과.md)).

그 결과 **Guard 1(§2.6)이 계산하지도 않는 지표를 방어하는 상태**가 되었다. 축을 추가하면
Guard 1과 아래 §2 "확정 시 내린 판단"의 종업원수 항목이 **동시에 정합해진다** — 문서 두 곳이
이미 생산성 축의 존재를 전제하고 있었으므로, 빼는 것보다 넣는 것이 문서 정합성 비용도 작다.

**이 축만 다른 점 — 두 영역을 결합한다**

| 축 | 필요한 데이터 |
|---|---|
| 성장성·수익성·재무구조·부채상환능력·활동성 | 재무제표(L1 19종)만 |
| **생산성** | 재무제표 + **기업개요의 종업원수**([12 §2](12_기업정보_지표체계.md) B영역) |

**종업원수가 없으면 이 축은 비워둔다.** 억지로 추정하지 않는다 — 비상장 소형사는 종업원수
공시가 불규칙하므로 비어 있는 것이 정상 상태다(§2.4 "근거 없는 것은 단정하지 않는다").

**Guard 1과의 연결**: 종업원수 기준일이 재무제표 기간과 6개월 이상 차이 나면 Guard 1이
`is_estimated`를 붙인다(§2.6). 이 플래그는 **생산성 3종에만 전파**되며, 나머지 5축은 종업원수를
쓰지 않으므로 영향받지 않는다 — 오염 범위가 축 하나로 격리된다는 점이 축을 분리해 둔 실익이다.

**계산하지 않는 원본 생산성 지표**: 1인당 인건비·부가가치·노동소득분배율·총자본투자효율은
인건비·부가가치가 L1에 없어 계산할 수 없다. **L1을 늘리지 않고 비워둔다** — O-41(계속사업이익)과
같은 판단이다. 필요해지면 그때 L1을 확장한다.

> **회전율 분모 기준(O-38)**: 위 표는 **기말잔액** 기준이다. 실무에서는 평균잔액(기초+기말)/2를
> 쓰기도 하며 값이 달라진다. 시계열을 보관하므로 평균 기준 전환도 가능하나, **어느 쪽인지
> 명시하지 않으면 같은 기업의 값이 자료마다 다르게 보인다** — 기말 기준으로 통일하고 리포트에
> 명기한다.

> **계산 불가와 값 없음을 구분한다**(D-17 연계): 분모가 0이거나 누락돼 계산할 수 없는 경우,
> `None`으로 뭉뚱그리지 않고 사유를 남긴다. "자기자본 데이터가 없어 ROE 계산 불가"와
> "ROE가 0"은 완전히 다른 정보다.

## 2.6 데이터 가드레일 5종 (사용자 제공, 2026-07-26)

정제되지 않은 데이터가 들어와 전체 계산을 무너뜨리지 않도록 설치하는 방어 장치다.

### ⚠ 실행 시점 보정 — 전부 "입력단"에 두면 안 된다

5개 가드는 성격이 달라 **작동 지점이 세 곳으로 나뉜다.** 전부 입력단(Ingestion)에 몰면
정상 데이터를 거부하는 문제가 생긴다.

| 가드 | 작동 지점 | 이유 |
|---|---|---|
| **Guard 0** OCR 신뢰도 하향 | **저장 시** | 파싱 결과를 L1으로 확정하는 순간 판정 |
| **Guard 1** 이종 데이터 결합 | **저장 시** | 두 영역 데이터를 붙이는 시점의 문제 |
| **Guard 2** 분모 0·음수 | **계산 시** ⚠ | 자본잠식은 **잘못된 데이터가 아니라 정상적 사실**이다. 입력단에서 막으면 진짜 자본잠식 기업을 받을 수 없다 |
| **Guard 3** 실효세율 캡핑 | **계산 시** ⚠ | 위와 동일 — 원본 세율은 그대로 두고 산출 단계에서만 보정 |
| **Guard 4** 회전율 기준 표기 | **표시 시** | 계산 결과를 사람에게 보여줄 때의 규격 |
| **Guard 5** 시계열 불연속 | **저장 시** | 레코드를 이력에 추가하는 시점의 검사 |

> Guard 2·3을 계산단에 두는 것이 핵심이다. **L1은 있는 그대로 저장하고, 판단은 L2 산출 시점에
> 한다** — 09 §2의 계층 분리가 여기서 값을 한다.

### Guard 0 — OCR 저신뢰 결과의 신뢰도 하향 (O-12 해결, 2026-07-26)

전처리부(§3)의 OCR 결과에 `extraction_warnings`가 있으면, 그 수치의 신뢰도를
**`Stated` → `Inferred`로 자동 하향**한다.

**근거**: 09 §2의 L1 정의는 *"재무제표에 **그대로 적힌** 금액"*이고 신뢰도가 `Stated`다.
그런데 OCR로 뽑은 값은 **원본에 그렇게 적혀 있는지 자체가 불확실**하다 — 숫자 `8`을 `3`으로
잘못 읽어도 형식상 L1으로 들어온다. 즉 **OCR 성공은 "원본에 이렇게 적혀 있다고 추정한다"는
뜻이지 확정이 아니다.**

- §2.4 "근거 없는 것은 단정하지 않는다"의 직접 적용이다
- 검증 에이전트(§7.1)가 5요소를 대조할 때 이 값을 **우선 확인 대상**으로 삼는다
- 09 §2.5의 `rounded`, 12 §4.1.1의 `converted`, Guard 3의 `adjusted_tax_rate`와 같은 계열 —
  **손댄 값에는 흔적을 남긴다**

> 작동 지점은 **저장 시**다(아래 표에 반영). 파싱 결과를 L1으로 확정하는 순간 판정한다.

### Guard 1 — 이종(Cross-Domain) 데이터 결합

종업원수는 재무제표가 아니라 **기업개요** 영역 데이터다(12 §2 B영역). 수집 시점이 다르면
생산성 지표가 오염된다.

```rust
pub struct EmployeeCount {
    pub count: u32,
    pub as_of_date: String,   // 기준일자 -- 필수
}

pub struct ProductivityMetric {
    pub value: f64,
    /// 재무제표 결산일과 종업원수 기준일의 차이가 6개월 이상이면 true
    pub is_estimated: bool,
}
```

- 지표 계산 시 **재무제표 결산일에 가장 가까운 시점**의 종업원수를 매핑한다
- 시점 차이 **6개월 이상**이면 `is_estimated: true`를 부착한다
- **방어 대상**: 6축 중 생산성 3종(1인당 매출액·영업이익·순이익)뿐이다. 나머지 5축은 종업원수를
  쓰지 않으므로 이 플래그가 붙지 않는다 — 오염 범위가 한 축으로 격리된다
- **종업원수 자체가 없으면** Guard 1이 작동할 일도 없다. 생산성 3종을 비워두면 끝이다
  (`is_estimated`는 "값이 있는데 근사"라는 뜻이지 "값이 없다"는 뜻이 아니다)

> **RD-03 이력 (2026-08-02)**: 재무진단 5축에 생산성이 없던 시기에는 이 가드가 **계산하지 않는
> 지표를 방어**하고 있었다. 생산성 축을 6번째로 추가하면서 방어 대상이 실재하게 되었다
> ([13 §RW-2](13_재워크스루_결과.md)).

### Guard 2 — 분모 0·음수 예외 처리

자본잠식·영업손실·무차입 기업에서 계산이 깨지지 않게 한다. D-17(계산 불가와 값 없음 구분)의
구체화다.

| 지표 | 예외 상황 | 처리 |
|---|---|---|
| ROIC | 투하자본(`TotalEquity + Borrowings`) ≤ 0 | `N/A` + **"투하자본 음수로 계산 불가"** 사유 명시 |
| ROE | `TotalEquity` < 0 | 숫자를 내지 않고 `N/A` (**자본잠식** 표기) |
| 이자보상배수 | `InterestExpense` = 0 | `Inf`가 아니라 **"무차입/무이자"** 텍스트 라벨 |
| 회전율 계열 | 기말잔액 = 0 | `N/A` |

> 이자보상배수에서 `Inf` 대신 텍스트 라벨을 쓰는 것이 중요하다 — 무한대는 "무한히 안전하다"는
> 오해를 주지만, 실제 의미는 "빚이 없다"는 다른 사실이다.

### Guard 3 — 실효세율 극단값 캡핑

ROIC의 세후영업이익 산출에 쓰는 실효세율(`IncomeTaxExpense ÷ ProfitBeforeTax`)은 환급·특수
회계 처리로 이상값이 나올 수 있다.

| 케이스 | 처리 |
|---|---|
| **A. 세전이익 < 0** (적자) | 실효세율 개념이 성립하지 않음 → 법정 기본세율 적용 또는 `세후영업이익 = 영업이익`으로 보수적 추정 |
| **B. 실효세율 > 100% 또는 < 0%** | **[0%, 45%] 범위로 캡핑** |

```rust
pub struct EffectiveTaxRate {
    pub rate: f64,
    /// 캡핑·대체가 적용됐는지. true면 원본 그대로가 아니다.
    pub adjusted_tax_rate: bool,
}
```

> **플래그 패턴의 일관성**: `adjusted_tax_rate`는 §2.5의 `rounded`, 12 §4.1.1의 `converted`와
> 같은 계열이다 — **값을 정규화하되 손댔다는 흔적을 반드시 남긴다.** 세 곳 모두 "보정된 값은
> 검증 시 우선 확인 대상"이라는 동일한 규칙을 따른다.

### Guard 4 — 회전율 기준 표기 의무화 (O-38 확정)

| 구분 | 규격 |
|---|---|
| UI·리포트 표기 | `매출채권회전율 (기말)` — 괄호 표기 **필수** |
| 계산식 스펙 | 매출액 ÷ **기말** 매출채권 |

나중에 평균잔액 방식으로 전환하더라도, 기존 리포트에 `(기말)`이 남아 있으면 **시계열 비교 시
착오가 생기지 않는다.** 기준을 바꾸는 것보다 기준을 감추는 것이 더 위험하다.

### Guard 5 — 시계열 불연속(파편화) 탐지

성장성 3종은 전기 값이 필수인데, 회계기준 변경(K-IFRS ↔ K-GAAP)이나 결산기 변경(12월 결산 →
3월 결산)이 있으면 단순 비교가 오류를 만든다.

```rust
pub struct FiscalPeriod {
    pub fiscal_year: String,
    /// 결산 월수 (기본 12). 결산기 변경이 있으면 달라진다.
    pub fiscal_month_count: u8,
}
```

- 시계열 레코드 추가 시 `fiscal_month_count`를 확인한다
- **전년도와 당해 결산 월수가 다르면 증가율 계산을 스킵**하고 `period_mismatch` 경고를 띄운다

> 연환산(annualize)해서 억지로 비교하지 않고 **스킵**하는 것이 맞다 — 연환산은 추정이 개입해
> `Stated` 값에서 나온 지표가 슬그머니 `Inferred`가 되어버린다.

## 2.5 단위(③) — 저장은 정밀하게, 반올림은 표시 시점에만 (사용자 결정, 2026-07-26)

**핵심 원칙**: 천원·백만원 단위 처리는 **보고서 작성·화면 표시 시점에만** 적용한다.
저장은 원 단위 정밀값 그대로 유지한다.

```
저장 계층 ─── 원 단위 i64 정밀값 (무손실)          ← 검증·계산은 여기서
    │
    ▼ 표시할 때만 변환
표시 계층 ─── 천원 / 백만원 반올림 + 반올림 고지     ← 사람이 읽는 곳
    │
    ▼ 사용자가 원하면
정밀 조회 ─── 저장된 정밀값 또는 OpenDART 원본 재조회
```

### 왜 저장 시점에 반올림하지 않는가

저장 단계에서 반올림하면 **정밀값이 영구히 사라진다.** 그러면:
- §7.1 검증 에이전트의 5요소 일치 판정에서 반올림 오차 때문에 정상 수치가 `Contradicted`로
  오판된다 (반올림 허용 오차라는 예외 규칙을 따로 만들어야 하는 부담이 생긴다)
- L2 지표 계산이 반올림된 값 위에서 이뤄져 오차가 누적된다
- 사용자가 정확한 금액을 알고 싶어도 되돌릴 방법이 없다

저장을 정밀하게 유지하면 **이 세 문제가 한꺼번에 사라진다** — 검증은 정밀값끼리 비교하므로
반올림 예외 규칙 자체가 불필요해지고, 계산도 정확하며, 정밀 조회도 가능하다.

### 표시 단위 선택 규칙

| 금액 규모 | 표시 단위 |
|---|---|
| 10억원 미만 | 천원 |
| 10억원 이상 | 백만원 |

### 반올림 고지 (필수)

반올림이 발생한 표시값에는 **반드시 다음 두 가지를 함께 제공**한다.

1. 반올림 사실 고지 문구
2. 정밀값을 직접 조회할 수 있는 경로

```
영업이익  35,000 백만원

※ 표시 금액은 백만원 단위로 반올림된 값입니다.
   정확한 금액이 필요하면 원본 데이터를 직접 조회하세요.
   → 정밀값: 34,999,617,000원  |  출처: OpenDART 2025 사업보고서 (조회하기)
```

### 데이터 모델

```rust
/// 저장은 항상 원 단위 정밀값. 표시 단위는 저장하지 않고 표시 시점에 계산한다.
pub struct MonetaryAmount {
    /// 원 단위 정밀값 -- 검증·계산은 전부 이 값으로 수행한다.
    pub won: i64,
    /// 원본 문서에 적혀 있던 표기 단위 (추적용, 계산에는 쓰지 않음)
    pub source_scale: SourceScale,
}

pub enum SourceScale { Won, Thousand, Million, HundredMillion, Trillion }

/// 표시 전용 -- 저장되지 않는 파생 값
pub struct DisplayAmount {
    pub value: i64,             // 반올림된 표시값
    pub scale: DisplayScale,    // 천원 | 백만원
    pub rounded: bool,          // 반올림 발생 여부 -> true면 고지 문구 필수
    pub exact_won: i64,         // 정밀 조회용 원본값
}

pub enum DisplayScale { Thousand, Million }

impl MonetaryAmount {
    pub fn to_display(&self) -> DisplayAmount { /* 위 규칙대로 단위 선택 + 반올림 */ }
}
```

> 표시 계층을 저장 계층에서 분리했으므로, 비교·L2 계산·검증은 전부 `won` 필드에서 이뤄진다 —
> 단위 환산 규칙이나 반올림 허용 오차를 따로 둘 필요가 없다.

## 3. D-04 해결에 직접 쓰이는 규칙 — 요약 불가능성

이 문서의 실질적 산출물이다.

### 3.1 재무 수치는 요약으로 갈음할 수 없다

[wiki.rs:244](../../src-tauri/src/wiki.rs)의 현재 동작은 임계값을 넘으면 본문을 버리고
`title`·`summary`·`tags`만 보낸다. 그런데 `summary`는 보통 이런 형태다.

```
title:   "삼성전자 2025년 재무제표"
summary: "2025년 연간 실적 요약"          ← 숫자가 하나도 없다
body:    "매출액 300조, 영업이익 35조..."  ← 재무 수치는 전부 여기
```

**즉 재무 수치를 담은 페이지에 한해, 요약 대체는 정보 손실이 아니라 정보 소멸이다.**
일반 서술형 페이지는 요약으로 대략의 뜻이 전달되지만, 수치 페이지는 요약하면 남는 게 없다.

### 3.2 페이지 단위 플래그 — `body_required`

라우터가 "이 페이지는 본문을 반드시 넣어야 하는가"를 판단할 수 있어야 한다.

```rust
pub struct WikiEntry {
    // ... 기존 필드 ...
    /// 이 페이지의 본문이 재무 수치를 포함하는가.
    /// true면 컨텍스트 예산이 부족하더라도 요약으로 대체하지 않는다 --
    /// 대체할 바에는 이 페이지를 아예 제외하고, 제외했음을 응답에 명시한다.
    pub body_required: bool,
}
```

### 3.3 예산 부족 시의 우선순위

컨텍스트 예산이 모자랄 때 무엇을 버릴지의 순서를 정한다.

```
1순위로 지킨다 ─ 질문 대상 기업의 L1 원천값 (5요소 완전한 것)
2순위          ─ 같은 기업의 L2 산출값
3순위          ─ 관련 서술형 페이지 본문
4순위          ─ 타 기업·타 기간 페이지 (먼저 버린다)

★ 4순위까지 버려도 예산이 모자라면:
  요약으로 "대체"하지 말고, 페이지를 "제외"한 뒤 응답에 제외 사실을 명시한다.
  -- 조용히 틀린 답보다, 부족함을 밝힌 답이 낫다 (D-04의 핵심)
```

## 5. 데이터 모델

```rust
/// 재무 수치 1건 -- 5요소 불가분 단위(1절).
pub struct FinancialFigure {
    pub account: AccountRef,      // ① 계정명 (표준 매핑 or 원본 표기)
    pub amount: i64,               // ② 금액
    pub unit: MonetaryUnit,        // ③ 단위·통화
    pub period: Period,            // ④ 기간·시점
    pub provenance: Provenance,    // ⑤ 출처·신뢰도
}

pub enum AccountRef {
    Standard(Account),      // 표준 계정으로 매핑됨
    Raw(String),            // 매핑 실패 -- 원본 표기 그대로 보존(L1 지위는 유지)
}

// 금액·단위는 2.5절의 MonetaryAmount / DisplayAmount 참고.
// 저장은 원 단위 정밀값, 반올림은 표시 시점에만 발생한다.

pub struct Period {
    pub label: String,      // "2025-FY", "2025-Q3"
    pub kind: PeriodKind,   // 회계연도 / 분기 / 특정 시점(재무상태표 기준일)
}

pub struct Provenance {
    pub layer: FigureLayer,        // L1 / L2 / L3
    pub confidence: Confidence,    // Stated / Inferred / Uncertain
    pub source_page_id: Option<String>,  // 근거 위키 페이지
}

pub enum FigureLayer { Source, Derived, Comparative }

/// L2 계산 결과 -- 값이 없는 이유를 구분한다(D-17).
pub enum MetricValue {
    Value(f64),
    NotAvailable { reason: String },   // 예: "자기자본 데이터 없음"
    DivisionByZero,
}
```
