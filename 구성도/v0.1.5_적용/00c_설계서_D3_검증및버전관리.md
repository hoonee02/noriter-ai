# 설계서 D3 (부분 개정) — §4.1 추가: 검증/최신화·버전관리 에이전트, SalesCS 재설정, 재작업 루프 상한

> 범위: [00b_설계서_D2_에이전트조직도.md](00b_설계서_D2_에이전트조직도.md)(D2) 위에 추가로 얹는
> 부분 개정. D2의 이사장 + ①~⑤ 5팀 구조는 그대로 유지하고, **신규 에이전트 2종**(검증,
> 최신화·버전관리)을 추가하며 **⑤ SalesCS를 재설정·통합**한다. D2가 미결로 남겨둔
> **O-5(SalesCS 범위)**와 **O-6(재작업 루프 상한)**을 이 문서에서 확정한다.
> D1·D2 본문은 결함 추적을 위해 그대로 보존한다.

## 1. 개정 배경

사용자가 제시한 참고 조직도(원장 → 기획조정실 → 정보수집통합단 / **정보검증·자산관리본부 ★** /
디지털플랫폼센터, 그 아래 실시간수집·모니터링센터·신뢰성검증센터·자산갱신·품질관리센터·
정보보호·보안센터)는 "효율적인 아카이빙"을 중심으로 한 정보기관형 구조다. 이번 개정은 그 조직도
전체를 이식하지 않고, **아카이빙 효율에 직접 기여하는 2개 기능만** 신규 에이전트로 추출한다:

| 신규 에이전트 | 참고 조직도의 대응 부서 | 핵심 기능 |
|---|---|---|
| **검증 에이전트** | 신뢰성검증센터 (팩트체크검증팀·AI·오류검수팀·출처·저작권검증팀) | 산출물의 사실확인·오류검수·출처검증 |
| **최신화·버전관리 에이전트** | 자산갱신·품질관리센터 (데이터최신화팀·오보·정정보도반영팀·역사·영구아카이브갱신팀) | 위키 반영 시 버전 관리·정정 처리·아카이빙 정책 |

실시간수집·모니터링센터는 이미 D2의 ① Ingestion팀(단, O-4 결정으로 실제 크롤링 없이 수동 원문
정리로 한정됨)과 기능이 겹치므로 신설하지 않는다. 정보보호·보안센터는 이번 목적(G-1~G-4) 범위
밖이라 신설하지 않는다.

## 2. 왜 이 2개가 "아카이빙 효율"의 핵심인가

D1 최초 [구성도.md](../구성도.md) §4에서 이미 "일반적인 LLM 위키 확장 포인트"로 **버전 히스토리**를
언급했지만("이전 버전 diff를 보존하는 것"), 지금까지 어떤 개정에서도 실제로 설계되지 않았다.
이번 2개 에이전트가 그 공백을 메운다.

- **검증 에이전트가 없으면**: D2의 "이사장 승인 게이트"는 이사장이 팀의 산출물을 **자기 판단만으로**
  승인/반려했다 — 사실상 자기 팀 결과를 자기가 채점하는 구조였다. 검증 에이전트를 별도로 두면
  이사장은 검증 리포트라는 **근거를 기반으로** 판단하게 되어, 하이브리드_에이전트_RAG.md의
  **Generation Evaluator**(생성 결과가 근거에 부합하는지 독립적으로 평가) 개념에 정확히 부합한다.
- **최신화·버전관리 에이전트가 없으면**: 위키에 새 정보가 들어올 때 기존 페이지와 어떻게
  병합·대체·아카이빙할지 규칙이 없다 — D-03(자기오염) 조치안이 "승격은 사람 검토"까지만
  정했을 뿐, 승격 **이후** 버전을 어떻게 관리할지는 공백이었다. 이 에이전트가 그 공백을 메운다.

## 5. 검증 에이전트 상세

- **입력**: 팀별 `TeamOutput`(D2) — findings + 팀 자체 판단 신뢰도
- **수행**: (a) findings 내 주장(claim) 단위로 쪼개 위키/원본 근거와 대조하는 팩트체크,
  (b) 서술의 논리적 비약·모순을 훑는 AI 오류검수, (c) 인용된 출처가 실제로 추적 가능한지 +
  원문을 과도하게 그대로 베끼지 않았는지(저작권) 점검
- **출력**: `VerificationReport` — 이사장은 이 리포트를 근거로 승인/반려를 판단하므로,
  이사장의 판단 근거가 처음으로 **추적 가능한 문서**가 된다(그 자체가 §2.5/§2.6이 요구하는
  "근거 있는 검증"의 실현)
- **팀 내부 1차 검수와의 관계**: D2 §5 ③에서 Research팀이 "AI 요약 검수"를 자체 수행한다고
  했는데, 이는 **팀의 자기 검수(1차)**이고 검증 에이전트는 **독립된 2차 검수**다 — 자기 채점과
  타인 채점을 구분한 것이 이번 개정의 핵심.
- **O-8 해결 (2026-07-26)**: "근거를 못 찾음"과 "애초에 관련 페이지가 없음"을 이사장에게
  다르게 보고하거나 처리 로직을 분기하지 않는다. **검증 에이전트 자신의 리포트에 있는 그대로
  정리만 한다** — `FactCheckItem.note`에 상황을 서술하고 끝. 이사장의 승인/반려 판단에는
  `verdict`(Unverifiable 여부)만 반영되고, note는 사람이 나중에 리포트를 읽을 때 참고하는
  부가 정보다. 별도 분기·에스컬레이션 로직을 추가하지 않는다.

## 6. 최신화·버전관리 에이전트 상세

- **입력**: 이사장이 승인한 draft
- **수행**:
  1. 같은 `company`+`period`(또는 같은 주제)의 기존 위키 페이지가 있는지 조회
  2. 있다면 `ChangeKind`를 판정 — 완전히 새로운 내용(`New`), 기존 서술이 틀렸음이 확인됨
     (`Correction`, 예: 뉴스 오보가 나중에 정정된 경우), 단순 수치 갱신(`Refresh`, 예: 분기가
     바뀌어 매출액이 갱신된 경우)
  3. `Correction`인 경우 기존 페이지를 삭제하지 않고 `supersedes`로 연결한 뒤 신뢰도를
     `Uncertain`으로 즉시 하향 — "이전에 확실하다고 했던 것이 틀렸다"는 사실 자체가 중요한
     이력이므로 삭제 대신 **보존 후 대체**
  4. **아카이빙 정책**: 오래되었거나 상위 버전으로 완전히 대체된 페이지는 `archived: true`로
     표시해 §2.5 인덱스 우선탐색 대상에서 제외한다 — 삭제는 하지 않는다("역사·영구아카이브갱신"
     기능 대응). 이렇게 하면 위키가 커져도 활성 인덱스는 항상 최신 버전만 남아 **검색 효율이
     유지**된다 — 이것이 "효율적인 아카이빙"의 실질적 구현이다.
- **D-06(ID 충돌)과의 관계**: 이 에이전트가 버전 부여를 전담하므로, ID 자체는 여전히 고유해야
  하지만(D1 조치안대로 단조 카운터/UUID 필요) 버전 충돌(같은 주제의 동시 갱신)은 이 에이전트가
  판정 로직으로 흡수한다.

## 7. ⑤ SalesCS 재설정·통합

D2 §5 ⑤에서 미결(O-5)로 남겼던 범위를 다음과 같이 확정한다.

- **범위**: 브리핑에서 제안한 "좁은 범위(A안)"를 채택 — 리포트/엑셀 포맷팅 + 전달 + 열람자의
  후속 질의응답. 외부 B2B 영업·고객 계정 관리(넓은 범위 B안)는 이번 버전에서 제외.
- **통합 방식**: 기존에는 SalesCS가 이사장 승인 직후의 draft를 바로 받아 포맷팅했다(D2 §3).
  이번 개정으로 **입력을 최신화·버전관리 에이전트의 확정 기록(`VersionRecord`가 붙은 최종본)으로
  변경**한다 — 즉 SalesCS는 더 이상 "승인된 초안"이 아니라 "버전이 확정된 위키 페이지"만 다룬다.
  - 이유: draft를 바로 포맷팅하면, 같은 분석이 나중에 `Correction`으로 정정될 때 SalesCS가 이미
    내보낸 리포트/엑셀이 구버전 그대로 남아 불일치가 생긴다. 최신화 에이전트를 거치게 하면
    SalesCS의 산출물은 항상 "그 시점의 확정 버전"을 반영하게 되고, 나중에 정정이 발생해도
    `supersedes` 체인을 통해 추적 가능하다.
- **엑셀 출력(G-4, D1 §4.4)과의 연결**: `근거` 시트에 위키 페이지 ID뿐 아니라 **버전 번호**도
  함께 기재하도록 D1 §4.4 명세를 확장한다 — "이 리포트는 v3 기준"임을 명시해, 이후 `Correction`이
  발생해도 당시 리포트가 어느 버전에 근거했는지 항상 추적 가능하게 한다.

## 8. O-6 해결 — 재작업 루프 상한 + 미결작업 문서

사용자 결정: **직전 3회 같은 작업을 수행한 뒤에도 같은 작업(반려)이 다시 나오면, 반복을 멈추고
"미결작업" 문서에 기록한다.** (D2 브리핑에서 제안했던 "상한 회수 + 강제 승인"안 대신 채택)

### 8.1 "같은 작업"의 판정 기준
반려 사유(reason)와 대상 팀(team)의 조합을 1회 시도로 카운트한다. 동일 팀에 대해 **3회** 반려가
발생한 뒤 **4번째**도 이전과 실질적으로 같은 반려(동일 팀 + 사유가 유의미하게 달라지지 않음)로
판정되면 루프를 중단한다.

```rust
pub struct ReworkAttempt {
    pub team: TeamRole,
    pub reason: String,
    pub attempt_no: u32,
}

const REWORK_LIMIT: u32 = 3;

pub enum ReworkOutcome {
    Continue(ReworkAttempt),
    Escalate { team: TeamRole, history: Vec<ReworkAttempt> }, // 미결작업으로 이관
}
```

### 8.2 `chair_analysis` 개정 (D2 §4 대체)

```rust
            ChairmanDecision::Approve => {
                let versioned = run_versioning_agent(app, wiki, &draft).await?; // 신규
                let report = deliver(app, wiki, model, num_ctx, company, &versioned, None).await?; // 재설정된 ⑤ (정상 완료 -> 플레이스홀더 없음)
                return Ok(report);
            }
            ChairmanDecision::RequestRevision { team, reason } => {
                let attempts = history.entry(team.clone()).or_default();
                attempts.push(ReworkAttempt { team: team.clone(), reason: reason.clone(), attempt_no: attempts.len() as u32 + 1 });

                if attempts.len() as u32 > REWORK_LIMIT {
                    // 3회 재작업 후 4번째도 같은 팀에서 반려 -> 미결작업으로 이관, 루프 종료
                    save_pending_work(app, company, &team, attempts).await;
                    // O-7 해결: 막힌 팀만 제외하고 이미 승인된 나머지 팀 결과로 부분 리포트 구성
                    return build_partial_report(app, wiki, model, num_ctx, company, &outputs, &team).await;
                }

                let redo = run_team_with_feedback(..., team, &reason).await?;
                outputs.retain(|o| o.team != team);
                outputs.push(redo);
            }
        }
    }
}
```

### 8.3 미결작업 문서

기존 `wiki/log.md`(append-only, grep 가능)와 같은 패턴으로 신설:

```
<config dir>/noriter-ai/wiki/미결작업.md
```

```markdown
## [2026-07-26 15:40] 삼성전자 분석 — Research(Finance) 팀 미결
- 재작업 횟수: 3회 (상한 도달)
- 반려 사유 이력:
  1. "영업이익률 계산 근거 누락"
  2. "전기 대비 수치 출처 불명확"
  3. "출처는 명확하나 신뢰도 등급 재검토 필요"
- 최종 draft(3차): (요약 첨부)
- 상태: 사람 검토 대기
```

이 문서는 §2.6 유지보수의 일부로, ④ Platform 팀의 정기 점검 항목에 편입한다(D2 §5 ④).

**O-9 해결 (2026-07-26)**: 미결작업.md 항목의 재개는 **자동화하지 않는다.** 별도의 "재개" 커맨드나
UI 진입점을 만들지 않고, 사람이 열람/편집 UI(§2.7)로 `미결작업.md`를 직접 열어 확인한 뒤, 필요하면
사용자가 직접 새 분석 요청을 다시 실행하는 것으로 처리한다. 시스템은 "기록해 둔다"까지만 책임지고,
"다시 시도할지, 언제, 어떻게"는 전적으로 사람의 판단에 맡긴다 — D-16(취소 기능)이나 다른 자동
재시도 로직과 얽히지 않도록 의도적으로 단순하게 유지한 것이다.

### 8.4 부분 리포트 구성 (O-7 해결)

**부분 리포트** = 분석에 관여한 팀 중 일부가 승인·버전화까지 정상 완료되고, 특정 팀만 재작업
상한(8.1)에 걸려 미결작업으로 이관된 경우, **완료된 팀 결과는 그대로 담고 미결 팀 자리는 명시적
플레이스홀더로 비워서** 전달하는 최종 리포트다. "전체 무효화" 대신 "됐던 만큼은 준다"는 원칙.

```rust
pub async fn build_partial_report(
    app: &AppHandle,
    wiki: &WikiState,
    model: &str,
    num_ctx: u32,
    company: &str,
    outputs: &[TeamOutput],   // 미결 팀을 포함해 이 시점까지 모인 팀별 결과
    blocked_team: &TeamRole,
) -> Result<String, String> {
    // 이미 검증·승인된(=blocked_team이 아닌) 결과만 최신화·버전관리 에이전트에 넘겨 버전화한다.
    let completed: Vec<&TeamOutput> = outputs.iter().filter(|o| &o.team != blocked_team).collect();
    let versioned = run_versioning_agent(app, wiki, &completed).await?;

    // synthesize를 다시 돌리지 않는다 -- 이미 만든 draft에서 막힌 팀 섹션만 제거하고
    // 플레이스홀더로 치환한다 (추가 LLM 호출 없이 문자열 수준에서 처리).
    let placeholder = format!(
        "[{}] 이 항목은 검증 합의에 이르지 못해 보류되었습니다. \
         자세한 반려 이력은 미결작업.md를 참고하세요.",
        team_label(blocked_team)
    );

    let report = deliver(app, wiki, model, num_ctx, company, &versioned, Some((blocked_team, &placeholder))).await?;
    Ok(report)
}
```

- **재종합(synthesize) 재실행 안 함**: 막힌 팀 하나 때문에 이미 완료된 팀들의 종합까지 다시
  LLM에 태우지 않는다 — 기존 draft에서 해당 섹션만 걷어내고 플레이스홀더로 바꾸는, 추가 LLM
  호출이 없는 단순한 처리로 한정한다(비용/속도 고려 + O-9와 같은 "단순하게 유지" 기조).
- **위키 반영 범위**: 미결 팀 항목은 애초에 승인되지 않았으므로 최신화·버전관리 에이전트가
  다루지 않는다 — 완료된 팀 결과만 정상적으로 버전화·저장된다.
- **엑셀 출력(G-4, D1 §4.4) 연동**: `근거` 시트에서 막힌 팀의 행은 값 대신 "보류"로 표시하고
  미결작업.md 참조를 남긴다.

## 9. 기존 결함·미결사항과의 관계 갱신

| 항목 | 상태 |
|---|---|
| D-01 (큐 교착) | **미해소, 유의 강화** — 파이프라인이 검증→승인→버전화 3단으로 늘어 큐 밖 실행 원칙(D1 조치안)의 중요성이 더 커짐. 검증/버전관리 에이전트의 LLM 호출도 leaf call로만 큐에 등록해야 함 |
| D-03 (자기오염) | **강화 해소** — 최신화·버전관리 에이전트가 `Correction`/`Uncertain` 하향 처리를 전담해, 틀린 추론이 사실처럼 굳는 경로를 한 단계 더 차단 |
| D-06 (ID 충돌) | 최신화·버전관리 에이전트가 버전 판정을 흡수하지만, ID 자체 고유성은 D1 조치안(단조 카운터/UUID) 그대로 필요 |
| 구성도.md §4 "버전 히스토리" 확장포인트 | **이번 개정으로 최초 반영** |
| O-5 (SalesCS 범위) | ✅ 해결 (7절) |
| O-6 (재작업 루프 상한) | ✅ 해결 (8절) |
| O-7 (부분 리포트 구성) | ✅ 해결 (8.4절) — 완료 팀은 그대로, 막힌 팀은 플레이스홀더로 치환, 재종합 없음 |
| O-8 (검증 에이전트 두 상황 구분) | ✅ 해결 (5절) — 별도 분기 없이 검증 에이전트 리포트에 서술로만 기록 |
| O-9 (미결작업 재개 방식) | ✅ 해결 (8.3절) — 자동 재개 없음, 사람이 직접 확인 후 재요청 |
