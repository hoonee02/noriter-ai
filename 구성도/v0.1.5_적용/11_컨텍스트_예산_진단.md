# 컨텍스트 예산 진단 — 가이드라인 및 점검 툴

> [08 §4.3](08_MapReduce_청킹_시험적용.md)에서 확인한 VRAM 6GB 제약을 **운용 가이드라인**으로
> 확정하고(사용자 결정, 2026-07-26), 이를 **수시로 점검할 수 있는 툴**을 설계한다.
>
> ## ⏸ 진단 툴 구현 보류 (사용자 결정, 2026-07-26)
>
> **§1(가이드라인)과 §4(파생 수식)는 유효**하며 프로토타입에 그대로 적용한다. 다만 **§3의 진단
> 툴 구현은 보류**한다.
>
> 이에 따라 §7의 **임시 안전값 `num_ctx = 4096`이 당분간 실질적 운용값**이 된다 — 측정으로
> 대체할 시점이 미정이므로, 구현 코드는 이 값을 상수로 박지 말고 반드시
> `ContextBudget::from_num_ctx(config.context_size)`를 거쳐 나중에 값만 바꿔도 되게 한다.
>
> §2(측정 방법 보정), §3(툴 설계), §5(재점검 트리거), §6(양자화 검토)은 **재개 시 참고용으로
> 보존**한다. 특히 §2의 "Ollama는 OOM으로 터지지 않고 조용히 오프로드한다"는 사실은 툴을 만들지
> 않더라도 수동 점검 시 알아야 할 내용이다.

## 1. 확정된 가이드라인

| # | 원칙 | 내용 |
|---|---|---|
| 1 | **`num_ctx` 단일 전역 설정** | 모델 로드 시점의 전역 설정 하나로 통일. 에이전트별로 다른 값을 쓰지 않는다(08 §4.3: KV 캐시가 로드 시 할당되므로 변경 시 리로드 필요) |
| 2 | **하위 파라미터는 수식으로 파생** | 청크 크기는 상수가 아니라 `chunk_size_for(num_ctx)` = 전체의 **20~25%** 로 자동 산출 |
| 3 | **벤치마킹은 상한 하나만** | 6GB에서 안전한 `num_ctx` 상한 **하나만 측정**하면 나머지 파라미터가 수식으로 자동 확정된다 |

3번이 이 구조의 핵심이다 — 측정해야 할 미지수를 **하나로 줄였다.**

```
     [측정] num_ctx 상한 1개
              │
              ▼ 수식으로 파생
   ┌──────────┼──────────┬──────────────┐
   ▼          ▼          ▼              ▼
청크 크기   논리오류    본문 예산      출력 여유
(20~25%)   프롬프트    (09 §3.3)
```

## 2. ⚠ 측정 방법 보정 — "OOM 지점"이 아니라 "오프로드 지점"이다

제안된 절차(`num_ctx`를 올리다 OOM이 터지는 지점 찾기)에는 보정이 필요하다.

**Ollama는 VRAM이 부족해도 대개 터지지 않는다.** 대신 일부 레이어를 시스템 RAM으로 조용히
내보내고(offload) 계속 동작한다. `CHANGELOG.md` v0.1.2에도 12B급 모델이 6GB 예산을 넘겨
"대부분 시스템 RAM에서 돌아 눈에 띄게 느려진다"는 기록이 있다.

| 기대 | 실제 |
|---|---|
| `num_ctx = 8192` → OOM 크래시 | `num_ctx = 8192` → **성공하지만 5~10배 느려짐** |

즉 성공/실패 이분법으로는 한계를 찾을 수 없다. **조용히 느려지는 것**이므로, D-04·D-08과 같은
부류의 silent 문제다.

### 대신 측정할 것 — VRAM 적재율

Ollama의 `/api/ps`는 로드된 모델의 **전체 크기**와 **VRAM에 올라간 크기**를 함께 보고한다.
둘을 비교하면 오프로드 발생 여부를 직접 알 수 있다.

```
size_vram == size   →  전량 VRAM 적재 (정상)
size_vram <  size   →  오프로드 발생 (이 지점이 실질적 상한)
```

보조 지표로 **토큰 생성 속도(tok/s)** 를 함께 본다 — `ollama.rs`가 이미 `eval_count`와
`elapsed_ms`를 수집하고 있으므로([ollama.rs:61-66](../../src-tauri/src/ollama.rs)) 추가 계측
없이 계산 가능하다.

## 3. 진단 툴 설계

### 3.1 배치 위치

**🔧 진단 패널** 신설(기존 ⚙ 설정 패널과 분리). 설정은 "값을 정하는 곳", 진단은 "값을 찾는 곳"으로
역할이 다르다.

### 3.2 표시 항목 (현재 상태)

| 항목 | 출처 |
|---|---|
| 모델명 · 양자화 수준 | `/api/tags`, `/api/ps` |
| 모델 전체 크기 vs VRAM 적재 크기 | `/api/ps` |
| **오프로드 여부** | 위 둘의 비교 — 초록/빨강으로 즉시 판별 가능하게 |
| 현재 `num_ctx` | `config.json` |
| 최근 생성 속도(tok/s) | 직전 요청의 `eval_count / elapsed_ms` |

### 3.3 자동 탐색 (이분 탐색)

제안하신 수동 절차(2048 → 4096 → 8192 실패 → 6144)가 정확히 이분 탐색이므로 그대로 자동화한다.

```rust
pub struct CtxProbeResult {
    pub num_ctx: u32,
    pub size_total: u64,
    pub size_vram: u64,
    pub fully_loaded: bool,      // size_vram == size_total
    pub tokens_per_sec: f64,
}

pub struct CtxBenchmark {
    pub probes: Vec<CtxProbeResult>,
    pub max_safe: u32,           // 오프로드가 발생하지 않은 최대값
    pub recommended: u32,        // max_safe에 안전 마진 적용
}

/// 각 단계: num_ctx 설정 -> 모델 로드 -> 짧은 생성 1회 -> /api/ps 확인
/// 모델 리로드가 매 단계 발생하므로 수 분이 걸린다 -- 진행률을 표시한다.
pub async fn probe_context_limit(app: &AppHandle, model: &str) -> Result<CtxBenchmark, String>;
```

### 3.4 안전 마진 — 찾은 상한을 그대로 쓰지 않는다

**VRAM 가용량은 고정이 아니다.** 브라우저·다른 GPU 앱이 VRAM을 점유하면 측정 당시보다 여유가
줄어든다. 측정값을 그대로 쓰면 평소엔 멀쩡하다가 다른 앱을 켠 순간 오프로드가 시작된다.

```
recommended = max_safe × 0.8   (여유 20%)
```

## 4. 파생 파라미터 수식

```rust
/// 확정된 num_ctx로부터 하위 예산을 계산한다. 상수를 직접 쓰지 않는다.
pub struct ContextBudget {
    pub total: u32,
    pub chunk_size: u32,        // Map-Reduce 청크 (08)
    pub fallacy_prompt: u32,    // 논리오류 26종 프롬프트판 (06)
    pub content: u32,           // 검사·분석 대상 본문 (09 §3.3)
    pub output_reserve: u32,    // 출력 여유
}

impl ContextBudget {
    pub fn from_num_ctx(num_ctx: u32) -> Self {
        Self {
            total: num_ctx,
            chunk_size: num_ctx / 4,        // 25% (가이드라인 2)
            output_reserve: num_ctx / 5,    // 20%
            // 나머지를 프롬프트와 본문이 나눠 쓴다
            ..
        }
    }
}
```

> 이 구조 덕분에 `num_ctx`를 바꾸면 **모든 하위 예산이 자동으로 따라 조정**된다. 모델을 교체하거나
> 양자화 수준을 바꿔도 수식은 그대로다.

## 5. 재점검 트리거 — 언제 다시 측정하나

한 번 측정하고 끝나는 값이 아니다.

| 트리거 | 자동/수동 | 이유 |
|---|---|---|
| **모델 변경** | 자동 감지 후 재측정 권고 | 12B → 4B면 여유가 크게 달라진다 |
| **양자화 수준 변경** | 자동 감지 후 재측정 권고 | Q4 → Q5는 모델 크기가 달라진다 |
| 정기 점검 | ④ Platform팀 유지보수 주기 | 드라이버·Ollama 버전 변경, 상시 점유 앱 변화 반영 |
| 사용자 요청 | 수동 | 체감 속도가 떨어졌을 때 |

**④ Platform팀 업무에 5번째 항목으로 편입한다** — Platform은 이미 "요청 경로에 참여하지 않고
§2.6 주기에 맞춰 도는" 상시 점검 담당이므로 성격이 맞는다.

## 6. 양자화 검토 (Step 2 대응)

측정된 `num_ctx` 상한이 실용에 못 미치면 모델 쪽에서 공간을 확보한다.

| 수단 | 효과 | 트레이드오프 |
|---|---|---|
| 더 강한 양자화 (Q5 → Q4) | 가중치 크기 감소 → KV 캐시 공간 확보 | 출력 품질 저하 |
| 더 작은 모델 (12B → 8B/4B) | 가중치 크기 대폭 감소 | 추론 능력 저하 — 특히 논리오류 26종 판별(06)·3축 심각도 판정(§7.3)처럼 판단이 필요한 작업에 영향 |

> **주의**: 이 프로젝트의 파이프라인은 검증·논리오류 판별·심각도 평가 등 **판단형 작업 비중이
> 크다.** 단순 요약이라면 작은 모델로 내려도 되지만, 3축 심각도 판정을 4B 모델에 맡기면
> E-2에서 우려한 오판 위험이 커진다. 컨텍스트를 얻으려다 판단 품질을 잃는 교환이므로, 양자화
> 조정을 모델 축소보다 먼저 시도한다.

## 7. 임시 안전값 — 측정 전 블로킹 해제 (Step 3 대응)

측정이 끝나기 전에도 구현을 진행할 수 있도록 보수적 기본값을 선언한다.

```rust
/// 측정 전 임시값. 진단 툴 실행 후 config.json의 값으로 대체된다.
const PROVISIONAL_NUM_CTX: u32 = 4096;   // config.rs 현재 기본값과 동일
```

- `4096`은 [config.rs:39](../../src-tauri/src/config.rs)의 현재 기본값이자, 6GB 환경에서
  대체로 안전한 것으로 알려진 값이다.
- 이 값으로 진행하면 청크 크기는 `4096 / 4 = 1024` 토큰이 된다 — 작지만 Map-Reduce 시험(08 §5)을
  돌리기에는 충분하다.
- **측정 완료 시 자동으로 대체**되므로, 구현 코드가 이 상수를 직접 참조하지 않고 항상
  `ContextBudget::from_num_ctx(config.context_size)`를 거치게 한다.
