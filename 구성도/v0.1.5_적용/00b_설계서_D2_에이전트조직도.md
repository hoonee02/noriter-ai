# 설계서 D2 (부분 개정) — §4.1 에이전트 오케스트레이션: 조직도 통합

> 범위: [00_v0.1.5_설계서.md](00_v0.1.5_설계서.md) D1의 **§4.1만** 개정한다. 나머지 절(§1~§3, §4.2~§8)은
> D1을 그대로 따른다. D1 §4.1은 결함 추적을 위해 원문 그대로 보존하고, 이 문서가 그 대체안이다.
> 이 개정은 [04_워크스루_결과보고서.md](04_워크스루_결과보고서.md) 후속조치 1항("D2 개정")의
> 일부이며, D-01/D-06/D-09/D-12/D-13/D-14/D-19와 직접 연결된다.

## 1. 개정 배경

사용자 요청: 오케스트레이터에 **"회사의 이사장" 페르소나**를 부여하고, 기존 4역할(Finance/News/
Market/Synthesis)을 아래 5개 팀 조직도로 재편·통합한다(팀은 향후 추가 가능).

```
[경영진 / 리더십] = 이사장 (오케스트레이터)
   │
   ├── ① 뉴스 수집/모니터링팀 (Ingestion & Scraping)
   ├── ② 데이터/분류 기획팀 (Taxonomy & Data Curation) ★ 도서관 기능의 핵심
   ├── ③ 리서치/인텔리전스 분석팀 (Analysis & Insights)
   ├── ④ 플랫폼/DB 개발팀 (Engine & Search Dev)
   └── ⑤ 영업 및 고객지원팀 (B2B Sales & CS)
```

## 2. 설계 원칙 — 기존 4역할을 어떻게 흡수했는가

기존 Finance/News/Market/Synthesis를 단순 병기하지 않고, **역할의 성격에 따라 조직도 5개 팀에
재배치**했다. 팀을 그대로 늘어놓지 않은 이유는, ④·⑤ 두 팀이 "요청마다 실행되는 분석 담당자"가
아니라 "상시 운영되는 인프라/커뮤니케이션 담당자" 성격이기 때문이다 — 이 구분이 이번 개정의
핵심 설계 판단이다.

| 팀 | 유형 | 실행 시점 | 흡수한 기존 역할 |
|---|---|---|---|
| ① Ingestion | 요청형 | 분석 요청마다 (필요시) | (신규 — G-3의 원천 수집 부분) |
| ② Taxonomy ★ | 요청형 + 상시 | 요청마다 + 백그라운드로 사전 유지보수 | (신규 — §2.3 구조화 규칙을 팀으로 격상) |
| ③ Research | 요청형 | 분석 요청마다 | 기존 **Finance/News/Market**을 산하 서브롤로 흡수 |
| ④ Platform | 상시(점검형) | 요청 시점이 아니라 주기적 점검 | (신규 — §2.6 유지보수를 팀으로 격상) |
| ⑤ SalesCS | 요청형(마지막 단계) | 리포트 확정 직전 1회 | 기존 **Synthesis**의 "전달 포맷" 부분을 흡수 |

기존 Synthesis 역할의 "결과 종합" 기능은 사라지지 않았다 — ③ Research 팀 내부의 마무리 단계로
들어가고, **이사장의 승인 게이트**가 그 위에 새로 추가되었다(3절 참고). "리포트를 사람이 읽기 좋게
포장해 전달하는" 부분만 ⑤ SalesCS로 분리했다.

**이사장 승인 게이트**가 이번 개정의 실질적 신규 요소다. 팀들이 만든 초안을 이사장이 검토해
승인하거나, 특정 팀에 "다시 해와"를 요청할 수 있다. 이는 [하이브리드_에이전트_RAG.md](../하이브리드_에이전트_RAG.md)의
**Generation Evaluator**(생성 결과가 근거에 부합하는지 평가) 개념과 같은 축이며, D-03(자기오염)
방지에도 기여한다 — 이사장 승인을 거치지 않은 초안은 위키에 정식 페이지로 승격되지 않는다.

> 다만 이 게이트는 **에이전트 내부 게이트**이지 사람 검토를 대체하지 않는다. 03_결함기록부의
> D-03 조치안(사람이 명시적으로 "위키에 반영"해야 정식 승격)은 이 게이트와 별개로 여전히 유효하다.

## 4. 데이터 모델 (D1 §3.1/§4.1 대체)

```rust
/// 팀 단위 — 요청마다 소집되는 팀과 상시 운영되는 팀을 구분한다.
pub enum TeamRole {
    Ingestion,  // ① 뉴스 수집/모니터링팀
    Taxonomy,   // ② 데이터/분류 기획팀 ★
    Research,   // ③ 리서치/인텔리전스 분석팀
    Platform,   // ④ 플랫폼/DB 개발팀 (상시 점검형 — 요청 경로에서는 보통 소집 안 됨)
    SalesCS,    // ⑤ 영업 및 고객지원팀 (마지막 전달 단계 전용)
}

/// ③ Research 팀 산하 — 기존 4역할 중 3개가 여기로 흡수됨
pub enum ResearchSubRole { Finance, News, Market }

pub struct TeamTask {
    pub team: TeamRole,
    pub sub_role: Option<ResearchSubRole>,
    pub company: String,
    pub context: Vec<WikiEntry>,  // 라우터가 골라준 관련 페이지
}

pub struct TeamOutput {
    pub team: TeamRole,
    pub findings: String,
    pub confidence: Confidence,
}

pub enum ChairmanDecision {
    Approve,
    RequestRevision { team: TeamRole, reason: String },
}

/// 이사장(오케스트레이터): 필요한 팀만 골라 소집 → 결과 검토 → 승인/반려 → 전달.
/// 주의(D-01 연계): 이 함수 자체를 run_queued로 감싸지 않는다. 큐에는 팀별 최종
/// LLM 호출(leaf call)만 등록한다 — 그렇지 않으면 교착이 재발한다.
pub async fn chair_analysis(
    app: &AppHandle,
    wiki: &WikiState,
    model: &str,
    num_ctx: u32,
    company: &str,
    request: &str,
) -> Result<String, String> {
    let teams = decide_teams(request);              // 예: "재무만" -> [Taxonomy(사전조회), Research(Finance)]
    let mut outputs = Vec::new();
    for team in teams {
        outputs.push(run_team(app, wiki, model, num_ctx, team, company).await?);
    }
    loop {
        let draft = synthesize(app, wiki, model, num_ctx, company, &outputs).await?;
        match chairman_review(app, model, num_ctx, &draft).await? {
            ChairmanDecision::Approve => {
                let report = deliver(app, wiki, model, num_ctx, company, &draft).await?; // ⑤ SalesCS
                return Ok(report);
            }
            ChairmanDecision::RequestRevision { team, reason } => {
                let redo = run_team_with_feedback(app, wiki, model, num_ctx, team, company, &reason).await?;
                outputs.retain(|o| o.team != team);
                outputs.push(redo);
                // 재작업 루프 상한 필요 (5절 미결사항 O-4 참고)
            }
        }
    }
}
```

## 5. 팀별 상세 및 기존 결함과의 연결

### ① Ingestion — 뉴스 수집/모니터링팀
- **결정 완료(O-4, 2026-07-26)**: 실제 외부 크롤링/언론사 제휴/실시간 스크래핑은 **허용하지
  않는다.** `SPEC.md`의 "offline AI assistant" 전제를 유지한다.
- 이 팀의 실제 업무는 **"사용자가 직접 가져온 뉴스 원문(붙여넣기·첨부파일)을 정리하는 것"**으로
  범위를 확정한다. 조직도 원안의 "실시간 크롤링, 언론사 제휴, 긴급 속보 처리"는 v0.1.5에서는
  수행하지 않으며, 후속 버전에서 온라인 모드가 도입될 경우에만 재검토한다.
- 이에 따라 이 팀의 실제 코드 책임은 새 네트워크 계층이 아니라, §2.2 수집·정제(raw → 구조화)
  파이프라인에 **입력 소스를 하나 추가하는 것**으로 좁아진다 — `finance.rs`가 재무제표 파일을
  받듯, 이 팀은 뉴스 원문 텍스트를 받아 정제해 ② Taxonomy 팀의 분류 체계에 태깅한다.
- D-13(G-3 범위 미확정)도 이 결정으로 함께 정리된다: G-3 "뉴스 검색을 위한 키워드 분석"은
  ①이 수집한 **사용자 제공 원문**을 바탕으로 검색 키워드를 뽑는 것이지, 시스템이 능동적으로
  뉴스를 검색·수집하는 것이 아니다.

### ② Taxonomy ★ — 데이터/분류 기획팀
- "도서관 기능의 핵심"이라는 사용자 지정이 [구성도.md](../구성도.md) §2.3(구조화)·§2.4(저장소의
  태그/관계 체계)와 정확히 일치한다. 이 팀을 **§2.3/§2.4의 실질적 소유자**로 지정한다.
- **D-12 해소 지점**: G-2의 "특정 형식" 재무제표 계정과목 매핑 사전(원본 표기 → 표준 계정)을
  이 팀의 산출물로 명확히 귀속시킨다. 재무 에이전트가 즉흥적으로 매핑을 판단하지 않고, 이 팀이
  미리 정의한 사전을 조회하는 구조로 D-12를 해소한다.
- 상시 운영 성격도 있다 — 분류 체계 자체는 요청마다 새로 만드는 게 아니라 누적·개정되므로,
  §2.6 유지보수 주기에 맞춰 백그라운드로도 점검한다.

### ③ Research — 리서치/인텔리전스 분석팀
- 기존 Finance/News/Market 3역할을 서브롤로 흡수. 팀 내부에서 "뉴스 요약, 트렌드 분석, **AI 요약
  검수**"까지 수행한다는 조직도 설명은, D1이 종합 에이전트에만 맡겼던 검증 기능을 이 팀 자체의
  책임으로 앞당긴 것 — 즉 이사장 승인 게이트 이전에 **팀 내부에서도 1차 자체 검수**가 있다는
  뜻으로 해석해 반영했다.
- 병렬/순차 여부(D-09)는 이 팀 산하 3서브롤에 한정해서 결정하면 된다 — 다른 4개 팀은 성격이
  달라(①⑤는 순차적 단계, ④는 비요청 경로) 애초에 "병렬 위임" 논쟁의 대상이 아니다. 이 점에서
  D-09의 범위가 좁혀졌다.

### ④ Platform — 플랫폼/DB 개발팀
- SEO·DB 인프라·UI/UX는 성격상 "기업을 분석하는 에이전트"가 아니라 **시스템 자체를 관리하는
  에이전트**다. 요청 경로(사용자가 "분석해줘"라고 할 때)에는 참여시키지 않는다.
- 대신 §2.6 유지보수 주기의 실행 주체로 배치한다 — **D-19(라우터 규칙 미정)**와
  **D-14(lint의 기업 스코프 미인지)**를 이 팀의 정기 점검 항목으로 귀속시킨다. 즉 "검색이 잘
  되는가", "분류가 꼬이지 않았는가"를 상시 점검하는 팀 = ④ Platform.

### ⑤ SalesCS — 영업 및 고객지원팀
- 요청 경로의 마지막 단계에서 1회만 참여한다: 이사장이 승인한 초안을 리포트/엑셀 형식으로
  포장하고, 후속 질의응답(추가로 궁금한 점) 창구 역할을 한다.
- 사용자가 이 프로젝트를 사내 도구를 넘어 **외부 대상 서비스**로 확장할 계획이 있는지에 따라
  이 팀의 실질 업무 범위(단순 리포트 포맷팅 vs 실제 고객 응대)가 크게 달라진다.
- **결정 필요(신규, O-5)**: 현재 4대 목적(G-1~G-4)은 전부 "내부 분석 도구" 관점이라, ⑤ 팀을
  일단 "최종 리포트 포맷·전달 담당"으로 좁게 정의해 시작하는 것을 권장한다.

## 6. 이번 개정이 낳은 신규 미결 사항

D1 §8의 O-1~O-3에 아래 3건을 추가한다.

- **O-4**: ✅ **결정 완료** — ① Ingestion 팀은 실제 크롤링을 수행하지 않는다. 사용자 제공 원문
  정리로 한정 (5절 참고).
- **O-5**: ✅ **결정 완료** — [00c_설계서_D3_검증및버전관리.md](00c_설계서_D3_검증및버전관리.md) §7에서
  좁은 범위(리포트 포맷·전달 + 후속 질의응답)로 재설정·통합됨.
- **O-6**: ✅ **결정 완료** — [00c_설계서_D3_검증및버전관리.md](00c_설계서_D3_검증및버전관리.md) §8에서
  "3회 재작업 후 동일 반려 반복 시 미결작업 문서로 이관"으로 확정됨.

## 7. D1 결함과의 관계 요약

| 결함 | 이번 개정 이후 상태 |
|---|---|
| D-01 (큐 교착) | **미해소, 오히려 유의 필요** — 계층이 2단(이사장→팀→서브롤)으로 깊어져, 큐 밖 실행 원칙을 지키지 않으면 교착 표면적이 넓어진다. D1 조치안(오케스트레이터를 큐 밖에서 실행) 그대로 적용해야 한다 |
| D-06 (ID 충돌) | 영향 범위 그대로 (③ Research 산하 3서브롤 병렬 시 여전히 유효) |
| D-09 (병렬/순차 모순) | **범위 축소** — ③ Research 팀 산하로 한정 |
| D-12 (계정과목 매핑 미정) | **해소 경로 마련** — ② Taxonomy 팀 소유로 귀속 (실제 사전 작성은 별건) |
| D-13 (G-3 범위 미확정) | **해소** — ① Ingestion 팀은 사용자 제공 원문만 다룸으로 결정 (O-4), G-3는 "제공된 원문 기반 키워드 생성"으로 확정 |
