# 확인사항 체크리스트 (2026-07-26 시점 종합)

> [00_v0.1.5.1_설계서.md](00_v0.1.5.1_설계서.md)(최신 통합본)까지 진행된 상태에서, 사용자가
> 다음으로 확인·결정해야 할 항목을 우선순위별로 모았다. D1~D3 및 이번 통합본에 흩어져 있던
> 미결 항목을 한곳에 모은 것으로, 새 항목은 만들지 않았다(맨 끝 "이번에 새로 포착된 항목" 제외).

## 1순위 — 구현 착수 전 반드시 해소 (Critical 결함)

이 3건은 "설계 방향의 문제"가 아니라 "그대로 구현하면 실제로 고장 나는" 결함이다. 나머지 모든
확인사항보다 먼저 처리해야 한다. (출처: [03_결함기록부.md](03_결함기록부.md))

| ID | 결함 | 상태 | 한 줄 요약 |
|---|---|---|---|
| D-01 | 큐 재진입 교착 | ✅ 해결 방안 확정 | `run_queued`는 "Ollama 처리 중인 작업 체크" 전용 게이트임을 재확인 — `call_llm()` 헬퍼 하나만 이를 호출하도록 구조적으로 강제. 이사장·검증·최신화 등 조율 함수는 직접 호출 안 함. **구현은 아직 안 됨** |
| D-02 | 위키 필드 추가 시 기존 데이터 소실 | ✅ 해결 방안 확정(단순화) | 기존 index.json 보존 불필요로 결정 → 마이그레이션·백업 로직 폐기, `#[serde(default)]`만 적용(재발 방지용, 거의 공짜). **구현은 아직 안 됨** |
| D-03 | 질의 답변 자동 승격 → 자기오염 | ✅ 해결 방안 확정(2저장소) | `query()`의 무조건 저장 로직은 그대로 두고, 저장소만 `wiki/draft.json`(미승격)과 `wiki/index.json`(승격)으로 분리. 컨텍스트 조회는 승격 저장소만 사용, `promote()`는 사람 또는 최신화·버전관리(사후)만 호출. **구현은 아직 안 됨** |

## 2순위 — 설계 확정 필요 ("⚠ 확인 필요" 7개, 이번 통합본이 임의로 채운 부분)

이 항목들은 사용자가 구조·원칙만 주고 구체값을 안 줘서, 설계자 판단으로 일단 채워 넣은 것들이다.
실제 업무 방식과 다를 수 있으니 맞는지 검토가 필요하다. (출처: 00_v0.1.5.1 §11)

| # | 항목 | 현재 채운 값(제안) | 확인할 것 |
|---|---|---|---|
| 1 | Taxonomy 3단계 분류 | ✅ **1단계 해결**(사용자 제공 16종 표준 정책분야: 공공행정·과학기술·교육·교통물류·국토관리·농축수산·문화관광·법률·보건의료·사회복지·산업고용·식품건강·재난안전·재정금융·통일외교안보·환경기상, `MajorCategory` 고정 열거값화) → 2단계(중분류=기업)·3단계(소분류=세부주제)는 여전히 제안 | 2·3단계만 남음 |
| 2 | Research 스탠드얼론 호출 조건 | ✅ **판단 주체 해결**(이사장이 직접 판단, `chairman::decide_routing` — Taxonomy/Research 소속 아님) → 판단 기준("신규 원본자료 없음 + 순수 분석질의")은 여전히 제안 | 구체 기준만 남음 |
| 3 | Platform 50종 통신 카탈로그 | ✅ **해결** — "50종" 상한 폐기, 발신자·수신자·목적 프레임워크만 고정하고 실제 통신은 무제한 누적 기록 후 통계로 품질관리(`CommStats`/`compute_stats`) | 해결됨 (3순위 O-11도 함께 해소) |
| 4 | 최신화팀 우선순위 단계 | ✅ **해결** — "완전일치"+"최근갱신" 병합, 5단계→4단계로 확정: 완전일치·최신 / 부분일치 / 간접참고 / 아카이브·불확실 | 해결됨 |
| 5 | 논리오류 검증의 반려 임계 | ✅ **해결** — 핵심성×파괴성×수용가능성 3축 심각도 평가 도입(§7.3). 기만·왜곡은 항상 반려, 그 외는 핵심성·파괴성 조합으로 반려/재작성지시/기록만 판정 | 해결됨 |
| 6 | Research 경로 무관 동일 거버넌스 | ✅ **해결** — 사용자 확정("맞음") | 해결됨 |
| 7 | 전처리부 스킬 저장소 구조 | ✅ **해결** — 사용자 확정("ok") | 해결됨 |

## 3순위 — 이번 통합본에서 파생된 신규 미결 (O-10~O-13)

(출처: 00_v0.1.5.1 §12)

| ID | 항목 |
|---|---|
| O-10 | 검증의 4대 논리오류 중 "경미함"과 "반려 사유"를 가르는 기준 없음 (2순위 #5와 연결) |

## 5순위 — 이번 대화에서 새로 포착된 항목 (문서에 아직 미기재)

| 항목 | 설명 |
|---|---|
| Platform 유지보수 주기 미정 | §2.6 유지보수 주기가 "몇 시간/며칠 간격"인지 구체 스케줄이 어느 문서에도 없음 — 라우터 규칙·lint 스코프·미결작업 점검·통신로그 분석 4가지 모두 이 주기에 걸려 있어 먼저 정해야 함 |
| 파이프라인 길이에 따른 비용/속도 재점검 | 병렬 디스패치(전처리부+최신화 사전) + Taxonomy/Research + 검증 + 승인 + 최신화 사후 + SalesCS — 분석 1건당 최소 LLM 호출 수가 D1 초안 대비 크게 늘어남. 실사용 시 응답 시간이 허용 범위인지 별도 확인 필요 |

## 체크 순서 권장

```
1순위(Critical 3건) — 설계 확정 완료, 구현만 남음 ──┐
        │                                        │ (구현은 2~5순위 결정과 병행 가능)
        ▼                                        │
2순위(⚠ 7개) 사용자 확정  ──┐                       │
        │                  │ (병행 가능 — 서로 독립적) │
        ▼                  │                      │
3순위(O-10~13) + 4순위(O-1~3) 결정 ◄─┘               │
        │                                        │
        ▼                                        │
5순위(유지보수 주기, 비용/속도) 확정 ◄─────────────────┘
        │
        ▼
전체 파이프라인 재워크스루 (00_v0.1.5.1 §13 "다음 단계" 3항)
        │
        ▼
1순위 3건(D-01/D-02/D-03) 실제 구현 + 재워크스루로 회귀 검증
```

> Critical 3건은 이제 "무엇을 할지"는 정해졌고 "실제 코드로 옮기는 일"만 남았다. 나머지
> 확인사항(2~5순위)과 병행해서 먼저 구현해도 무방하다 — 서로 독립적인 작업이다.
