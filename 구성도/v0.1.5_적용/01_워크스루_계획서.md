## 2. 정적 테스트로 워크스루를 택한 이유

v0.1.5는 아직 코드가 없는 **설계 단계**다. 이 시점의 결함(구조·인터페이스·데이터 모델 오류)은 구현 후
동적 테스트로 잡으면 재작업 비용이 크므로, 코드 작성 전에 설계와 기존 코드의 접합부를 정적으로 검증한다.
특히 이번 변경은 **기존 모듈(`queue.rs`, `wiki.rs`)의 전제를 바꾸는** 성격이라, 신규 설계 단독이 아니라
"신규 설계 × 기존 코드"의 상호작용을 추적하는 것이 핵심이다.

## 6. 체크리스트 (통합_인사이트 8대 원칙 기준)

각 시나리오 추적 시 아래 항목을 대조한다.

| # | 점검 항목 |
|---|---|
| C-1 | 원본(raw)과 정리본(wiki)이 물리적으로 분리되는가 |
| C-2 | 요약/인덱스를 먼저 읽고 필요한 만큼만 하위로 내려가는가 |
| C-3 | 관계에 종류와 신뢰도가 함께 기록되는가 |
| C-4 | 자동 반영과 사람 승인의 경계가 명시되어 있는가 |
| C-5 | 되먹임(질의→저장)이 무분별한 오염을 일으키지 않는가 |
| C-6 | 역할별 에이전트 분업이 실패 지점을 진단 가능하게 하는가 |
| C-7 | 외부 기능이 이름 붙은 도구로 추상화되어 있는가 |
| C-8 | 점검·검증 결과가 본문을 오염시키지 않고 분리되는가 |

## 7. 결함 심각도 기준

| 등급 | 정의 |
|---|---|
| **Critical** | 해당 경로가 아예 동작하지 않거나(교착·크래시), 데이터가 영구 손실됨 |
| **High** | 동작은 하나 결과가 조용히 틀림(silent wrong) — 사용자가 오류를 인지할 수 없음 |
| **Medium** | 기능 제약·누락. 구현 전 결정 필요 |
| **Low** | 개선 권고. v0.1.5 릴리스 차단 사유 아님 |
