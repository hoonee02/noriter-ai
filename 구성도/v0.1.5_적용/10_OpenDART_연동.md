# OpenDART 연동 설계

> 사용자가 OpenDART API 키를 확보(2026-07-26)함에 따라 작성. 이 연동은 **D-05(기업 스코프 필터
> 부재) 보류 해제**의 직접적 계기이며, 동시에 [09_재무수치_정의.md](09_재무수치_정의.md) §2.5의
> "정밀값 직접 조회" 경로를 실제로 구현 가능하게 만든다.
>
> 참고 문서: OpenDART 개발가이드 DS001(공시정보) —
> https://opendart.fss.or.kr/guide/main.do?apiGrpCd=DS001

## ⚠ API 키 취급

**API 키 값은 이 문서를 포함한 어떤 설계 문서·소스 코드에도 기재하지 않는다.** 설계 문서는
저장소에 커밋되므로 키가 이력에 남는다.

기존 `telegram_bot_token`과 동일한 방식으로 처리한다.

```rust
// config.rs -- AppConfig에 필드 추가
pub struct AppConfig {
    pub telegram_bot_token: Option<String>,
    pub opendart_api_key: Option<String>,   // 신규 -- config.json에만 저장
    // ...
}
```

- 저장 위치: `<config dir>/noriter-ai/config.json` (기존 설정 파일)
- 입력 경로: ⚙ 설정 패널에 입력란 추가 (텔레그램 토큰 입력란과 동일한 패턴)
- 키가 없으면 연동 기능 전체를 비활성화하고 안내 문구를 표시한다

## 1. 이 연동이 해소하는 것

| 기존 문제 | OpenDART가 제공하는 것 |
|---|---|
| **D-05c** 기업명 표기 정규화 (`삼성전자` / `삼성전자(주)` / `005930`이 서로 다른 문자열) | **고유번호(corp_code)** — 기업마다 부여된 8자리 고유 식별자. 표기가 어떻든 하나의 키로 수렴 |
| **D-05b** `company` 필드를 채울 출처가 없음 | corp_code 조회 결과를 그대로 채운다 |
| **09 §2.5** "정밀값 직접 조회" 경로가 개념만 있었음 | 실제 조회 API가 생김 |

즉 **D-05의 3개 하위 결함 중 b·c가 해소되고, a(읽기 필터)만 남는다.**

## 2. 정책 변경 — O-4(크롤링 금지)와의 관계

D2에서 확정한 **O-4: ① Ingestion팀은 실제 크롤링을 하지 않는다**(오프라인 전제 유지)와
외형상 충돌한다. 이를 다음과 같이 구분해 정리한다.

| 구분 | 성격 | v0.1.5 정책 |
|---|---|---|
| **크롤링** (O-4가 금지한 것) | 대상을 특정하지 않고 웹을 무차별 수집 | **계속 금지** |
| **공시 API 조회** (이번 신규) | 사용자가 지정한 특정 기업·특정 보고서를 목적을 갖고 조회 | **허용** — 단 사용자 명시 요청 시에만 |

> O-4의 취지는 "시스템이 능동적으로 외부를 돌아다니지 않는다"였으므로, **사용자가 명시적으로
> 요청한 조회**는 그 취지를 깨지 않는다. 다만 `SPEC.md`의 "offline AI assistant" 서술은
> 더 이상 문자 그대로 성립하지 않으므로 **문서 갱신이 필요하다**(O-25).

## 3. 사용 API (DS001 공시정보 그룹)

> 실제 엔드포인트 경로·파라미터명은 구현 시 위 개발가이드에서 확인한다. 아래는 **어떤 기능을
> 무엇에 쓸지**의 설계 수준 정리다.

| 용도 | 필요한 기능 | 우리 시스템에서의 쓰임 |
|---|---|---|
| **기업 식별** | 고유번호(corp_code) 전체 목록 조회 | D-05c의 `canonical_key` 확보. 최초 1회 내려받아 로컬 캐시 |
| **기업 기본정보** | 기업개황 | 2단계(기업) 분류 시 정식 회사명·업종 확인 |
| **공시 탐색** | 공시검색(기간·유형별 목록) | 사업보고서 등 원본 문서 특정 |
| **정밀값 조회** | 공시서류 원문 | 09 §2.5의 "정확한 금액이 필요하면 직접 조회" 경로 |

> DS003(상장기업 재무정보) 그룹에는 재무제표 계정을 직접 반환하는 API가 있어, 장기적으로는
> G-2(재무제표 분석)의 입력을 파일 업로드 대신 API 조회로 대체할 수 있다. 다만 이번 범위는
> 사용자가 지정한 DS001에 한정하고, DS003 활용은 별도 판단으로 남긴다(O-26).

## 4. 기업 식별자 도입 — D-05c 확정 조치

```rust
/// 기업 식별 -- 표시명과 정규화 키를 분리한다(D-05c 조치안).
pub struct CompanyRef {
    /// OpenDART 고유번호(8자리). 필터·경로·인덱스 키는 전부 이 값을 쓴다.
    pub corp_code: String,
    /// 사람이 보는 이름. 표기가 흔들려도 무방하다.
    pub display_name: String,
    /// 종목코드(상장사만). 표시·검색 보조용.
    pub stock_code: Option<String>,
}
```

- `WikiEntry.company: Option<String>` → **`Option<CompanyRef>`** 로 변경
- D-10(기업명이 파일 경로로 직행)도 함께 해소된다 — 디렉터리명에 `corp_code`를 쓰면
  경로 조작 문자(`/`, `..`, `:`)가 원천적으로 들어올 수 없다

```
companies/
└── 00126380/          ← corp_code (표시명이 아님)
    ├── raw/
    └── output/
```

## 5. 캐시 정책

corp_code 전체 목록은 자주 바뀌지 않으므로 매번 조회하지 않는다.

| 데이터 | 캐시 위치 | 갱신 시점 |
|---|---|---|
| 고유번호 전체 목록 | `<config dir>/noriter-ai/dart/corp_codes.json` | 최초 1회 + 사용자가 명시적으로 갱신 요청할 때 |
| 기업개황 | 위키 페이지로 저장 (§2.4 저장소) | 신규 기업 조회 시 |
| 공시 원문 | `companies/<corp_code>/raw/` | 사용자가 조회한 건만 |

> 캐시를 두는 이유는 성능만이 아니다 — 네트워크가 없어도 **이미 조회한 기업에 대해서는 기존
> 오프라인 동작이 그대로 유지**되어야 하기 때문이다.

## 6. 실패 처리

외부 API는 실패할 수 있고, 이 시스템은 실패를 조용히 넘기면 안 된다(D-04·D-08과 같은 부류의
silent-wrong을 만들지 않기 위함).

| 상황 | 처리 |
|---|---|
| API 키 미설정 | 연동 기능 비활성화 + ⚙ 설정 패널로 안내. 나머지 기능은 정상 동작 |
| 네트워크 실패 | 캐시된 데이터로 진행하고, **캐시 사용 사실을 응답에 명시** |
| 조회 결과 없음 | `CompanyRef` 없이 진행하되 해당 페이지의 `company`를 `None`으로 두고 그 사실을 기록 |
| API 오류 응답 | 원문 오류 코드를 로그에 남기고 사용자에게는 재시도 안내 |

## 7. 미결 사항

| ID | 내용 |
|---|---|
| O-25 | `SPEC.md`의 "offline AI assistant" 서술 갱신 — 이제 조건부 온라인이다 |
| O-26 | DS003(재무정보) 활용 여부 — G-2 입력을 파일 업로드에서 API 조회로 대체할지 |
| O-27 | corp_code 캐시 갱신 주기 — 신규 상장·상호 변경 반영을 사용자 수동 갱신에만 맡길지 |
| O-28 | 비상장·해외 기업처럼 corp_code가 없는 대상의 `canonical_key`를 무엇으로 할지 |
